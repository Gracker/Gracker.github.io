在讨论 Android 性能问题的时候，卡顿、响应速度、ANR 常被放在一起。它们可能有共同原因，也可能同时出现，但不是按严重程度划分的三个等级。用户说“卡”，还需要分清是动画不连贯、操作后等得太久，还是系统触发了无响应判定。

动画或列表滚动的不连贯通常称为 Jank；应用启动、亮灭屏或场景切换耗时过长属于 响应慢（slow response / high latency）；ANR 则由具体的系统超时条件触发。掉帧率、启动耗时和 ANR 率各有测量口径，分析时要分开。

本文是响应速度系列的第三篇，主要是讲在使用 Systrace 分析应用响应速度问题的时候，其中的一些延伸知识，包括启动速度测试、Log 输出解读、Systrace 状态解读、三方启动库等内容

版本与历史说明（2026-10-14 核查）：保留 2021 年的分析图片和章节。Traceview 已弃用，下文改用 Android Studio CPU Profiler 的术语，并修正采样单位。线程/组件示例按 AOSP Android 10/11 解释，命令单位另核对 Android 16；App Startup 补充 1.2.0 的依赖和按需初始化行为。不同工具截图不是同一次实验，旧图中的状态、组件名和“加载完成”标注以正文修正为准。

1. Systrace 中进程三种状态解读

这里观察的是 线程调度状态，不是整个进程只有一个状态。同一进程的主线程可以等待，而工作线程仍在运行。旧 Systrace 常把 Running 显示为绿色、Runnable 为蓝色、Sleep 留白；颜色随查看器变化，函数色块更不能当作调度状态。

选中线程状态轨道确认标签，再看对应调度事件。除了这三种，还可能遇到不可中断等待等状态；空白或缺失数据不能一律解释为 Sleep。

1.1 如何分析 Sleep 状态的 Task

Sleep 表示线程此时未在运行、也未在等待 CPU 调度，不能仅凭状态区分“主动/被动”或判断是否正常。常见等待包括 Looper 的 poll、同步 Binder 回复、锁/条件变量和显式 sleep。nativePollOnce 在没有到期消息时等待通常合理，但启动关键任务为何还没送达、消息是否延迟或被屏障阻挡，仍可能值得查。

下图包含 IWindowSession.remove 的 Binder 调用。先把调用区间与线程状态重叠部分对应起来；同步调用可能等待远端，oneway 语义则不同。调用次数多并不独立证明瓶颈，要看关键路径上的累计等待和对端工作。

1.2 如何分析 Running 状态的 Task

Running 表示线程被调度到某个 CPU 上。区间变长时，先比较工作量与输入，再看核心能力、频率、缓存/内存访问和调度切换。函数墙钟区间可能包含多个 Running 和等待区间，不能与实际 CPU 时间混用。

图中选中的是 CPU 0 上的运行区间，另一图的 5.112 ms 是选区。截图没有给出 CPU 拓扑与频率数值，不能据此判断“小核跑错了”或频率不足。前台 UI/RenderThread 也不保证始终在大核运行；调度要平衡延迟、能耗、温控、亲和性和可用算力。

1.3 如何分析 Runnable 状态的 Task

从睡眠被唤醒的线程先具备运行条件，再被调度执行；Running 线程被抢占后也可能回到 Runnable。Runnable 不保证立即运行，其区间很短时甚至不容易在当前缩放下分辨。

这张旧图主要是 Java 线程状态示意，不能直接当成 Linux 调度状态机。Java Thread.State 的 RUNNABLE 可以包含等待 CPU 的线程；RUNNING、READY 不是该枚举的独立值。VM 的 BLOCKED 与内核不可中断等待也不是同一状态；Object.notify 唤醒等待者后仍需重新竞争 monitor，不能理解为立刻进入 Running。

分析长 Runnable 时，查看允许在哪些 CPU 运行、优先级、cpuset/affinity、同核竞争和可用容量。全系统繁忙是候选原因之一，但只剩某些核心忙、亲和性限制或更高优先级任务占用也会造成等待，不能据此断言所有 CPU 已跑满。

2. TraceView 工具在响应速度方面的使用

旧标题沿用 TraceView，但截图是 Android Studio CPU Profiler。独立 Traceview 已弃用，官方建议 Android Studio 3.2 及以后使用 CPU Profiler 检查方法 trace。方法采样/插桩、系统 Trace 和工具的查看界面要分开理解。

2.1 如何抓取应用启动时候的 TraceView

这是 ART Java/Kotlin 方法采样的诊断示例，不是通用的 native 栈或端到端启动基准。先核对设备 am start --help、目标应用的调试权限和可写输出路径。--sampling 的单位是 微秒：1000 微秒才是 1 ms，原文的 --sampling 1 不是每毫秒采一次。单位见 AOSP Android 16 命令帮助。

-S 会停止目标包，避免复用已有进程；它不清空文件缓存或应用数据，也不模拟桌面触摸链路。启动失败、权限拒绝或 Activity 复用时先处理原因，不能把空 trace 当作启动很快。按实际业务终点停止采集，而不是固定等待 10 秒就认定完全加载。文件导入方式与格式兼容性按所用 Studio 版本确认。

2.2 TraceView 工具怎么看

导入方法 trace 后，先确认进程、线程、采集区间、采样或插桩模式及计时口径。下面旧图中，绿色区域还包括应用打包的第三方库，并不只代表作者自己的代码；颜色应结合方法全名和工具图例解释。

阅读 Top Down/Bottom Up 时，区分包含子调用的总耗时与自身耗时；父子项不能重复相加。采样可能漏掉短调用，时间线和调用次数也不能当作完整逐次执行日志。

2.3 TraceView 工具的弊端

方法采样有统计误差，方法插桩会记录更多边界，但往往有更明显的运行开销；不能把两种模式混称为“TraceView 高频采样”。更短的请求间隔也不保证每次按时采到，尤其不应按 1 微秒请求去推算实际频率。

这些数据可以帮助找热点和调用关系，也能在注明计时口径、样本量和开销的前提下比较。最终启动耗时要用较低开销的系统 Trace/启动基准复测；不要用被 profiling 扰动的单次方法时长冒充用户实际延迟。

5. AppStartup 是否能优化启动速度？

三方库的初始化

有些库，你在 Application.onCreate 里明明没调用初始化，它却已经悄悄做了。常见的办法就是通过清单中的 ContentProvider 自动初始化。它依赖 Provider 的进程归属、启用状态和系统绑定流程；不是启动时把整个 APK 声明的所有 Provider 都执行一遍。

SDK 的初始化方式随版本变化。例如 WorkManager 2.6 起使用 App Startup，旧版本独立 Provider 的移除方法不能直接套到新版本。应检查当前依赖和最终合并清单，而不是凭 SDK 名称推断。

这张图概括正常进程初始化中的先后关系。多个库分别自动初始化会增加启动路径工作，也让依赖关系不容易看清；但开发者并非绝对无法控制，是否能关闭自动初始化、替换入口或延迟执行，要看每个 SDK 的公开约定。

AppStartup 库

App Startup 让采用 Initializer 接口的组件共享 InitializationProvider，并通过 dependencies() 声明前置依赖。它不会自动改造任意 SDK 的 Provider，也不承诺给互不依赖的初始化器固定全局顺序。App Startup 1.2.0 的 AppInitializer 会递归初始化依赖、缓存结果并检测循环；自动初始化通常在主线程，手动调用也不会自动切到后台。

原文的“50+ Provider 才有明显收益”和“二三十个库只减少 20 ms 以内”缺少可复核的设备、版本、基线和重复样本，不保留为通用阈值。收益取决于实际移除/延后的关键路径工作；仅合并入口不会消除 SDK 自身的初始化开销。

总结

  1. 用统一入口和显式依赖管理参与的组件，减少重复 Provider 入口。
  2. 将非首屏必需的初始化移出启动关键路径，代价可能转移到首次使用；同时观察 TTID、TTFD 和首次操作延迟。
  3. 控制顺序不等于减少工作或后台化，是否有效需要相同条件下的重复测量。

需要 App 开发同学验证

  1. 检查目标构建的 Merged Manifest/最终 APK，确认 Provider、进程和 Initializer metadata，而不只数源清单条目。
  2. 记录各初始化项的线程、墙钟/CPU时间及依赖，找出关键路径。
  3. 对照 SDK 的初始化合同，确认哪些可延迟、由谁触发、首次使用前如何保证就绪。
  4. 修改后验证冷启动、后台入口、多进程及首次使用，保留失败/缺失样本；用相同编译和数据条件比较结果。

6. IdleHandler 在 App 启动场景下的使用

IdleHandler 在所属 MessageQueue 的 Looper 线程上执行。在 AOSP Android 10 MessageQueue.next 中，队列为空或队头消息尚未到期时可以运行 idle handlers；不要求未来所有消息都已执行完。已到期的同步屏障还会影响这个判断。

原图“所有 Message 都执行完成后”的注释过强。主线程暂时空闲时，网络、后台任务、GPU 或下一次绘制仍可能没有完成；队列持续繁忙时，idle handler 也可能迟迟不执行。

  1. 延后轻量、非必需的工作。 在 Activity.onCreate 注册主队列 IdleHandler，不保证它一定在首帧之后运行，也不会自动使用后台线程。耗时回调会阻挡随后到达的输入/帧任务。queueIdle() 返回 false 会移除，返回 true 会保留以等待以后的空闲机会；不要把 true 当成独立循环或保证执行的定时器。生命周期结束时移除不再需要的处理器。

  1. 完整显示指标应由业务就绪条件触发。 Activity.reportFullyDrawn() 从 API 19 提供，用于报告关键内容/可用状态；它不要求通过 IdleHandler 调用。下图是旧示例：先收到数据完成信号，再等一次主队列空闲。数据已返回和队列空闲仍不足以证明列表、图片都已经展示。

图中的 Android M（API 23）判断与使用 Looper.getQueue() 有关，不能解释为 reportFullyDrawn 到 API 23 才提供。重做时明确成功、空数据和错误页各自的就绪条件，防止重复注册、Activity 已销毁或旧请求回调误报。使用 AndroidX 的就绪报告工具时，也要保留同样的业务条件。

总览图中的 onWindowFocusChange 应为 onWindowFocusChanged，窗口获焦不等于初始显示或内容就绪。am start -W 的等待结果与焦点回调也不是相同指标；Splash→Main 的统计范围取决于实际启动序列与系统实现。对比 TTID/TTFD 官方说明，同时保留首次显示和完整显示的定义。

这个历史输出包含 SplashActivity 的 Displayed +968 ms、MainActivity 的 Displayed +475 ms 和 Fully drawn +3s221ms；am start -W 显示 TotalTime 968、WaitTime 975。这些字段的起点与 Activity 归属不同，不能相加或直接相减求某一阶段，也不能把 +3s221ms 自动当作从触摸桌面图标开始的完整耗时。截图命令还用 sleep 5 后读取现有 logcat 缓冲，可能混入旧记录；实际测量要按时间、包名/Activity及本次启动关联日志。

正确上报 TTFD 能补充首帧指标，并不使原来 TTID 变成“错误时间”。漏报、数据失败或采集不全要单独记录，不记作 0。
