120 Hz 把显示刷新间隔从 60 Hz 的约 16.67 ms 缩短到约 8.33 ms，但屏幕刷新率、App 产帧率和用户看到的帧并不是同一个数字。这篇从一份 Perfetto Trace 出发，解释三个数字怎样对应，以及高刷新率给渲染和功耗带来的取舍。

基本概念

什么是屏幕刷新率？

屏幕刷新率表示显示设备每秒更新的次数，单位是赫兹（Hz）。以下是固定模式下的名义间隔；支持可变刷新率的设备可按其支持范围和策略调整：

  • 60Hz 屏幕：每秒刷新 60 次，每次刷新间隔约 16.67ms
  • 90Hz 屏幕：每秒刷新 90 次，每次刷新间隔约 11.11ms
  • 120Hz 屏幕：每秒刷新 120 次，每次刷新间隔约 8.33ms

显示刷新率限定了屏幕每秒可呈现的更新次数。显示器可以重复显示上一帧，因此刷新 120 次不等于 App 产生或用户看到 120 个不同画面。

什么是 FPS？

FPS（Frames Per Second）需要说明测量对象：可以指 App 产出的帧数，也可以指最终呈现的新帧数。分析卡顿时应先确定指标取的是哪一侧。

以下间隔假设均匀产帧/呈现，不是从平均 FPS 就能推出的每帧处理时长：

  • 60 FPS 的相邻帧间隔约 16.67 ms。
  • 90 FPS 的相邻帧间隔约 11.11 ms。
  • 120 FPS 的相邻帧间隔约 8.33 ms。

App 帧率低于显示刷新率时，屏幕可以重复上一帧；这不一定叫「掉帧」，24 FPS 视频在高刷屏上就是正常例子。判断交互卡顿要看期望呈现时间、实际呈现时间和帧间隔是否稳定。

  1. 内容类型差异：
  • 视频内容：24 FPS 或 30 FPS 视频不必为 120 Hz 屏幕额外合成 120 个不同画面；播放是否平顺还取决于帧节奏与显示模式。
  • 交互界面：滑动列表和跟手动画更依赖稳定的响应节奏。平均 FPS 相同，偶发长帧仍可能很明显。

  1. 帧率稳定性：帧间隔波动会影响观感；比较两种模式时，应连同场景和逐帧呈现时间一起看。

  2. 系统行为：

  • App 没有新帧时，显示系统可能继续呈现上一帧。
  • App 产帧快于显示节奏时，部分工作可能不会转化为新的可见画面；具体是否丢帧要看缓冲区与呈现记录。

不同应用场景有不同的流畅度标准，开发者需要根据应用类型选择合适的优化策略。

什么是 Vsync？

VSync 给 App 和 SurfaceFlinger 提供与显示刷新相关的调度时点。App 有待处理帧时，Choreographer 会请求相应回调；并非每一次 VSync 都触发 App 绘制。相关相位和偏移在第 8 篇展开。

为什么 120Hz 成为新标准？

120 Hz 模式的主要变化是可见更新机会更密，但它是否有收益取决于内容和设备：

  1. 更密的更新机会：如果 App 能稳定产帧，120 Hz 的滑动和动画比 60 Hz 可以呈现更多中间状态；静态内容没有同样收益。

  2. 缩短等待下一次刷新的上限：名义刷新间隔从 16.67 ms 变为 8.33 ms；端到端输入延迟还包含事件分发、App、GPU 与合成，不能直接写成 16.67 ms 变 8.33 ms。

  3. 设备能力：芯片、面板与散热决定能否持续运行在目标模式；只看到屏幕支持 120 Hz，不能推断 App 也能稳定输出 120 FPS。

  4. 功耗管理：设备可按内容与交互状态切换刷新率，避免静态画面持续使用高刷新模式。

  5. 可变刷新率：支持相应硬件和系统策略的设备可调整刷新节奏；传统模式切换与 ARR 的模式内调整要分开，可用范围以具体机型为准。

苹果的 ProMotion 也采用按场景选择帧率的思路。后文引用它的动画建议，目的是比较调度原则，不把 iOS 数值直接当成 Android 设备的配置。

系统实现与工作原理

Perfetto 视角下的 120Hz 渲染流程

120 Hz 固定刷新模式的名义周期是 8.33 ms；主线程、RenderThread、GPU 和 SurfaceFlinger 可流水线重叠，不必串行塞进同一个周期。下面保留历史截图：

  1. Vsync 节奏：图中选择区间为 8.326 ms，接近 120 Hz 的间隔。VSYNC-app 是软件时序计数器，翻转不等于持续执行的高电平，也不能独自证明硬件刷新模式。
  2. 回调与截止时点：Choreographer 处理到期的 Input、Animation、Insets Animation、Traversal、Commit。图注“留给 App 的时间是 8.33 ms”应理解为间隔示意；实际可用时间需对照回调开始、deadline 和 FrameTimeline 预测。
  3. GPU 与提交：图中 RenderThread 是 CPU 线程。箭头 4 把 GPU 绘制与 buffer 入队画在一起，只是示意；queueBuffer 不保证 GPU 同时开始或已经结束。

两个计数器需要按采集版本解释。以 Android 15 BLASTBufferQueue 为例：

  • QueuedBuffer：由 App 进程的 BLASTBufferQueue 输出，公式为 mNumFrameAvailable + mNumAcquired - mPendingRelease.size()。它包含尚待取得和已取得的 buffer 状态，并扣掉待释放项，不是单纯 BufferQueue 队列长度，也不表示 GPU 已完成。
  • BufferTX：SurfaceFlinger 侧的待处理 buffer 事务计数。Android 15 Layer 使用 mPendingBufferTransactions，轨道名为 BufferTX - 加 Layer 名；不是所有版本都叫 mPendingBuffers。

典型路径如下，但两个计数器不能逐跳配对成同一帧：

  1. App 提交 buffer，BLAST 的 onFrameAvailable() 更新计数，再按同步/队列状态取得 buffer 并组织 transaction；acquire fence 可能尚未完成。
  2. SurfaceFlinger 收到含有效 buffer 的事务时增加相应待处理计数；latch 或 drop 路径会减少计数。减少不等于已经呈现。
  3. 不再需要的 buffer 经 release callback/fence 返回。BLAST 可能暂留部分待释放 buffer，回调到达和计数下降均不保证已经可以立即重写；还要满足 release fence。显示一个静态画面很久，本身不是自动释放条件。

下图把 App 帧 54161669 与 SurfaceFlinger 帧关联起来。App Actual Timeline 结束表示应用工作（含 GPU）及提交的完成边界，不是最终上屏；SF Actual Timeline 才延伸到呈现。红字“超过 50 ms”不能解释成 SF 连续计算了 50 ms、主线程阻塞了 50 ms，也不能拿顶部 23.58 ms 的另一选择范围直接替代。缺少原 trace 时不重算该样例的精确端到端延迟。

选中帧后，应核对 token、Layer、关联 DisplayFrame、Present Type 和 Prediction Type。浅绿色也可能表示高延迟状态，不能只凭颜色判断响应及时。参见 FrameTimeline 官方说明及第 1 篇。

支撑 120Hz 的系统架构优化

设备要持续在高刷新模式下运行，需要同时控制帧耗时与功耗。显示模式选择是其中一环。

自适应刷新率技术

需要区分面板能力、传统显示模式切换与 Android 的 ARR：面板标注 LTPO，并不保证设备支持特定帧率范围或 AOSP ARR。

AOSP 从 Android 15 引入 ARR，依赖面板、内核、系统及 composer3 v3 接口。它可在同一显示模式内调整刷新节奏；TE/Vsync 与实际刷新率可以不同，例如官方示例使用 240 Hz 时序、最高 120 Hz 刷新。应用侧文档进一步注明 Android 15 QPR1 及以上、具备对应 HAL 的设备条件。因此不能只按 Android 版本号或“120 Hz/LTPO”规格推断支持。

120Hz 的优势与挑战

120Hz 带来的体验提升

我拿到第一台 120 Hz 手机时，最直观的感受来自这些场景：

  1. 滑动更连贯：桌面滑动、应用切换，还有刷微博和朋友圈，都让我明显感觉更流畅。但要把这种体感归因到刷新率，需要在同设备上控制应用帧率和显示模式再比较。

  2. 游戏有更密的反馈机会：我当时玩《王者荣耀》和《和平精英》，感觉操作也更容易控制。游戏稳定产帧且显示模式允许时，新的画面可以更频繁呈现。「提前 8 ms 看到画面」不是固定收益，输入、渲染和显示延迟都要实测。

  3. 阅读体感因人而异：我长时间滑动内容时觉得高刷新模式更舒服；这里是个人感受，没有做盲测，也不能当成视觉健康结论。

  4. 触控与显示分开看：触控采样率和屏幕刷新率是两项规格。高刷可能缩短等待下一次呈现的时间，但不能据此推断触控采样也提高了。

120Hz 面临的实际问题

当然，高刷屏幕也带来了一系列技术挑战：

  1. 功耗：高刷新模式可能增加显示和渲染功耗。没有固定设备、亮度、应用、时长和测量方法，就不能给出统一的耗电百分比。

  2. 帧节奏更紧：若应用目标是稳定 120 FPS，帧间隔约 8.33 ms。App 的具体截止时点应结合设备调度和 FrameTimeline 预测检查；不能把全部系统工作都算进一段 8.33 ms 的串行预算。

  3. 温度：游戏持续高帧率可能让 CPU、GPU 和显示模块工作更久，随后触发降频。要区分刷新率与游戏负载的影响，需要同机同场景测试。

  4. 应用目标帧率：120 Hz 屏幕上运行 60 FPS 应用不一定是适配失败；视频、静态内容或省电模式可能有意选择较低帧率。

思考与展望

按需调整：从 ProMotion 看刷新率的智能管理

我们真的需要在所有场景下都保持 120 Hz 吗？静态页面和快速滑动对刷新率的需求不同。苹果的 ProMotion 开发文档提供了按内容选择动画帧率的示例：

  1. 高影响力动画：全屏转场等可请求 CAFrameRateRange(minimum:80, maximum:120, preferred:120)，谨慎使用高帧率。
  2. 透明度、颜色过渡及小幅移动：使用 CAFrameRateRange.default。
  3. 低速小动画：表中列出 8–15、15–24、30–48 的范围示例，preferred 为 0，并非保证硬件支持区间内每个整数频率。
  4. 其他情况：使用默认范围。

这是 iOS 15 起帧率范围 API 的使用建议，不是系统对所有动画的固定规则，也不是 Android 配置。请求值不保证被采用；iPhone 自定义动画要请求超过 60 Hz，还需按文档配置 CADisableMinimumFrameDurationOnPhone。降低动画更新频率可能减少渲染工作，但显示侧是否省电还要看硬件和实际刷新策略，不能从表中推导固定收益。

电量与体验的权衡

从 120 Hz 切到 60 Hz 可能省电，幅度取决于设备、亮度、内容和应用实际产帧率。没有同条件测试，不能给出统一的「节省 10–15% 电量」结论。

高刷新率的价值主要出现在滑动、动画和其他需要快速反馈的场景。静态内容可以让系统选择较低模式，前提是切换过程没有引入可见抖动。

开发者的适配策略

对自己管理的 Surface，按内容帧率提供提示并控制产帧节奏。普通 View 动画沿用系统帧调度；本例适用于应用自己管理的 Surface，ARR 设备条件见前文。

复测至少记录显示模式/实际刷新节奏、App 产帧及呈现间隔、输入到反馈的延迟和功耗条件。只报“设备支持 120 Hz”无法说明交互有没有改善。

结论

2025 年写这篇时，我觉得 120 Hz 是手机交互体验的一次明显改善。我当时的判断是，120 Hz 可能会常用很久，后续更需要下功夫的是按场景调节刷新率。这是对发展方向的个人判断，不是所有设备的统一标准。

120 Hz 提供更密的显示更新机会，也让稳定产帧更难。Perfetto 里先看设备当时的刷新模式，再对照 App 与 SurfaceFlinger 的 Expected/Actual Timeline，区分 App 晚完成、合成晚呈现和正常的低帧率内容。功耗结论则需要同设备、同亮度、同场景的独立测量。
