3. Post

When we call DecorView’s Post method, it will ultimately call View’s Post method because DecorView ultimately inherits from View:

For the ordinary newly created Activity path here, decor has not yet been added to the window during onCreate(), so this View’s mAttachInfo is null. Do not infer the same state for every View from a lifecycle callback name: an already attached View posts directly to its associated Handler.

What do the Activity callbacks actually do? When writing an app, it can feel as though everything happens in onCreate. onStart? onResume? We may barely touch them. But the framework still has work to do there.

PhoneWindow was created earlier in Activity.attach(). Decor and content Views can be created during onCreate(), but construction is not window attachment, layout, or presentation. In this old ActivityThread’s ordinary visible-start path, handleResumeActivity() calls the resume logic and then adds decor through WindowManager. Creating ViewRootImpl and a hardware renderer also depends on window and acceleration conditions; onResume() itself is not a completion guarantee.

performTraversals() measures, lays out, and draws as required by state. Every frame need not perform all three, and RenderThread-driven animation frames need not rerun UI traversal. The old RunQueue forwarding occurs here:

The executeActions we discussed in the previous section is executed within performTraversals:

The mHandler here is a ViewRootHandler object:

ViewRootHandler extends Handler without explicitly supplying a Looper in this tag. A default Handler binds to the creating thread’s Looper, not automatically to mainLooper. This ordinary Activity path creates ViewRootImpl on the main thread, so it uses the main Looper. A thread without a Looper would cause that constructor to throw.

On this old UI-thread/first-attachment path, the next performTraversals() forwards the outer Runnable to the main queue. It can run only after the current call stack returns. That explains the first post, but not yet why the second post sometimes lands after another traversal.

5. UpdateText

A reader asked in the comments on Part 1: why post again inside run() instead of calling updateText directly? We need to follow the sequence a little further to answer that.

Part 1 observed updateText after a later traversal when using two posts. Old source contains conditions that explain such ordering, but “EGL initialization always causes two traversals” is too broad.

In android-5.1.1_r1, acquiring a valid Surface during relayout when there was none sets newSurface = true. The source explains that drawing is deferred and another traversal scheduled so WindowManager can learn about the windows to display; hardware-renderer initialization also occurs in that branch. Pre-draw cancellation, visibility, skipDraw, and other state still affect drawing. Two is not a universal startup count.

Synchronization barriers are the other condition. scheduleTraversals() inserts a barrier when arranging traversal:

doTraversal() removes its barrier before entering performTraversals():

When the queue head is a barrier with a null target, MessageQueue looks for an asynchronous message instead of dispatching ordinary synchronous messages behind it. Choreographer marks its VSYNC message asynchronous, so it can pass. Asynchronous messages can still run on the same main thread; this does not mean background execution.

For one source-supported ordering consistent with the observation, label the outer task A and the updateText task C:

  1. The first traversal forwards pending A to the main queue.
  2. That traversal schedules another traversal because of newSurface or related conditions and inserts barrier B. A is already before B.
  3. A runs and posts C through an ordinary Handler. C lands behind B and cannot yet be dispatched.
  4. An asynchronous frame message runs. The next doTraversal() removes B and performs traversal.
  5. C can run after that main-thread call stack returns. GPU, SurfaceFlinger, and display work may still be in progress.

This requires the relevant implementation, an unattached-View posting path, the A/B/C ordering, a synchronous Handler, and a subsequent traversal actually being scheduled. The original image lacks complete queue logs, so it does not prove this arrangement for every launch. An attached View, asynchronous Handler, or other scheduling state changes the outcome. Apps should not use internal barrier APIs to manufacture a post-first-frame callback.

7. 2026 Update

  • Android 16 / android-16.0.0_r1: DecorView is now the separate com.android.internal.policy.DecorView class. An unattached View keeps actions in its own HandlerActionQueue, forwarding them during dispatchAttachedToWindow. The old ThreadLocal RunQueue reasoning does not transfer unchanged. Handler.createAsync, available from API 28, bypasses synchronization barriers; it is not a background executor for startup delays.
  • Android 12 / API 31 onward: The system SplashScreen adds new API boundaries to the old starting-window/theme-preview discussion. Follow the official migration guidance and the appropriate windowSplashScreenBackground, postSplashScreenTheme, and related attributes. Changing old windowBackground alone is not the whole configuration, and a separate SplashActivity can produce duplicate splash screens. Keeping a splash visible does not reduce initialization time.
  • Tools: Android Device Monitor was deprecated in Android Studio 3.1 and removed in 3.2. Use Layout Inspector for hierarchy inspection, Perfetto/System Trace for system timing, and the current Profiler for method analysis. The original screenshots are historical, not current tool UI. Instrumented method tracing and debug logging add overhead and should not be treated as an unperturbed startup benchmark.
  • Choose the right condition: Use layout callbacks for dimensions; even API 29 frame-commit callbacks do not guarantee visible pixels. See Part 1 for examples. Validate initial display, full usability, and subsequent frames instead of substituting traversal counts or Runnable completion for presentation evidence.
