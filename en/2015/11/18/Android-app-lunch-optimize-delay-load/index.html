To make an Android app start faster, the main idea is to do less during startup. In practice, we usually reach for:

  1. Asynchronous Loading
  2. Delayed Loading (DelayLoad)
  3. Lazy Loading

If you have worked on startup optimization, you have probably used these already. Here I want to look at one DelayLoad implementation and why it behaves as it does. The code is simple, but following it takes us through Looper, Handler, MessageQueue, and VSYNC. I’ll also discuss the problems I ran into and some thoughts along the way.

Version note (reviewed 2026-10-13): This is a historical 2015 experiment; its screenshots and three approaches are retained. Neither “two posts guarantee execution after the first frame is visible” nor “startup always needs two performTraversals calls” is a valid API guarantee. The discussion checks AOSP Android 6.0 and 16 queue behavior and adds layout callbacks, Android 10 / API 29 frame-commit callbacks, and current measurement guidance. The screenshots establish only the observed ordering in those samples, not universal presentation timing.

1. Implementation of Optimized DelayLoad

A common DelayLoad approach is Handler.postDelayed in onCreate. It sets an earliest eligible execution time, not a signal that the interface is ready. Queue contention, a busy main thread, and deep sleep can delay it further. The first question is therefore: how long should it wait?

The same fixed delay can behave differently across devices and startup states; fast hardware alone does not guarantee a particular initialization time.

To compare the three approaches, I wrote a small app with three differently sized images and a TextView under each to show its dimensions. getWidth() / getHeight() report View layout dimensions in pixels, not the intrinsic dimensions of a Drawable or Bitmap. Keep three questions separate:

  1. When is updateText executed?
  2. Have the ImageViews been laid out, and do the values reflect that layout?
  3. Has work left the initial-display critical path, and does it delay later usability?

Here the task still ran before the first traversal and could lengthen the initial-display path. There is no universal requirement for two traversals before the first frame. Traversal count depends on window state and other conditions, and finishing CPU drawing is not proof of GPU completion or presentation.

3. Reflections

The code is small, but understanding the observed order requires looking at Handler/MessageQueue/Looper, View attachment, and ViewRootImpl traversal scheduling. The next part follows those details. A successful delay in one capture is not a stable first-frame callback.

5. 2026 Update: Choose the Condition You Need

For layout dimensions, use a layout callback. This Kotlin helper uses AndroidX Core’s doOnLayout (available since 1.1.0). Call it on the UI thread for each bound ImageView/TextView pair. If layout is already complete with no pending layout request, it runs immediately; otherwise it runs once after the next layout and removes its listener. It does not wait for presentation and should not contain expensive initialization.

For pre-draw or frame submission, distinguish the signals. OnPreDrawListener runs before drawing. Android 10 / API 29 registerFrameCommitCallback reports rendered content submitted to the swap chain and only works with hardware rendering; the frame may still not be visible. Register before the target frame and remove unfired callbacks as required by the lifecycle. It is not an exact presentation-complete notification.

For deferring nonessential work, first identify dependencies. Keep only short UI-required work on the main thread. Handler posts and IdleHandler do not create background work; queue idleness does not mean the first frame is visible. Run CPU/IO work on an appropriate executor and manage cancellation. Primary-content loading still contributes to the user’s wait. AndroidX App Startup manages initialization dependencies and entry points, not post-frame scheduling. For manual lazy initialization, remove its automatic initialization configuration and check that another initializer does not initialize it early as a dependency.

The third approach is not a contract: in AOSP android-6.0.0_r1, an unattached View posts into ViewRootImpl.getRunQueue(), forwarded to a Handler during traversal. In android-16.0.0_r1, each View has its own queue, forwarded during attachment. Attached Views post directly to their associated Handler in both versions. Posting again creates another queued task; it does not wait for the GPU or display.

Measure initial display separately from full usability. Macrobenchmark StartupTimingMetric (since 1.1.0) exposes timeToInitialDisplayMs and timeToFullDisplayMs, the latter based on the fully-drawn signal. It ends when the frame containing or following that signal finishes rendering. This metric may be unavailable before API 29; a missing value is not zero. Report fully drawn when primary content has rendered and meets the product’s usable-state definition, not unconditionally in onCreate. Compare repeated cold/warm/hot starts with device, build, data, and compilation state held constant, and inspect subsequent frames. Moving work past the first frame alone does not establish a successful optimization.

Baseline Profiles guide ART precompilation; Startup Profiles improve DEX layout at build time. Neither schedules tasks. DEX layout optimization is available from AGP 8.1 and enabled by default from AGP 8.3, with the required configuration, R8, and generated profiles. No fixed speedup is promised. Android 12 / API 31 onward also supports correlating app, GPU, and display work through Perfetto FrameTimeline.
