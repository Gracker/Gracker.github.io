技术复核 · 2026-10-13。 本文保留 2019 年四种启动模式的操作记录，按 AOSP android-9.0.0_r1、android-16.0.0_r1 核对任务选择、affinity 与最近任务行为，并补充 Android 12（API 31）的 singleInstancePerTask。旧记录未注明设备完整版本，本次没有真机重跑，不能当作当前系统的逐步实测。

Android 中的 Activity 有几种重要的启动模式：standard、singleTop、singleTask、singleInstance。网上讲这些模式的文章不少，我这里写了个 Demo，想从任务中的 Activity 排列给大家看它们的区别；较新的 singleInstancePerTask 放在后面补充。

普通任务内导航通常后进先出。下方 A -> B 表示操作顺序；“栈内容”按顶部在前列出实际排列。留意每一步之后的变化，边操作边对照会好理解一些。重复发起启动不一定增加实例。Task 是系统管理的任务，不等于进程，也不等于最近任务列表中的一张卡片。

Demo 我也放到了 GitHub：AndroidLunchModeTest。本次核对的快照为 eaa1f987e332e0f85187a911ad9ae01cd20fff05。工程 compile/target SDK 29、min SDK 26；源码包名为 com.example.lunchmodetest，与下方保留的旧日志 com.example.launchmodetest 不同。

运行前需要按每个案例核对所有跳转目标：快照中 MainActivity.startSingleTopActivity 实际跳到 SingleTaskActivity，StandardActivity 默认跳到 SingleInstanceWithAffinityActivity，仅改一个目标无法自动跑完全部案例。类名 WithAffinity 表示旧命名，实际 manifest 配置为空 affinity；SingleTopWithAffinityActivity 甚至未声明 singleTop，不能凭类名判断模式。本次只核查代码，没有改动或编译这个示例工程。

下面先按同一用户、普通前台 Activity 发起、无额外 Intent flags 的条件解释。若把旧工程升级到 target SDK 31+，还需为带 intent-filter 的组件显式配置 android:exported，其中 Launcher 入口设为 true。

Standard 标准模式

最基本的模式。在本文“从 Activity 发起、没有额外改变复用语义的 Intent flags”的条件下，每次启动会创建新实例。Manifest 中的 standard 不能脱离 flags 单独解释所有结果。

SingleTop 栈顶复用模式

如果目标任务的栈顶已经是要启动的 Activity 实例，则复用并投递 onNewIntent()；位于同一任务但不在顶部，仍会新建。这里的“顶部”是所选 Task 的顶部，不是整个设备只有一个栈顶。

测试2 ： SingleTopActivity 在栈顶

SingleTask 栈内复用模式

  1. 系统会按启动条件寻找可复用的任务；范围不只是调用者当前的 Task。未找到合适任务时再创建新 Task。
  2. 找到任务后，如果其中已有目标实例，复用它并投递新 Intent，清除它上方的 Activity；如果没有目标实例，可能在选中的同 affinity 任务里加入新实例。
  3. 原例中未声明 taskAffinity 的 Activity 继承应用默认 affinity，因此可能落入已有任务。这不是“未写 affinity 就永远留在当前 Task”，也不能说 singleTask 无条件永远在任务根部。

Android 9 的 ActivityStarter.getReusableIntentActivity 与 ActivityStack.findTaskLocked 会结合组件、用户、文档 Intent 和 rootAffinity 查找。Android 16 的 ActivityStarter 仍区分任务选择、清栈和实例复用。

测试2：SingleTask（WithAffinity）

示例中的 SingleTaskWithAffinity 实际设置的是 android:taskAffinity=""，即无 affinity，类名容易造成误解。空值不能通过共同 affinity 匹配普通任务，所以首次启动、且没有可复用目标任务时会新建 Task；再次启动仍可能通过目标组件匹配复用已有 Task，并非每次新建。

总结

  1. 本例两种配置选中了不同的 Task；Task 不等于 framework 内部的 ActivityStack，不能据此说必定新建 ActivityStack。
  2. 从 SingleTaskWithAffinity 普通启动 StandardActivity 时，后者可以加入该 Task，即使其默认 affinity 不同。
  3. 从另一个 Task 再次启动 SingleTaskWithAffinity，可复用目标任务和实例，并清除目标上方的 Activity。
  4. 是否在最近任务列表显示独立卡片，还受 Recents 管理、排除标记与系统实现影响，不能只由类名或空 affinity 推断。

SingleInstance 单实例模式

singleInstance 的任务只容纳该 Activity；它启动的其他 Activity 必须进入其他 Task。对同一用户下的同一目标组件，系统会查找并复用已有实例；不能把它理解为跨用户、跨工作资料或进程死亡后 Java 对象仍“全局常驻”。

下面日志括号里的“多任务里面有/没有 Task”保留了我当时的界面观察，指的是最近任务卡片，不是 Task 是否存在；也不是 launchMode 的固定保证。

测试1：SingleInstance （Without Affinity）

未显式设置 taskAffinity，使用默认值。下方 StandardActivity 回到 Task 0，是该示例中的任务匹配结果；一般情况也可能选中其他已有任务或新建任务。

总结1

  1. singleInstance 独占一个 Task，但不保证隐藏最近任务卡片。
  2. 复用需要匹配用户和目标组件；已有 Activity 可收到 onNewIntent。配置变化或进程重建仍可能重新创建客户端 Activity 对象。
  3. 从它启动其他 Activity 会走其他任务的选择逻辑，不是“永远回到上一个 Task”。

例如，Android 9 RecentTasks.findRemoveIndexForAddTask 和 Android 16 RecentTasks 对普通任务会比较非空 affinity、基础 Intent 等条件进行条目去重/裁剪。这能解释为何相同 affinity 可能影响卡片，但不能仅凭旧记录确定每次设备界面的具体原因。

测试2： SingleInstance （With Affinity）

此处旧称 “With Affinity” 仍指 android:taskAffinity=""，即无 affinity。原记录出现独立最近任务卡片，只作为当时观察保留；空 affinity 不会取消 singleInstance 的复用规则。

Android 12 起：singleInstancePerTask

Android 12（API 31）新增 singleInstancePerTask。它要求目标 Activity 位于任务根部，同一 Task 只有一个该实例，但该 Task 可以继续容纳其他 Activity。

普通重复启动可以复用已有任务并清除目标上方的 Activity；使用 MULTIPLE_TASK 或 NEW_DOCUMENT 等符合条件的启动方式，可以让同一组件在多个 Task 各有实例。它与 singleInstance 的“任务内只有一个 Activity”不同。具体文档模式与 flags 仍要一起看，不能把单一 flag 当成无条件多开保证。原 2019 Demo 没有实现这个模式。

Intent flags 与 onNewIntent

Manifest 之外，调用方的 flags 也影响行为。下面只列最容易影响本文实验的组合：

启动方式 影响
SINGLE_TOP 目标已在所选 Task 顶部时可复用，不会自动搜索并清掉中间所有页面
NEW_TASK 进入查找/创建任务的路径，不保证每次新建 Task
CLEAR_TOP 找到目标后清除其上方页面；目标为 standard 且没有 SINGLE_TOP 等复用条件时，目标本身也可能被结束后重建
NEW_TASK + CLEAR_TASK 清除所选任务的旧内容，让新 Activity 成为新的根；不是 CLEAR_TOP 的别名

这些分支可对照 Android 16 ActivityStarter 与 Task.clearTopActivities。应用从后台启动还需满足对应版本的启动限制；launchMode 本身不授予后台启动权限。

一些概念

TaskAffinity

taskAffinity 表示 Activity 与任务的亲和关系。它是任务选择或允许 reparenting 时的一个条件，不是“相同 affinity 的 Activity 必定同属一个 Task”。普通 Activity 内的 startActivity 可以把不同 affinity 的 Activity 放进调用者任务；同一应用也可以拥有多个任务。

配置 含义
不写 activity 的 taskAffinity 继承 <application> 的值；应用未指定时默认是包名
android:taskAffinity="" 无 affinity；dump 中通常表示为 null
android:taskAffinity="com.example.launchmodetest.detail" 一个显式非空 affinity，不是 Task ID

NEW_TASK 相关查找及 allowTaskReparenting 会使用 affinity，具体还要结合组件、用户、flags 和任务状态。它不定义权限，也不让不同应用自动共享进程。属性定义见 activity manifest 文档。

ActivityRecord、TaskRecord、ActivityStack 之间的关系

这些名称对应旧 AMS 容器结构，适合阅读本文历史图；不能原样套到所有新版本。

  1. ActivityRecord 是 system_server 侧的一条 Activity 记录。同一个 Activity 类可有多条记录；记录不等于应用进程中某个 Java 对象永久存活。
  2. TaskRecord 管理一个任务中的 ActivityRecord。普通导航通常表现为后进先出，清栈、重排和跨任务启动会改变这个过程。
  3. ActivityStack 管理多个 TaskRecord；ActivityDisplay 管理对应显示上的 stacks，ActivityStackSupervisor 协调它们。显示对象不是全系统永远只有一个，stack 数量也不固定为 Home/App/Recents 三个。
