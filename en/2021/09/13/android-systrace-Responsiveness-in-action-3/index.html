Jank, slow response, and ANRs can share causes or occur together, but they are not three severity levels of the same problem. When a user says an app feels slow, first distinguish uneven animation, a long delay after an action, and a system-detected failure to respond.

Animation and scrolling stutter is usually called jank. Long startup, screen wake-up, or navigation delays are slow response / high latency. An ANR depends on a specific system timeout condition. Frame-drop rate, startup duration, and ANR rate measure different things.

This is the third article in the Responsiveness series, focusing on extended knowledge when using Systrace to analyze app responsiveness, including startup speed testing, log interpretation, state analysis, and third-party startup libraries.

Versions and historical context (reviewed 2026-10-14): The 2021 figures and chapter structure are retained. Traceview is deprecated; the text uses Android Studio CPU Profiler terminology and corrects the sampling unit. Thread/component examples are checked against AOSP Android 10/11, command units against Android 16, and dependency/lazy initialization behavior against App Startup 1.2.0. Figures from different tools are not one experiment; corrected text takes precedence over old state, component, and readiness annotations.

1. Interpretation of the Three Process States in Systrace

These are thread scheduling states, not one state for an entire process. A main thread can wait while a worker runs. Older Systrace viewers commonly show Running in green, Runnable in blue, and Sleep as blank space. Colors depend on the viewer; function-slice colors do not identify scheduling state.

Select the thread-state track and inspect its label and scheduling events. Other states, including uninterruptible waits, also exist. Blank or missing data is not automatically Sleep.

1.1 Analyzing the Sleep State

Sleep means the thread is neither running nor waiting to be scheduled on a CPU. It does not by itself distinguish “active/passive” waiting or establish that the wait is harmless. Common causes include Looper polling, synchronous Binder replies, locks/conditions, and explicit sleeps. nativePollOnce waiting with no due message can be normal, but a missing startup task, delayed message, or synchronization barrier may still need investigation.

The figure contains an IWindowSession.remove Binder call. Correlate its interval with thread-state intervals. Synchronous calls can wait for the remote side; oneway calls have different semantics. Call count alone does not establish a bottleneck: inspect accumulated critical-path waits and remote work.

Select binder transaction to follow request and reply flows:

The selected transaction has a 34.216 ms wall duration, not necessarily 34.216 ms of Sleep or remote CPU work. This figure’s outgoing flow is 29928→1515 and incoming return is 1515→29928. Its bottom annotation mistakenly calls the outgoing flow “incoming.” Verify transaction identity and receiving thread rather than treating any incoming flow as a reply.

Wakeup information helps continue the dependency investigation:

Here, wakeup from tid: 1515 identifies the observed waker, not automatically a lock owner, complete wait object, or root cause. Inspect the preceding stack, remote work, and subsequent scheduling. A method named invokeSuspend also does not mean that its OS thread slept throughout the method slice.

1.2 Analyzing the Running State

Running means the thread is scheduled on a CPU. If an interval grows, compare workload and inputs before examining CPU capacity, frequency, cache/memory behavior, and context switches. A function’s wall interval may include multiple Running and waiting intervals; it is not the same as CPU time.

The selected execution is on CPU 0; the second image shows a 5.112 ms selection. Neither establishes the CPU topology or numeric frequency. It therefore cannot prove “the wrong little core” or insufficient frequency. Foreground UI/RenderThread work is not guaranteed to stay on big cores: scheduling also depends on energy, thermal limits, affinity, and available capacity.

1.3 Analyzing the Runnable State

A sleeping thread becomes eligible to run when woken, then executes when scheduled. A preempted Running thread can return to Runnable as well. Runnable does not guarantee immediate execution, and very short intervals may be hard to see at the current zoom level.

This older figure primarily illustrates Java thread states, not the Linux scheduler state machine. Java Thread.State RUNNABLE can include waiting for CPU time; RUNNING and READY are not separate enum constants. VM BLOCKED is also different from a kernel uninterruptible wait. A waiter notified by Object.notify must reacquire the monitor; notification does not mean it immediately enters Running.

For long Runnable intervals, examine allowed CPUs, priority, cpuset/affinity, competing work, and available capacity. System-wide saturation is one possible cause. Restricted placement or higher-priority work on eligible CPUs can also delay a thread while other CPUs are idle.

2. Using TraceView for Responsiveness Analysis

The historical heading says TraceView, but the screenshot is Android Studio CPU Profiler. Standalone Traceview is deprecated; for Android Studio 3.2 and later, the official guide recommends CPU Profiler. Distinguish method sampling/instrumentation, system tracing, and the viewer used to inspect them.

2.1 Capturing TraceView During Startup

This is an ART Java/Kotlin method-sampling diagnostic, not a general native-stack capture or end-to-end startup benchmark. Check the device’s am start --help, target debugging permissions, and writable output path first. --sampling is in microseconds: 1000 microseconds equals 1 ms. The original --sampling 1 did not mean one sample per millisecond. See the AOSP Android 16 command help.

-S stops the target package to avoid reusing its process; it does not clear file caches/app data or reproduce the Launcher touch path. Resolve launch failures, permission errors, or Activity reuse before interpreting results. An empty trace is not a fast startup. Stop after the agreed scenario completes, rather than assuming ten seconds means fully loaded. Import steps and format compatibility depend on your Studio version.

2.2 Interpreting TraceView

After importing the method trace, confirm process/thread, selected interval, sampling versus instrumentation mode, and timing basis. Green regions in these older figures include bundled third-party libraries, not only the app author’s code. Interpret colors using method names and the viewer’s legend.

In Top Down/Bottom Up views, distinguish inclusive time from self time; do not add parent and child totals twice. Sampling can miss short calls, so its timeline and counts are not a complete invocation log.

2.3 Pros and Cons

Method sampling has statistical error; instrumentation records more method boundaries but can introduce greater runtime overhead. They are different capture modes, not one “TraceView high-frequency sampling” mode. A requested short interval does not guarantee samples arrive at that rate, especially for a one-microsecond request.

Use profiles to find hotspots and call relationships, and compare them with explicit timing definitions, sample counts, and overhead controls. Recheck final startup latency with lower-overhead system tracing/benchmarks; a profiling-perturbed method duration is not automatically the user’s real delay.

4. Locating Other Component Startups in Systrace

4.1 Service Startup

This excerpt is from AOSP android-11.0.0_r1 ActivityThread, with debug logging omitted. It is framework source, not code to paste directly into an app.

The system schedules Service creation/binding through ApplicationThread, which posts work to H on the app main thread. A returned startService call does not mean Service.onCreate has run; system scheduling or process creation may still intervene. MessageQueue considers due times, synchronization barriers, and async status, not just submission order.

These callbacks follow a doFrame in this sample; this is not a guarantee that Services run after the first frame, nor proof that the frame has been physically presented. The image’s “register receiver” annotation also needs correction: broadcastReceiveComp identifies component broadcast delivery, not receiver registration.

4.2 Custom Messages

This is a Handler callback interval with an AndroidX LiveData class in its label. Inspect the Handler/Runnable and nested calls before attributing all such work to custom app logic.

4.3 Service Startup Visualized

The label is LoadedApk$ServiceDispatcher$RunConnection: client-side connection-state dispatch, which can invoke ServiceConnection.onServiceConnected and related callbacks. It is not Service.onCreate itself. See Android 11 LoadedApk; locate creation/binding/argument delivery in the service process as well.

4.4 BroadcastReceiver Execution

broadcastReceiveComp is the execution interval for delivery to a manifest component. Handler message numbers alone are not stable cross-version identifiers.

The next image shows registration called from Activity.onStart. The registration call’s thread and a later onReceive callback’s thread are separate matters. Dynamic receivers normally receive callbacks on the main thread; overloads with a scheduler Handler can change delivery. Registration does not automatically choose its calling thread for future callbacks. Match registration lifetime with unregistration.

4.5 ContentProvider Startup Timing

In the normal Android 11 process-binding path, initial providers for that process are installed after Application creation/attachment and before Application.onCreate. Every Activity launch does not initialize every provider in the APK, and each query does not rerun onCreate. The publishContentProviders marker reports installed providers to the system; that Binder interval is not the total provider initialization cost.

5. Can AppStartup Optimize Startup Speed?

Third-Party Library Initialization

Some libraries quietly initialize themselves even though you never called their initialization method in Application.onCreate. A common way to do that is through a manifest ContentProvider. This depends on process assignment, enabled state, and process binding; it does not mean every provider declared anywhere in the APK is initialized on every launch.

SDK behavior changes across versions. For example, WorkManager uses App Startup from 2.6; instructions for removing its old standalone provider cannot be applied unchanged to newer versions. Inspect current dependencies and the final merged manifest rather than inferring behavior from an SDK name.

This figure summarizes normal process-initialization ordering. Separate automatic initializers can add startup work and obscure dependencies. Developers are not categorically unable to control them: disabling, replacing, or deferring initialization depends on each SDK’s documented contract.

AppStartup Library

App Startup lets participating Initializers share InitializationProvider and declare prerequisites through dependencies(). It does not automatically convert arbitrary SDK providers or promise a fixed global order among unrelated initializers. AppInitializer in 1.2.0 recursively initializes dependencies, caches results, and detects cycles. Automatic initialization normally runs on the main thread; a manual call does not automatically move work to a worker thread.

The original “50+ providers” threshold and “less than 20 ms for 20–30 libraries” lack reproducible device/version/baseline and repeated-sample evidence. They are not general performance limits. Gains depend on critical-path work removed or deferred; merging entry points does not erase SDK initialization work.

To defer an existing Initializer, remove its automatic-discovery metadata within the app manifest’s <application>. Declare xmlns:tools="http://schemas.android.com/tools" on the root manifest element:

Removing this metadata alone does not defer the initializer if another automatic initializer still depends on it. Inspect the dependency graph, then initialize before first use on the thread required by the SDK:

ExampleLoggerInitializer is a placeholder for your existing Initializer implementation; import androidx.startup.AppInitializer. Do not remove metadata without providing initialization, or delete the shared provider merely to defer one component. The app/SDK must still handle asynchronous completion and multiple processes.

Summary

  1. Consolidate participating components under one entry point with explicit dependencies.
  2. Move nonessential initialization off the startup critical path, checking TTID, TTFD, and first-use latency for shifted cost.
  3. Ordering does not automatically reduce work or make it asynchronous; measure repeatedly under matched conditions.

Action Items for App Developers:

  1. Inspect the target build’s merged manifest/final APK for providers, processes, and initializer metadata, not just source-manifest counts.
  2. Record initialization threads, wall/CPU time, and dependencies to identify the critical path.
  3. Check SDK requirements: what can be deferred, who triggers it, and how readiness is guaranteed before use.
  4. Verify cold launch, background entry points, multiple processes, and first use after changes. Keep failed/missing samples distinct and compare matching compilation/data conditions.

6. Using IdleHandler in App Startup Scenarios

IdleHandler runs on the Looper thread owning its MessageQueue. In AOSP Android 10 MessageQueue.next, idle handlers can run when the queue is empty or its head message is not yet due. All future messages need not have completed. An already-due synchronization barrier also affects this condition.

The original “all messages completed” annotation is too strong. Network work, background tasks, GPU work, or the next draw may remain unfinished while the main queue is momentarily idle. A continuously busy queue can also postpone an idle handler indefinitely.

  1. Defer short, nonessential work. Registering a main-queue IdleHandler in Activity.onCreate does not guarantee execution after the first frame or on a background thread. A long callback delays subsequent input/frame work. Returning false from queueIdle removes it; true retains it for future idle opportunities, not a separate loop or guaranteed timer. Remove handlers that are no longer needed when their owner’s lifecycle ends.

  1. Report full display from a business readiness condition. Activity.reportFullyDrawn() is available from API 19 to report critical content/usability; IdleHandler is not required. The old example below waits for a data-loaded signal and then one idle opportunity. Neither data arrival nor an idle queue proves the list and images have appeared.

The Android M (API 23) guard relates to using Looper.getQueue(), not the introduction of reportFullyDrawn. Define readiness for success, empty data, and error states, and avoid duplicate registration, destroyed Activities, or stale request callbacks reporting readiness. AndroidX readiness-reporting helpers still need the same explicit business conditions.

The overview image’s onWindowFocusChange should be onWindowFocusChanged. Focus does not establish initial display or content readiness, and am start -W does not measure the same event as the focus callback. Accounting across Splash→Main depends on the actual launch sequence and OS implementation. Retain separate initial/full-display definitions using the official TTID/TTFD guide.

This historical output shows SplashActivity Displayed +968 ms, MainActivity Displayed +475 ms, and Fully drawn +3s221ms; am start -W reports TotalTime 968 and WaitTime 975. These fields have different boundaries and Activity associations. Do not add/subtract them to derive a stage, or assume +3s221ms begins with physical contact on the Launcher icon. The screenshot command also sleeps five seconds before reading an existing logcat buffer, which can include older records. Correlate logs by time, package/Activity, and the specific launch.

Correct TTFD reporting complements TTID; it does not make TTID an incorrect measurement. Missing reports, data failures, and incomplete captures are distinct outcomes, not zeros.
