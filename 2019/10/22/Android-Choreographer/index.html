本文介绍了 App 开发者不经常接触到但是在 Android Framework 渲染链路中非常重要的一个类 Choreographer。包括 Choreographer 的引入背景、Choreographer 的简介、部分源码解析、Choreographer 与 MessageQueue、Choreographer 和 APM，以及手机厂商基于 Choreographer 的一些优化思路

Choreographer 让动画、部分输入处理和 View 更新围绕显示时序协调执行。它在有待处理工作时请求帧回调，而不是每个物理刷新周期都无条件唤醒 App。2019 年常见的 60Hz 屏幕刷新间隔约为 16.67ms；90Hz、120Hz 分别约为 11.11ms、8.33ms，现代设备还可能动态切换刷新率。回调及时不等于画面已经呈现，后续还涉及 RenderThread、GPU 和合成显示链路。了解这套流程，也有助于理解 Message、Handler、Looper、MessageQueue、Measure、Layout 和 Draw。

主线程运行机制的本质

这篇文章对应后续的 Perfetto 5：Android App 基于 Choreographer 的渲染流程。Android 主线程通过 Looper 分发 Message；不是 MessageQueue 自己执行应用代码。等待下一条消息时，native poll 也可能处理文件描述符事件，VSync 接收正与此有关，所以“主线程所有操作都是 Message”只是过度简化。

在 Perfetto 中，把问题帧与主线程、RenderThread、GPU 和 SurfaceFlinger 对齐。Android 12 / API 31 及以上，且采集包含对应数据时，可利用 FrameTimeline 的 expected/actual 轨道定位超期；缺轨道不等于零掉帧。线程 Sleep、Runnable 和 Running 要分别调查，不能把 slice 墙钟时长直接当 CPU 时间。下图展示的是一个有间隔的历史分发过程，MethodTrace 插桩也会影响时间。

稳定的呈现节奏很重要，但“稳定 50fps 一定比 40–60fps 波动更流畅”不能一概而论。在固定 60Hz 显示上，50fps 本身也无法逐帧按整数刷新间隔均匀呈现。VSync 协调与缓冲机制能改善 pacing，并不保证稳定帧率或消除工作量。

引入 Choreographer

Choreographer 请求下一次适用的 VSync 事件，由绑定 Looper 的线程调度回调。它不负责自行改变屏幕刷新率，App 的 VSync 回调也不是直接运行在硬件中断上下文。没有待处理工作时，普通 View 窗口不需要持续产生新帧。

这张原示意图需要按简化图阅读：RenderThread 是 CPU 线程，图中把它的工作框整体写成“GPU”不准确；获取 Buffer、提交 GPU 命令、入队和合成并非图上每格都严格串行。16.6ms 只是当时 60Hz 的近似刷新间隔，不代表任意一帧的所有阶段都在这一段内完成，也不是端到端输入延迟。高刷背景可参考90Hz 漫谈。

Choreographer 简介

Choreographer 接收有时限的帧回调，按阶段执行到期工作，并请求下一次需要的显示事件。Android 10 的顺序是 INPUT → ANIMATION → INSETS_ANIMATION → TRAVERSAL → COMMIT；这不是把 App 的所有 Message 都收进来，也不意味着每帧必做完整 measure/layout/draw。

Choreographer、SurfaceFlinger 和缓冲机制共同参与帧调度，但不能保证 App 固定达到 20、60 或 90fps。监控中还要区分公开 FrameCallback、隐藏的 FrameInfo、Looper 消息计时与最终呈现数据。IdleHandler 在消息队列满足空闲条件时运行，不是“每帧结束”的固定通知。

另外虽然画图是一个比较好的解释流程的好路子，但是我个人不是很喜欢画图，因为平时 Systrace 和 MethodTrace 用的比较多，Systrace 是按从左到右展示整个系统的运行情况的一个工具(包括 cpu、SurfaceFlinger、SystemServer、App 等关键进程)，使用 Systrace 和 MethodTrace 也可以很方便地展示关键流程。当你对系统代码比较熟悉的时候，看 Systrace 就可以和手机运行的实际情况对应起来。所以下面的文章除了一些网图之外，其他的我会多以 Systrace 来展示。

Choreographer 的工作流程

  1. 初始化线程内 Choreographer，绑定 Looper/FrameHandler，创建显示事件接收器与回调队列。
  2. 有到期工作且尚未安排帧时，请求 VSync；事件到达后，onVsync 将一个异步 Runnable 放入同一 Looper 的队列，之后 run() 执行 doFrame()。
  3. doFrame 核对帧是否仍需要执行，计算开始处理相对帧时间的延迟，必要时校正动画帧时间。
  4. 依次执行到期的 INPUT、ANIMATION、INSETS_ANIMATION、TRAVERSAL、COMMIT 回调。Traversal 中可能把绘制状态同步给 RenderThread。
  5. RenderThread 提交 GPU 工作与 Buffer；提交返回不表示 GPU 已完成。相关 fence 描述工作完成/使用约束，SurfaceFlinger/HWC 后续才能按依赖安排合成和显示。
  6. 动画等仍有后续工作时再次安排帧；并非无条件永久循环。

上图的旧标注把 Traversal 写作第三项，省略了 Insets Animation；Android 10 源码中它是第四类。图中“渲染完成抛 Buffer”也应按上述异步 GPU/fence 边界理解。

计算掉帧逻辑

这里计算的是 startNanos - frameTimeNanos：当前 doFrame 开始处理时，距离所携带的帧时间过去了多久。整数除以该版本的帧间隔，得到错过的调度间隔数；它不是这帧绘制耗时，也不是完整的实际呈现掉帧数。源码还会调整用于动画的 frameTimeNanos，并处理时间倒退等情况。

图中 start_time 应理解为事件携带的帧时间戳，不是 Java 收到回调那一刻的系统时间；分母也不能固定为 16ms。

前一段长工作可能拖延下一次回调，但“这只是在算前一帧掉帧”并不准确。GPU、合成或呈现超期可能没有对应的这条警告，主线程处理延迟也可能来自 Runnable 调度等待，而不全是业务代码在 CPU 上忙。图中最后一处 start_time - end_time 还写反了，源码计算方向为开始处理时间减帧时间戳。

源码小结

  1. getInstance() 取得当前 Looper 线程的 Choreographer，不是整个进程唯一一个；无 Looper 时会抛异常。显示事件和 doFrame 都在绑定线程上处理。
  2. VSync 请求走显示连接，事件经 FD/Looper 分发，再以异步 Message 执行 doFrame；不是在 App 中处理显示硬件中断。
  3. FrameCallback 单次有效，不能当成自动常驻订阅。FrameCallback 位于 ANIMATION 阶段，执行一次不保证生成新 Buffer。
  4. Android 10/16 都按 INPUT、ANIMATION、INSETS_ANIMATION、TRAVERSAL、COMMIT 顺序处理到期队列；前面阶段的状态变化可以影响后面的 traversal。
  5. COMMIT 在 traversal 后执行，不是 GPU/SurfaceFlinger 完成或实际呈现通知。ActivityThread.scheduleTrimMemory()会在有主线程 Choreographer 时把内存整理安排到这一阶段，但这只是用途之一，也不是每帧都会调用 onTrimMemory。
  6. ListView 的 obtain/setup 可能由输入滚动或动画继续滚动触发，也可能出现在布局路径。应根据实际栈区分，不能只按阶段名猜调用原因。

APM 与 Choreographer

不同入口观测的是不同阶段，不能把所有数字都叫“FPS”或“掉帧数”：

  • FrameCallback：观察所在 Looper 的帧回调节奏，不是 Buffer/呈现计数。
  • dumpsys gfxinfo ... framestats：查看对应窗口的 HWUI 帧统计；按该设备输出的字段解释。
  • SurfaceFlinger --latency：旧版的帧时间统计，需匹配真实 layer 和系统实现。
  • PageFlip 私有事务：仅保留为历史说明，Android 16 的旧查询已不可用。
  • Choreographer skip warning：开始处理的延迟提示，非完整呈现判据。
  • Looper/BlockCanary：消息分发耗时，非帧显示耗时。

现代入口中，Android 7 / API 24 提供 Window.OnFrameMetricsAvailableListener；回调通知也可能丢失，dropCountSinceLastInvocation 不是画面掉帧数。Android 12 / API 31 起，在有数据的设备/采集中可用 Perfetto FrameTimeline关联 expected/actual 和应用/SF 帧，继续定位 CPU、GPU 或合成延迟。

  1. A：desiredPresentTime，期望呈现时间。

它们不是“App 开始画”“提交硬件前 VSync”“硬件接受完”的三个时刻。该版 ring buffer 大小为 128，而每个 tracker 的 dump 循环输出 127 个槽位；零值、未就绪的 INT64_MAX 等不是有效帧。只统计目标、时间范围和有效记录，先验证单调性、缺失和刷新率变化，不能假设每次命令得到 128 个新帧。

原文的 ceil((C - A) / refresh_period) 及“相邻值变化就是掉帧”不构成通用判据：期望、就绪和实际呈现是不同阶段，稳定的长延迟甚至可能让该值保持不变。应根据该版本的数据定义分析实际呈现间隔/预期 deadline；支持时优先关联 FrameTimeline，不能沿用公式自动认定 jank。

Choreographer 自身的掉帧计算逻辑

Android 10 的 SKIPPED_FRAME_WARNING_LIMIT 默认是 30，由启动时读取的 debug.choreographer.skipwarning 属性配置。它控制日志阈值，并不意味着少于 30 个错过间隔就不卡，也不是每帧完整测量。

要区分帧时间、doFrame 实际开始、工作完成与最终呈现；改变告警阈值不会修复这些阶段的延迟。

MessageQueue 与 Choreographer

在 Android 10 的 MessageQueue.next()里，当队首是 target == null 的同步屏障时，会向后查找异步消息，并仍检查它是否到达 when。屏障后的同步消息需等屏障移除；这不是抢占正在执行的消息，也不会提高线程的 CPU 调度优先级。

Message.setAsynchronous()从 API 22 起公开，原文“隐藏方法”的说法已过期；Handler.createAsync()从 API 28 起公开。异步表示可以越过同步屏障，不表示自动放到队首、另开线程或必定立即执行。没有屏障时，它仍受队列时间和顺序约束；框架的 post/removeSyncBarrier 本身不是普通 App 应依赖的公开 SDK。

厂商优化

系统厂商由于可以直接修改源码，也利用这方面的便利，做一些功能和优化，不过由于保密的问题，代码就不直接放上来了，我可以大概说一下思路，感兴趣的可以私下讨论

移动事件优化

原文“Choreographer 本身没有 input”的说法需要区分：AOSP 已有 CALLBACK_INPUT 和批量输入消费；厂商可能尝试的是改变输入调度或更早响应的策略。本文没有公开对应代码和实验，不能将其当成 AOSP 标准能力。提前处理要同时评估事件合并、重采样、功耗和后续帧的呈现节奏，并非越早越好。

后台动画优化

应用不可见后，自己不断续订的 FrameCallback 或动画可能仍制造工作；是否需要停止，应结合窗口可见性、生命周期、多窗口和具体业务。不能把所有后台回调都判为无意义，也不能仅凭未被杀就推断它能无限制运行。

这张图展示历史 com.netease.newsreader.activity 的密集帧活动。这是我当时记录的后台场景，截图本身没有独立可见性/功耗证据，也不能据此评价当前应用。应用侧先取消不再需要的动画和回调；系统策略还需验证可见窗口、功能正确性与调度限制。

帧绘制优化

“不等 VSync 就立即合成”是原文分享的厂商探索方向，不是普通 App 的公开开关。合成排期仍需满足 Buffer/fence、显示硬件和刷新约束；立即调度不保证降低端到端延迟，也可能增加功耗或破坏 pacing。没有提供实现与对照数据，因此不写成已验证优化。

应用启动优化

启动时应先找关键路径上的长工作、锁和排队。系统内部改变消息顺序要维护生命周期和依赖关系；任意把所谓重要消息放到队首会造成顺序错误或饥饿，不是通用提速方法。普通应用优先减少启动关键路径工作、延后非必要初始化，并核对实际首帧与可交互时间。

高帧率优化

60/90/120Hz 的刷新间隔分别约为 16.67/11.11/8.33ms，原文的 120Hz“8.8ms”不准确。刷新间隔也不是每个线程独占的完整预算。高刷策略需一起评估应用与游戏负载、帧率切换、温度、功耗和呈现节奏，而不能只要求所有 App 永远跑满刷新率。
