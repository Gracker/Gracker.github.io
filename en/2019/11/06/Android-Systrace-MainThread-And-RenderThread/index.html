This is the ninth article in the Systrace series, primarily introducing the MainThread and RenderThread in Android Apps—commonly known as the Main Thread and Rendering Thread. This article examines their workflows from the perspective of Systrace and covers related topics: jank, software rendering, and dropped frame calculation.

The purpose of this series is to view the overall operation of the Android system from a different perspective using Systrace, while also providing an alternative angle for learning the Framework. Perhaps you’ve read many articles about the Framework but can never remember the code, or you’re unclear about the execution flow. Maybe from Systrace’s graphical perspective, you can gain a deeper understanding.

Main Content

Version note — reviewed October 13, 2026: The original article and captures date from 2019; their exact device builds and Flutter SDK versions were not recorded. The View and process-entry explanations below use AOSP android-9.0.0_r1 / android-10.0.0_r1, with HWUI synchronization checked against android-16.0.0_r1. The old Flutter thread and Skia diagrams no longer describe all versions; that section includes the Flutter 3.27 and 3.29 changes.

The same topic continues in Choreographer Rendering in Perfetto and MainThread and RenderThread. The old captures show the relative positions of the UI thread, RenderThread, and SurfaceFlinger; the newer approach follows thread scheduling, FrameTimeline, and Buffer flow.

Start with the target frame rate, display refresh rate, and deadlines, then follow dependencies through the main thread, RenderThread, GPU, and presentation. Input, Animation, Insets Animation, Traversal, and Commit are separate doFrame phases; each need not have work on every frame. Scheduling, Binder, locks, and Buffer waits can also delay a frame.

Here is one hardware-accelerated View frame during list scrolling. Focus on the UI Thread and RenderThread rows. This is a concrete example, not a mandatory path for every View frame, game, or software-rendered window.

Read this capture in the following order:

  1. The main thread is waiting because it has no runnable work. Input and other events can also wake it; it does not wait exclusively for Vsync.
  2. After a frame has been requested, a Vsync event reaches FrameDisplayEventReceiver.onVsync. It posts an asynchronous message to its Looper, which later runs run() / doFrame(); receiving Vsync does not itself complete drawing.
  3. Due Input callbacks run. Not all input delivery goes through this batching phase.
  4. Due Animation callbacks run. Android 10/16 also have Insets Animation before Traversal, which this image does not separately show.
  5. Traversal performs Measure, Layout, and Draw as needed. Updating View drawing records can synchronize with RenderThread. Commit follows later in doFrame; this partial image does not establish whether it has callbacks.
  6. The main thread waits inside the synchronization call until RenderThread releases it. It can then overlap with later rendering when conditions permit. IdleHandler execution depends on queue-idle conditions, not merely on a frame ending.
  7. In this GL/EGL capture, RenderThread obtains a Buffer and submits rendering work. queueBuffer passes a Buffer and its associated fence; it does not prove GPU completion or display. SurfaceFlinger still handles the layer according to scheduling, readiness, and composition policy.

The old annotation about a “finished” Buffer is shorthand. Modern HWUI can use different graphics backends, and Android 16 View Surface paths also involve BLASTBufferQueue. CPU submission, GPU completion, composition, and presentation remain distinct stages.

For the Choreographer portion, see Android’s Choreographer Rendering Mechanism. This article focuses on thread creation and responsibilities, followed by games and Flutter.

Creation of the Main Thread

An ordinary Android App process is derived from Zygote through a path involving fork. A process and a thread are different objects: the initial execution thread in the child continues runtime initialization and enters the App entrypoint. The forked process is not itself a Java Thread object.

ActivityThread does not extend Thread. It manages framework transactions on the App’s main thread. ActivityThread.main() prepares the main Looper and creates ActivityThread and its Handler H. Other Handlers and native Looper callbacks also run there; H does not own every App message.

Creation of ActivityThread

In the ordinary App branch of Android 10 ZygoteConnection, the path is ZygoteInit.zygoteInit() → RuntimeInit.applicationInit() → findStaticMain(), followed by android.app.ActivityThread.main(). The original childZygoteInit() excerpt belongs to the child-Zygote branch, not ordinary App startup.

Creation and Evolution of the Render Thread

HWUI introduced RenderThread in Android 5.0 (API 21) to move part of rendering work off the main thread. View GPU hardware acceleration already existed in Android 3.0 (API 11), however; pre-Lollipop does not mean CPU-only rendering.

Software Rendering

View hardware acceleration is enabled by default for targetSdkVersion >= 14, with configuration at several levels whose capabilities differ. This attribute fragment in <application> disables the application default; an Activity can override it:

Software View drawing rasterizes on the CPU and submits through the window Surface. That window need not use the usual HWUI RenderThread path, but other windows or embedded components may still use HWUI in the same process. A software layer on one View also does not disable acceleration for the entire window. To identify the current drawing Canvas, use Canvas.isHardwareAccelerated(). See the hardware acceleration controls.

This old capture shows lockAsync, drawing, and Buffer submission on the main thread. Its selected 21.064 ms interval also contains a fence wait; the entire wall duration is not CPU rasterization time. Two different captures cannot quantify a universal slowdown from disabling acceleration. Extra main-thread work or waiting does reduce time available for other messages.

Hardware-Accelerated Rendering

The Draw phase records or reuses DisplayLists and synchronizes with RenderThread. Recording, including View.onDraw(), still costs main-thread time. RenderThread can continue after the main thread is released, but that release is conditional, as described below.

Rendering Thread Initialization

Distinguish creating the thread from initializing a window Surface. Android 9 constructs a native RenderProxy from ThreadedRenderer, and that proxy obtains RenderThread::getInstance(). RenderThread can therefore exist before the first Draw. The initializeIfNeeded() call in ViewRootImpl concerns renderer / Surface initialization; it is not the unique point where the native thread is born.

In Android 9 DrawFrameTask.cpp, postAndWait() posts to RenderThread and waits on a condition variable. syncFrameState() determines whether the UI thread may be released early. Otherwise, release occurs after later drawing or fence waiting. Android 16 retains this conditional structure. A long main-thread synchronization interval calls for inspecting what RenderThread is doing or waiting for.

dequeueBuffer, flush commands, and eglSwapBuffersWithDamageKHR label this GL/EGL path. They are not universal backend markers, and their end times do not directly identify GPU completion or presentation.

Division of Labor: Main Thread vs. Render Thread

For a typical hardware-accelerated View pipeline, the main thread handles messages, input, common animations, layout, and drawing-record updates. RenderThread synchronizes the RenderNode tree and drives backend rendering. Both are CPU threads; neither thread’s wall duration is itself GPU time. Window or SurfaceControl operations can also involve the main thread in system graphics interactions, so “the main thread never interacts with SurfaceFlinger” is too broad.

A DisplayList records drawing operations. RenderNode also carries properties such as transforms; the two are not interchangeable concepts. This division provides several benefits:

  1. Unchanged content can reuse drawing records without repeating the View recording work.
  2. Node properties such as translation and scale can reuse content when applicable; content changes may still require recording again.
  3. The backend can optimize while preserving ordering, clipping, and blending semantics. It cannot necessarily draw all text in one batch.
  4. RenderThread can handle rendering and supported animations, while business logic and ordinary View updates still need the main thread.
  5. When synchronization permits, the two threads can overlap. The main thread is not guaranteed never to wait for RenderThread.

The original RenderThread reference remains historical reading; use the tagged AOSP sources above for specific branches.

Main Thread and Render Thread in Games

Game engines often submit Buffers through their own Surface and rendering pipeline instead of the View HWUI path. The Android main thread still handles lifecycle, windows, input, and some plugin calls. Game logic, rendering submission, and worker tasks are divided according to the engine and its configuration.

Main Thread and Render Thread in Flutter

This 2019 Flutter capture has separate .ui and .gpu threads alongside Android’s platform thread. The .gpu thread performs raster work on the CPU; it is not the hardware GPU. Flutter content follows its Engine pipeline rather than ordinary View HWUI drawing. This is not simply a consequence of using Skia—Android HWUI also uses Skia. An App embedding native Views can still have an HWUI RenderThread.

The thread diagram is outdated: Flutter 3.29 merges UI and platform threads by default on Android and iOS, running Dart UI work on the platform thread. Raster work remains a separate responsibility; the whole engine has not become single-threaded. Do not require a distinct old-style .ui track when reading a new capture. Slow platform-thread plugin calls can now delay Dart UI work on that same thread. See the Flutter architecture overview.

Flutter still uses Android for windows, input, and frame scheduling. The class in the old method capture is VsyncWaiter, not the original text’s VsyncView. Flutter 3.29.3 VsyncWaiter.java also uses Choreographer.postFrameCallback(); its callback forwards timing through flutterJNI.onVsync().

Shipping the rendering engine with the App permits SDK updates independently of Android OS updates. It does not automatically give every App the newest Skia or prove that a screen is faster than its native counterpart. This presentation slide explains the Skia architecture of its time, not a workload-specific benchmark.

The backend changed too: Flutter 3.27 made Impeller the default on Android API 29+. The official documentation describes fallback to the legacy OpenGL renderer on older Android versions or devices without Vulkan support. “Flutter always uses Skia → OpenGL” is therefore no longer an adequate model. Record the Flutter version, Android version, and actual backend. See Impeller.

The Framework / Engine division remains useful: the Dart framework builds and lays out the UI and records drawing work; the Engine rasterizes and submits the scene. The Engine box containing only Skia below is historical, not a complete diagram for newer versions.

When UI updates are needed, the framework requests a frame. Platform timing drives animation, build, layout, and paint work, then the scene reaches the raster pipeline. Not every Layer necessarily becomes a new texture. GPU submission still precedes Android Buffer, fence, and composition handling rather than directly displaying pixels.

This last diagram is also historical. “GPU Thread” means a raster CPU thread, and the top “GPU → Vsync” arrow should not be read as Flutter waiting directly for GPU completion to begin a frame. The bottom already says GL or Vulkan, not OpenGL alone. Account for both merged threads and Impeller when applying it to newer versions.

Performance

Slow queries, computation, or synchronous waits on the main thread delay input and drawing. Separate two kinds of failure:

  1. Jank: Refresh intervals at 60 / 90 / 120 Hz are about 16.67 / 11.11 / 8.33 ms, but lateness depends on the target frame rate and actual deadlines. Main-thread and RenderThread work includes synchronization and overlap; adding their wall durations is not a dropped-frame test. GPU work or system composition may also delay presentation. On Android 12 (API 31) and later, Perfetto FrameTimeline can compare expected and actual timing when the relevant data was captured.
  2. ANR: Input, broadcasts, Services, and other cases have their own timeout rules. An arbitrary message taking a few seconds does not always produce a dialog, and dialog display depends on context and policy. Inspect the ANR type, logs, and blocking dependencies; see Diagnose and fix ANRs.

Both harm the user experience and need continuing attention. ANR stacks help, but a late capture may miss the original blockage. Intermittent jank needs system Trace analysis and, where useful, method sampling. Instrumented tools such as TraceView perturb timing, so their durations are not automatically representative of an uninstrumented run. Understanding the two threads and their dependencies is a central motivation for this series.
