Android资源优化

1. Bitmap优化

Bitmap 可能是图片密集型应用的主要内存来源，但不能据此断言所有 Android 内存问题都来自 Bitmap。先测量存活对象、缓存和分配来源，再决定优化重点。

Bitmap 的像素位置有版本差异，不能在所有 HPROF 中都期待找到一块对应的 byte[]：

Android 版本 像素存储的典型位置
Android 2.3.x 及更早（API 10 及以下） native 内存，Java 堆中的 Bitmap 是包装对象。
3.0 / API 11 至 7.1 / API 25 随 Bitmap 存在于托管堆中。
8.0 / API 26 及以上 native 堆；只看 Java 包装对象不能代表像素总占用。

依据 Managing Bitmap Memory。具体位图类型、图形分配和厂商实现仍应结合实际工具输出分析。对象还没被回收，也不一定就是泄漏：有界缓存、正在显示或处理的图像都有合理的持有期。

1.1 主动释放Bitmap资源

不要把 recycle() 当作每张图片都必须执行的清理步骤。 旧指南特别针对 API 10 及以下给出主动回收建议；现代代码先处理解码尺寸、缓存容量和所有权。

当前 Bitmap.recycle() 文档 将它描述为立即释放像素数据，适用于确定不再使用的图像，例如独占的变换中间缓冲区；同时明确警告不要随意回收已交给 View 或可能被其他地方引用的 Bitmap。Java 包装对象本身仍由 GC 管理。旧文引用的 mBuffer、nativeRecycle() 片段属于旧实现，不能拿来解释所有版本。

isRecycled() == false 只说明还没被标记为已回收，不能证明没有其他使用方，也不能消除线程竞争。清掉自己持有的引用、解除显示关系和取消加载任务，是不同操作；在方法里把形参赋成 null，也不会清掉调用方的字段。使用图片加载库时，应遵守该库的目标清理和 Bitmap 池所有权，不要绕过它手动 recycle。

1.4 用合适的NinePatch替代大背景图

NinePatch 本身也是 PNG，应用资源文件的扩展名是 **.9.png**，不是 .9.webp。它通过边缘标记指定拉伸区和内容区，适合气泡、边框等可以局部拉伸的背景；并不是所有照片都适合，也不保证选错拉伸区域后仍然不变形。

用较小的源图覆盖多种尺寸，可能省去多张大背景图，但最终开销仍受源图尺寸、解码和使用方式影响。Android Studio 的 Draw 9-patch 工具 可以编辑标记并预览不同尺寸。

1.5 使用大图之前，先按目标尺寸解码

这里需要区分“压小文件”和“减少解码像素”。把 JPEG 质量调低，通常只是让压缩文件变小；宽高和像素格式不变时，解码后仍可能占用相近的像素内存。先解码完整大图再缩放，也已经产生了大图的峰值分配。

只显示缩略图时，应在解码前确定所需尺寸；若支持放大或编辑，则把这些需求也算进去。使用 BitmapFactory 时，可以分两步处理：

  1. 设 inJustDecodeBounds = true 读取宽高和类型，不分配完整像素。检查 outWidth、outHeight 是否有效，不能把失败结果继续当成尺寸。
  2. 按目标像素大小计算 inSampleSize，再关闭 bounds 模式进行实际解码。资源 density 缩放等因素可能继续影响输出尺寸，应检查实际结果。

Android 9（API 28）起还可使用 ImageDecoder.setTargetSize() 指定输出尺寸，并按需求维护宽高比例。已有加载库则优先传入正确的目标尺寸，让它统一处理解码、缓存和取消。

解码和大图处理应避免阻塞 UI 线程。当前官方说明：Loading Large Bitmaps Efficiently。

3 构造Adapter时，没有使用缓存的convertView

5 在Activity的生命周期中释放资源

释放时机应与获取时机和用途成对：只在可见期需要的监听可在 onStart() 获取、onStop() 释放；只在交互期需要的工作可以跟随 onResume() / onPause()。API 24 起的多窗口场景中，onPause 后的页面仍可能可见，不宜只按“暂停就是看不见”处理。

onDestroy() 不是系统终止进程前保证调用的清理钩子。需要持久化的用户状态不能只等它保存，也不要在生命周期回调中做大量同步 IO。跨配置变化保留的数据与某一代 Activity/View 的引用要分开管理。参考 Activity 生命周期 与 进程生命周期。

6 消除过度绘制

过度绘制是同一帧中一个像素被绘制多次。文字叠在背景上可以是正常需要；应减少的是没有视觉作用的重复背景和覆盖层，而不是一律删除背景。

多余绘制可能增加 GPU 工作和内存带宽需求，但 View 层次深并不必然等于每层都在覆盖同一区域，移除一次绘制也不保证按比例释放 Bitmap 或降低进程堆占用。结合裁剪、透明度、实际帧耗时与 GPU 证据判断收益。

可继续阅读本博客的 过度绘制及其优化 和官方 Reduce overdraw。

7 使用Android系统自带的资源

系统公开的字符串、drawable、样式和布局，可以在语义及外观适合时复用，减少应用自带的重复资源。但系统版本、主题或设备差异可能影响效果，需要检查目标设备；不要依赖隐藏的内部资源。

8 使用内存相关工具检测

很难一次就把内存管理做好，所以每个开发阶段都要检查进入退出页面、滚动、图片加载和前后台切换。关注对象是否超出预期生命周期，而不是只看某一时刻内存是不是偏高。

Android Studio 的 堆转储 可以帮助查看 Java/Kotlin 对象和引用链；MAT 可继续分析兼容的 HPROF，native 和图形内存还需相应工具。Lint 提供静态线索，不能单独证明“没有泄漏”。

对于 Bitmap 问题，可以结合本博客的 MAT 中还原 Bitmap 中的版本限制；只有 native 地址的堆转储不能凭空还原像素。所有修复都应回到原来的操作路径复查分配、存活和用户体验。
