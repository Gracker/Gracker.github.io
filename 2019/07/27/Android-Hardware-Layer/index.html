硬件加速与软件加速

很多人会把 Android 中的硬件加速和 Hardware Layer 搞混，以为启用了硬件加速，就是启用了 Hardware Layer。所以在说 Hardware Layer 之前，我们先说一下硬件加速。

原文推荐的两篇文章保留为历史阅读：Android 硬件加速原理与实现简介、理解 Android 硬件加速的小白文。API 支持范围以 Android 官方文档 为准。

对 View 绘制来说，软件路径主要由 CPU 栅格化，硬件加速路径由 HWUI 使用 GPU 完成相应绘制；CPU 仍要处理布局、记录绘制命令和提交工作。Skia 也支持 GPU 后端，不能把“用了 Skia”直接等同于软件渲染。

View 硬件加速从 Android 3.0（API 11）引入，对 targetSdkVersion ≥ 14 的应用默认开启；应用、Activity、Window 的配置以及 View 的软件 layer 会影响实际路径。原理和代码可以顺着上面的文章继续看，这里我想换个角度，用当时的 Systrace 带大家看看两种绘制路径的差别。

总结

  1. 硬件加速改变 View 的绘制路径，不会让 CPU 工作消失；是否看到 RenderThread 不能单独作为整个 App 的开关判据。
  2. 软件 View、软件窗口和硬件加速窗口可以共存，App 绘制与系统合成也要分开看。
  3. 硬件加速通常适合现代 View 界面，但收益取决于工作量、资源和设备，不能仅凭两张图断言始终更快。
  4. 不支持的绘制操作要按 Android API 版本检查；必要时对局部 View 使用软件 layer，而不是无条件关闭整个应用的硬件加速。

Software Layer VS Hardware Layer

说完硬件渲染，再看 View 的 Software Layer 和 Hardware Layer。这里的 layer 是 View 的离屏像素缓存，不是 SurfaceFlinger 的合成 layer，也不等于整个窗口的硬件加速开关。

一个 View 的 layerType 有三种状态：

  1. LAYER_TYPE_NONE：不额外建立显式的 View 像素 layer。
  2. LAYER_TYPE_SOFTWARE：将 View 内容用软件路径绘制到 Bitmap；所在窗口开启硬件加速时仍可使用。
  3. LAYER_TYPE_HARDWARE：在硬件加速的 View 层级中使用 GPU 离屏 layer；未开启硬件加速时按软件 layer 处理。

LAYER_TYPE_NONE

这是默认值。它不等于关闭硬件加速，也不等于每次都从零绘制：硬件路径仍可复用 RenderNode/display list 中记录的绘制命令。

Software layer 的作用如下

  1. 软件绘制时，可将 View 及其子 View 作为一组应用透明度、颜色过滤或混合效果。
  2. 硬件绘制时，可承接该版本硬件路径不支持的局部操作；稳定内容也可能通过缓存减少重复绘制。
  3. 内容频繁更新时，要承担软件重绘及硬件路径中的纹理上传成本，不宜把它当作通用动画优化。

LAYER_TYPE_HARDWARE

Hardware Layer 将 View 内容绘制到 GPU 离屏资源，再用于窗口绘制。OpenGL 后端中可以用 FBO 理解它，但不能把所有 Android 版本和 Skia GL/Vulkan 后端都写成同一个 FBO 实现。它仍依赖当前 View 层级的硬件加速状态；关闭时退化为软件 layer。

Hardware layer 的作用：

Hardware Layer 可以给一组内容应用混合效果，也可能减少稳定复杂 View 在 translation、alpha、scale、rotation 动画中的重复绘制。缓存还会影响旋转或 3D 变换时的裁剪与采样，但不保证所有缩放都更清晰或更快。

总结

  1. Software Layer 与 Hardware Layer 是不同的像素缓存路径；按绘制支持范围和实际开销选择。
  2. 对稳定复杂内容的属性动画，Hardware Layer 可能有收益，仍需与默认 NONE 比较。
  3. 动画结束后恢复原类型，避免长期持有不需要的 layer。图形资源可能延后释放或被底层复用，不保证调用后进程内存立即下降。

例如 Android 9 SkiaPipeline::createOrUpdateLayer 会检查 layer 是否存在、尺寸是否变化，允许复用现有资源；内容重绘与资源分配不是同一件事。

Debug 工具

部分历史系统的开发者选项提供“显示硬件层更新（Show hardware layers updates）”。入口和可用性因版本、厂商而异，不一定在“辅助功能”下面。

它标记更新的硬件 layer 区域，不是必然让整个界面变绿。稳定内容的变换动画通常希望初始化后复用；持续高亮说明要检查更新来源，但动态内容需要更新本来就是正常行为。没有高亮也不能单独证明缓存行为或性能。结合 Trace 中的 layer 绘制、尺寸和帧时序一起判断。

总结

  1. 先看内容是否稳定、绘制是否足够复杂，再决定是否给属性动画加 Hardware Layer。
  2. 不要“能加就加”。建立缓存、占用内存、绘制离屏内容再合成到窗口都有成本。
  3. Alpha 是否需要额外离屏工作与重叠内容、渲染路径等有关；不能把所有 setAlpha 或透明度动画都说成必然创建同一种 buffer。
  4. 内容 invalidate 可能导致重绘，但不等于必然重新分配整块资源。频繁变化时，应比较 NONE 与 layer 路径，而不是预设固定优劣。
  5. 临时修改 layerType 后恢复原值；软件 layer 用于有明确兼容需求或收益的局部场景。

统计工具:GFXInfo

当时除了看 Systrace，我还用了 adb shell dumpsys gfxinfo <包名> 记录 HWUI 帧统计。下面是历史输出示意，图片里的旧解释需要按以下规则阅读：

  1. Janky frames 按对应系统的帧间隔/截止时间规则统计，不是跨版本固定的“超过 16 ms”；直方图和 percentile 是分桶统计，99th percentile 不是精确最大值。
  2. High input latency 不是 CPU 负载，也不等于输入回调执行时长。Android 9 JankTracker 中存在三缓冲延后截止时间的分支；它可记录 high input latency 而不记录 missed deadline。各原因计数也不能简单相加当作 janky 总数。
  3. Android 16 JankTracker 同时保留 legacy 与更新的 deadline 统计路径。比较新设备时要保存系统版本、刷新率、统计区间和原始输出；gfxinfo 不覆盖完整输入到屏幕延迟。
  4. 六组旧日志每组只有 29–31 帧，设备、系统与采集重置条件记录不足。案例一和六连直方图都完全相同，不能当作已确认的独立测量。本次未在设备重跑，也未补造数据。

总结

六个案例保留了“内容稳定时缓存可能有用、内容变化时缓存需要更新”的观察方向，但不足以支持原来的固定性能排序。样本很小，案例一与六数据重复，动态文本还改变了工作量。

  1. 稳定且绘制复杂的 View，可比较临时 Hardware Layer 与 NONE 的帧时序、内存和 GPU 开销。
  2. 动态内容场景，先查为何失效、尺寸是否变化，再看 layer 的额外离屏成本，不预设 NONE 或某一种 layer 必胜。
  3. 重复 buildDrawingCache/drawLayer 是调查线索，不是“每帧重新分配”的证据，也不能单凭它归因系统或厂商。
  4. 新设备要固定版本、刷新率、初始状态和重复次数。Android 12（API 31）起还可结合 Perfetto FrameTimeline 观察 expected/actual frame；需要采到对应数据，缺失不代表没有卡顿。

现代实现可继续对照 Android 16 View、RenderNode、SkiaPipeline 与 ViewPropertyAnimator；源码标签用于说明实现边界，不代表本次在 Android 16 设备复现了旧实验。
