ANR(Application Not Responding)，应用程序无响应，简单一个定义，却涵盖了很多 Android 系统的设计思想

首先，ANR 属于应用程序的范畴。这不同于 SNR(System Not Respoding)，SNR 反映的问题是系统进程(system_server)失去了响应能力，而 ANR 明确将问题圈定在应用程序。SNR 由 Watchdog 机制保证，具体可以查阅 Watchdog 机制以及问题分析; ANR 由消息处理机制保证，Android 在系统层实现了一套精密的机制来发现 ANR，核心原理是消息调度和超时处理

其次，ANR 机制主体实现在系统层。所有与 ANR 相关的消息，都会经过系统进程(system_server)调度，然后派发到应用进程完成对消息的实际处理，同时，系统进程设计了不同的超时限制来跟踪消息的处理。 一旦应用程序处理消息不当，超时限制就起作用了，它收集一些系统状态，譬如 CPU/IO 使用情况、进程函数调用栈，并且报告用户有进程无响应了(ANR 对话框，部分 Rom 不显示 ANR 对话框，而是直接闪退到主界面)

然后，ANR 问题本质是一个性能问题。ANR 机制实际上对应用程序主线程的限制，要求主线程在限定的时间内处理完一些最常见的操作(启动服务、处理广播、处理输入)， 如果处理超时，则认为主线程已经失去了响应其他操作的能力。主线程中的耗时操作，譬如密集 CPU 运算、大量 IO、复杂界面布局等，都会降低应用程序的响应能力

最后，部分 ANR 问题是很难分析的。有时候由于系统底层的一些影响，导致消息调度失败，出现问题的场景又难以复现。 这类 ANR 问题往往需要花费大量的时间去了解系统的一些行为，超出了 ANR 机制本身的范畴。有一些 ANR 问题很难调查清楚，因为整个系统不稳定的因素很多，例如 Linux Kernel 本身的 Bug 引起的内存碎片过多、硬件损坏等。这类比较底层的原因引起的 ANR 问题往往无从查起，并且这根本不是应用程序的问题，浪费了应用开发人员很多时间，如果你从事过整个系统的开发和维护工作的话会深有体会。所以我不能保证了解了本章的所有内容后能够解决一切 ANR 问题，如果出现了很疑难的 ANR 问题，我建议最好去和做 Framework、驱动和内核的朋友聊聊，或者，如果问题只是个十万分之一的偶然现象，不影响程序的正常运行，我倒是建议不去理它

ANR 分析套路

先按 ANR 类型整理证据：线上看 Android Vitals 或自研监控中的 Input dispatch、Service、Broadcast、JobScheduler 等类型、设备版本和影响范围；本地及时抓 bugreport、EventLog、main/system log。/data/anr/anr_* 的直接读取受设备权限限制，不能假定普通量产机可 adb pull。怀疑调度、Binder、锁、I/O 或渲染时，要让 Perfetto/System Trace 覆盖超时之前的时间段。

Android 11（API 30）起可查 ApplicationExitInfo，但它是历史退出记录：时间戳是进程退出时间，ANR trace 可能已被覆盖；应用从 ANR 恢复后因其他原因退出，也可能带着此前的 trace。不要把它当作所有 ANR 的实时清单，详见系列第一篇。

分析时分别检查应用逻辑与系统依赖，再追踪两者之间的等待关系。系统压力可能放大应用原有的同步等待，不能只凭某个进程 CPU 高就决定归属。

ANR 问题一般的分析步骤如下：

拿到一份 ANR trace，先问一句：这是“第一案发现场”吗？日志、CPU 采样和线程 dump 未必停在同一时刻，时间没对上，后面很容易越查越偏。

  1. 先按包名、PID、用户、设备启动周期和 am_anr reason 对齐事件，防止拿错 trace。区分业务开始、超时检测、CPU 采样、线程 dump 和日志写出的时间；am_anr 不保证是故障开始时刻，dump 也可能晚于阻塞现场。
  2. 搜索 ANR in，记录责任进程、原因、CPU 采样起止时间、各进程/线程占用、Load、PSI 和缺页计数。日志打印者可能是 system_server，不要与责任进程混淆。
  3. 把超时前后相关的启动、解锁、进程变化、慢消息、锁竞争和 Binder 信息放到同一时间线上。可以先把关键行提取到一个文件里，用 VS Code 或 Notepad++ 搜索线索：是重启后第一次解锁，还是短时间内多个应用启动？沿关键线程的等待继续找持锁者、Binder 服务端、调度或 I/O；检查证据是否覆盖整个超时窗口。
  4. 证据不足时保留未知，在可复现环境补业务日志和 trace。新增采集也会有开销，不要用事后单张堆栈补写未观察到的过程。

区分是应用的问题还是系统的问题

首先应该分析是否是应用的问题

分析应用的问题的关键是需要理清当时用户的操作是什么，应用在用户这个操作的过程中扮演了什么角色，然后再进行进一步的分析

  1. 分析应用是否关键组件中的生命周期中有耗时操作，可能平时没有暴露出来，一旦系统负载上来，就会暴露问题（建议在关键生命周期函数中加上对应的 Log，方便 Debug）。
  2. 分析是否出现极端情况，导致应用的逻辑耗时，比如大量的数据处理或者导入，同时运行线程过多等（看应用的 cpu \ io 使用情况）。
  3. 分析是否存在死锁。
  4. 分析是否是在等待 binder 返回。
  5. 分析 Trace 文件中 MainThread 和 RenderThread 是否存在异常。
  6. 分析 Trace 文件中 MainThread 跟 WorkerThread 是否存在等待关系。

分析系统的状态

  1. 检查 CPU 使用率、Load 和调度等待，定位 system_server、Audio、SurfaceFlinger 等相关进程。HeapTaskDaemon 是应用 ART 的 GC 相关线程，不是独立系统服务。
  2. 检查 I/O 延迟和 /proc/pressure/io；minor/major 是缺页计数，不是内存访问次数或 I/O 吞吐量，具体见下文。
  3. 将 dumpsys meminfo、内存 PSI、回收/换页、kswapd 和杀进程记录对齐。旧设备可能用内核 lowmemorykiller，现代 Android 常用用户态 lmkd，还要区分内核 OOM。
  4. 怀疑冻结时检查设备的 freezer 状态和解冻日志。D 表示不可中断等待，不能单独证明冻结；旧内核的 __refrigerator 栈是 freezer 线索，仍需确认触发者和时间。xxxHansManager 是厂商线索，不是 AOSP 通用标签。
  5. 怀疑系统服务异常时，跟进 Binder 服务端与持锁线程的栈及调度。高负载只能提示调查方向，必须说明它如何阻塞本次超时操作。

继续分析：应用可以解决还是系统可以解决

  1. 等待链落在系统或其他进程时，提交对应版本、时间线、栈和 trace，让负责该依赖的团队继续定位，不能把“转系统”等同于无解。
  2. 应用侧仍需评估能否移出主线程、减少持锁范围或避免同步等待；能规避不等于根因就在应用。
  3. 只有证据能连接超时操作与具体阻塞原因时再归因。缺少系统权限或现场数据，就说明尚未定位。

CPU 使用率分析

搜索 ANR in 后，先读 CPU 采样区间，不能统一称为“ANR 前”。下面是 2020 年旧日志及解释性注释，later 区间可能包含检测之后的诊断工作；两个区间的百分比不能直接相加。缺页注释已按 Linux 定义纠正，原统计数值保留。

按 Android 15 ProcessCpuTracker，进程/线程的用户态和内核态 CPU 时间以采样 uptime 时长为分母。多线程并行时，进程出现 191% 或 290% 并不矛盾；TOTAL 则按聚合 CPU 时间计算，分母不同。faults 是采样间的增量。应把这些统计与关键线程调度对齐，不能仅靠进程总量归因。

CPU 负载

Load 是约 1、5、15 分钟尺度的平均活跃任务数，包含可运行任务和不可中断等待任务；不是 CPU 利用率。CPU 刚空闲时历史平均值仍可能很高。0.7、1、5 都不能作为手机通用的告警线，需要结合在线核心、调度限制和 I/O 等待判断。大小核的能力、频率和热限制不同，八核不能简单理解为单核能力乘八。Linux loadavg 定义

/sys/devices/system/cpu/cpu%d/cpufreq/stats/time_in_state（若内核提供）记录各频率驻留时间，不是核心忙碌时间，也不是应用 CPU 时间；统计从驱动初始化或重置开始。上游文档的 usertime 单位为 10 ms，厂商扩展须核对实现。参考 CPUFreq Stats。上面的独立摘录为 1.871，前一完整日志为 1.87，这里保留原摘录精度，不据此计算新结论。

Memory 负载

这是 /proc/pressure/memory 的 PSI 输出；已把旧文转录的 somavg10 修为 some avg10，数值未改。avg10/60/300 是对应时间尺度的平滑压力百分比；total 是累计停滞时间，单位为微秒（µs），不是毫秒。

some 表示至少有任务因该资源停滞，full 表示所有非 idle 任务同时因该资源停滞。这里度量的是资源压力，不能把百分比直接读成 CPU 使用率。Linux PSI 文档

IO 负载

  1. Minor fault：处理时不需要从存储加载页面的缺页，例如页面已在内存、但需要建立映射。它不是 CPU cache miss，也不是每次内存访问都会发生。
  2. Major fault：需要从存储加载页面的缺页。它不覆盖所有 I/O，例如普通文件读写未必产生进程 major fault。

因此 118172 minor / 2 major 是采样窗口的缺页增量，不能换算成 I/O 次数或带宽。大量 major 是进一步检查缺页延迟、I/O PSI 和关键线程等待的线索，不能单独证明本次 ANR 由存储造成。Linux /proc/pid/stat 定义

进程负载

23% user 与 6.4% kernel 分别是用户态和内核态占用。总计显示 30% 涉及格式化精度，不应要求已舍入的各项相加后逐位相等。分母和多核解释见前面的 CPU 使用情况。

CPU 异常进程

以下是排查方向，不是凭进程名即可成立的原因：

  1. system_server 高占用：找具体线程，以及本次业务等待的服务/锁。
  2. kswapd 活跃：核对内存回收、换页和关键线程是否被拖慢。
  3. logd 高占用：检查日志量和实际写日志耗时，不能推断所有进程都同步阻塞在日志输出。
  4. vold 高占用：沿存储操作和 Binder 依赖找等待。
  5. 应用自身高占用：分清主线程、工作线程，以及调度竞争；应用低 CPU 也可能因锁或 Binder 等待而 ANR。
  6. 应用线程为 D：继续读阻塞栈；冻结判断见前文，不能仅凭 D 状态归因功耗策略。
  7. CPU 行前 +/-：表示采样跟踪中的新增/移除状态，不是精确的进程创建/死亡时间戳。结合进程生命周期日志确认。

日志写出线程是 TID 14216，记录的持锁者是 InputDispatcher (17039)。141ms 是锁等待耗时，不是持锁者的 CPU 时间；waiters=0 是记录点的计数，不能解释为从未有人等待。上面保留旧版格式化代码，字段应按相同 ART 版本核对；Android 15 Monitor 在竞争结束后记录等待信息。

Binder Thread

这表示该进程的 libbinder 线程池出现饱和线索，31 是此处配置值，不是所有进程的通用上限。Android 15 IPCThreadState 在执行线程数达到上限时开始计时，降到上限以下后，若超过 100 ms 则打印。它不表示所有 Binder 通信都停止，也不能单独证明死锁；继续查看池内线程的锁、同步调用与耗时。

am_kill

这是旧的五字段样例：用户 0、PID 18555、进程名、OomAdj 945、原因 remove task；已去掉旧文末尾多出的转录字符 1。Android 15 EventLogTags 还增加了 RSS 字段，解析器须匹配版本。以下五张图是旧实现的 kill 路径/原因索引，保留作历史查阅，不是当前版本所有杀进程路径的完整清单。

其他杀进程

由框架相应 kill 路径产生的 am_kill 与所有进程死亡不是一回事。Process.killProcess(pid)、shell 发信号或 LMK/lmkd 的行为未必经过该路径，但仍可能有其他日志；发信号受 UID、权限和 SELinux 等限制，不能杀任意 PID。

缺少 am_kill 也可能是日志覆盖或采集不全。要结合死亡、退出和内核记录，不能从“没这条日志”反推出一定由某种方式杀死。

am_proc_died

按 Android 15 EventLogTags，字段是用户、PID、进程名、OomAdj、ProcState。这里的 935/19 不是死亡原因；该事件表示系统观察到进程死亡，还要关联 am_kill、crash、lmkd 或退出记录。

am_anr

字段依次是用户、PID、进程名、ApplicationInfo flags 和 reason。本例用户 0、PID 8769、com.android.updater，reason 指向 BOOT_COMPLETED 广播。952680005 不是超时时长；Intent 的 flg=0x9000010 与前面的应用 flags 也不是同一字段，且未设置 0x10000000（FLAG_RECEIVER_FOREGROUND）。应按实际版本、广播标志及接收路径判断超时规则，不凭十六进制看起来大就套短期限。日志时间是事件记录时间，不等于广播开始时间。

Lowmemorykiller

这是旧设备的内核 lowmemorykiller 格式，不代表现代 lmkd 总会在 kernel log 打印。首行列出进程名、PID 15545、UID 10136、标作 oom_adj 的 995 和预计回收量 105068 kB。995 不能按旧 Linux oom_adj 的 -17～15 范围解码；需核对厂商实现是否使用 oom_score_adj 量纲。

第二行没有 PID，不能仅靠相邻两行就认定同一受害进程，或把 606 无条件解释为 min_adj。日志中的预计/报告回收量也不保证等于系统最终净释放的物理内存。现代低内存调查可参考 AOSP lmkd。

Blocked msg

这是内部/厂商增补日志，旧文的 1.5 s 是该采集实现的慢消息门槛，不是 AOSP 通用 ANR 超时。cost=32436 ms 是消息处理耗时，不等于 CPU 时间；Current msg List 是当时待处理队列，不是已经执行完的消息列表。when 的负数表示相对预定执行时间的差值，不能直接当每条消息的 CPU 耗时。what=110/114/121 等编号需按对应版本 ActivityThread.H 查义。

灭屏 Log

关键是 power_screen_broadcast_done、screen_toggled 和 power_screen_state

以上是旧日志序列。power_screen_broadcast_done 的三项是 on、广播耗时（ms）、wakelockCount；611 是广播流程耗时，不是屏幕面板熄灭延迟。power_screen_broadcast_send: 1 的 1 是 wakelockCount，不是亮屏标志。Android 15 Notifier

亮屏 Log

关键是 power_screen_broadcast_done、screen_toggled 和 power_screen_state

其中
power_screen_state

  1. offOrOn|1|5
  2. becauseOfUser|1|5
  3. totalTouchDownTime|2|3
  4. touchCycles|1|1
  5. latency|1|3

同理，633 ms 是亮屏广播耗时，不是从按键到屏幕可见的总延迟。上面的 |1|5 等是 EventLog 字段类型/单位元数据，不是日志中的实际数值。厂商 power_screen_state 的 reason/latency 还要核对写入点，不能把该旧序列视为每台设备必有的日志。

解锁完整 Log

wm_set_keyguard_shown 的值

  1. (keyguardShowing|1) ：Keyguard 是否在显示
  2. (aodShowing|1) ：aodShowing 是否在显示
  3. (keyguardGoingAway|1) ：Keyguard 消失
  4. (Reason|3) ：原因

这是旧四字段格式。Android 15 的 wm_set_keyguard_shown 已包含 DisplayId、keyguardShowing、aodShowing、keyguardGoingAway、occluded、Reason 六项，不能按旧位置解析。setKeyguardShown 是调用原因，不证明桌面已呈现或可交互；还要对齐窗口、绘制和输入证据。WindowManager EventLogTags

通知栏下拉完整 Log

sysui_multi_action 的数字是版本相关的 Metrics 编码，应查对应定义。notification_visibility 的顺序为 key、visible、lifespan、freshness、exposure、rank；这些时长字段不是事故的绝对时间戳。visible=1 提示通知可见，不能单独还原一次完整手势。

这里 notification_visibility 的 visible 变为 0。日志开关和版本会影响可见内容；没有这几行不能证明用户没展开/收起通知栏。
