前言

本篇文章是自己的一个学习笔记，记录了 Android 5.0 中 hwui 中的 RenderThread 的简单工作流程。由于是学习笔记，所以其中一些细节不会太详细，我只是将大概的流程走一遍，将其工作流标注出来，下次遇到问题的时候就可以知道去哪里查。

下图是我用 Systrace 抓取的应用启动时 RenderThread 第一次 Draw 的历史 Trace。它能帮助观察线程内的执行顺序，但 DrawFrame 区间结束不等于画面已显示：还需要核对 GPU 完成、缓冲区消费、合成和显示的时点。启动期间可能先看到 StartingWindow，它的退出也不能仅凭这段 CPU Trace 判断。

版本说明（2026-10-13 核查）：本文保留 Android 5.0 的历史流程，源码以 AOSP android-5.0.0_r1 为基准。原截图含设备侧插桩，事件名称不必与 AOSP 完全相同；下方补全了原稿的省略片段，并统一到此标签。旧 OpenGLRenderer、DisplayListRenderer 和 EGL 细节已过时，不能直接套到当前系统；文末补充 Android 16 的对应实现和 Android 12 起的 FrameTimeline。本文讨论 View 硬件加速路径，不涵盖所有自定义 Surface 渲染。

2.4 swapBuffers

CanvasContext::swapBuffers() 经 EglManager::swapBuffers() 调用 eglSwapBuffers(mEglDisplay, surface)，并处理 surface 失效等错误。提交的缓冲区还要由消费者获取，经过 SurfaceFlinger/HWC 合成与显示；swap 返回不等于像素此刻已上屏。缓冲区交接还受同步 fence 约束，不能把提交时刻当成 GPU 完成时刻。

这里主要结束 profiler 的帧统计，不是等待 GPU 或显示完成的同步点。

总结

鉴于我比较懒，而且总结能力不如老罗，下面沿着他的总结顺序回看流程，并按 AOSP 5.0 补上几个边界：

  1. UI 线程记录 View 的绘制状态，提交 DrawFrameTask 后等待。RenderThread 同步 native RenderNode 的 staging 状态并处理纹理、layer 和动画。
  2. 若 info.prepareTextures 允许提前放行，就在绘制分支之前唤醒 UI 线程；否则在绘制分支之后唤醒。该分支也可能跳过绘制。两条路径都不能当成 GPU 完成或最终显示的通知。
  3. 默认 deferred 路径处理需要更新的离屏 layer，并把窗口绘制结果写入从 Surface/BufferQueue 生产端取得的图形缓冲区，再提交给消费者。对于这里的应用窗口，后续由 SurfaceFlinger/HWC 完成合成与显示。

第 2 步给了 UI 线程与 RenderThread 并行工作的机会：RenderThread 处理当前帧时，UI 线程可能已经开始准备下一帧。但两个线程仍有同步和资源依赖，提前唤醒不保证下一帧一定准时。

在 Android 4.x 的这条 View/HWUI 路径中，Display List 记录和回放的 CPU 工作主要在 UI 线程上，尚未拆到本文的 RenderThread。因此 UI 线程需要先走完当前绘制调用再处理后续工作；GPU 和 SurfaceFlinger 当时也可以异步工作，并不是整个图形系统只有 Main Thread。如下图：

2026 年补充：现在如何对应这条链路

  • Android 16 / AOSP android-16.0.0_r1：DrawFrameTask 仍有投递、状态同步、按条件唤醒 UI 线程的过程，但队列接口、帧信息和 Trace 名称已经变化。此标签记录 DrawFrames <vsyncId>，帧信息还包含 deadline、interval 等，不能把 5.0 的函数签名或固定帧预算当成当前合同。
  • 绘制后端：此标签的 CanvasContext 通过 IRenderPipeline 进入 SkiaOpenGLPipeline 或 SkiaVulkanPipeline。选择取决于配置，不能认为所有设备都走 GLES；Vulkan 路径中名为 swapBuffers 的内部方法也不是 eglSwapBuffers。原文的旧 OpenGLRenderer / DeferredDisplayList 分析保留为历史实现。
  • Android 12 / API 31 起：可在 Perfetto 中结合 FrameTimeline 看 Expected/Actual Timeline、jank 类型及应用帧到 SurfaceFlinger 帧的关联。应用 Actual slice 结束取 GPU 完成与提交时间的较晚者，仍不同于最终上屏；再看对应 SurfaceFlinger/DisplayFrame，才能追踪显示结果。采集缺少这些轨道时，不把单个 DrawFrame CPU 区间当作完整帧耗时或掉帧数。

排查时可以沿着原文的顺序，但把问题分开：UI 线程是在记录 Display List，还是在等同步；RenderThread 是未获得 CPU、处理纹理/绘制，还是等缓冲区；GPU 和显示端是否已经完成各自工作。这样才能判断该优化的是哪一段，而不是把所有长条都归因于 onDraw()。
