怎么定义掉帧？

这篇文章可与 Perfetto 8：Vsync 机制与性能分析 对照阅读。分析时要区分 App 错过渲染期限、某个 Buffer 没有呈现、画面更新不均匀，以及输入到显示的延迟增加；它们并不总是同一件事。

60 Hz 的显示周期约为 16.67 ms，90 Hz 约 11.11 ms，120 Hz 约 8.33 ms，但一个主线程 Slice 的允许时长不能只套这个数字。还要看目标帧率、调度给出的 deadline、CPU/GPU 流水线和目标呈现时间。FrameTimeline 从 Android 12 起提供相关证据；采集支持该数据时，先看 Expected/Actual Timeline、jank 类型和 present 状态，再沿 App、RenderThread、SurfaceFlinger、fence 和调度轨道找原因。旧 Trace 没有这些数据时，结论要相应保留边界。

App 端判断掉帧

初看这张图，很容易想：主线程都超过 16.6 ms 了，这不就是掉帧吗？先别急着下结论。下面框选区间是 30.891 ms，其中主线程 Choreographer#doFrame 很长。它提示 App 生产延迟，不能单凭它断定屏幕在某次刷新中一定重复了旧画面。此前已生产、尚未呈现的新 Buffer 可能暂时维持输出节奏，但也可能没有。

因此，旧 App 端方法耗时要与下游呈现证据对应起来；这不等于“App 端任何帧指标都不能判断 jank”。

SurfaceFlinger 端判断掉帧

这张旧图显示，目标 Layer 的队列在相关时段没有新条目，SurfaceFlinger 也没有对应的新一轮工作。若当时预期画面应每个周期更新，这与旧画面多保留一个周期的情况一致。没有新 Buffer 不等于 App 的 Layer 消失或被跳过合成：系统可以保留已锁存的内容；若其他 Layer 更新，也可以继续使用它。静止画面或低于显示刷新率的内容正常复用旧帧，本身不是卡顿。

图上 Layer 计数表示排队条目数，不是总共分配了几个 Buffer，也不保证 GPU 已经完成。正值与 SurfaceFlinger 有工作只能支持进一步关联，不能独立证明每帧按时显示、输入延迟没有增加。要继续看 frame number/token、acquire fence 和实际呈现。图中的 0/1/2 也只是这个样本的取值范围。

逻辑掉帧

还有一种问题是画面按时输出，但内容更新节奏不对。这里沿用“逻辑掉帧”的叫法：比如列表惯性滑动时，位移步长本应按动画曲线变化，却无故出现 20、10、30 像素的跳变。即便渲染和呈现都赶上了期限，用户仍会感觉不连贯。

仅看通用帧轨道未必能发现原因；可以补充动画进度、位置、输入时间戳等埋点，并结合录像核查。不要把所有曲线不均匀都归为 bug：加速、减速和弹簧运动本就可能是有意设计。

BufferQueue 和 Triple Buffer

BufferQueue

BufferQueue 连接生产者与消费者，传递图形 Buffer 的句柄和同步信息，队列本身不复制整幅像素。两端可以跨进程，也可以在同一进程。AOSP BufferQueue 文档介绍了基本模型：

  1. 生产者通过 dequeueBuffer() 请求空闲 Buffer 槽位，参数包括尺寸、像素格式和 usage；拿到槽位后还要遵守返回的 release fence，才能安全覆盖上次内容。这不是“请求释放一个 Buffer”。
  2. 生产者提交 CPU/GPU 绘制工作后，通过 queueBuffer() 提交 Buffer 及其 fence。GPU 可以仍在执行，入队不等于渲染已完成。
  3. 消费者通过 acquireBuffer() 取得条目，并在使用像素前满足 acquire fence 依赖；获取句柄与实际读取内容可以是不同时间。
  4. 消费者通过 releaseBuffer() 归还槽位并传递 release fence，生产者再次使用时仍需等待相关访问完成。

普通非 shared 模式的槽位通常经过 FREE → DEQUEUED → QUEUED → ACQUIRED → FREE。这是所有权状态，不能代替 fence 的完成状态；取消、丢弃等路径也会改变状态。见 Android 16 BufferSlot.h。

Vsync 帮助安排渲染和呈现，BufferQueue 的所有权与 fence 负责访问同步；四个操作并不是每次都由 Vsync 直接触发。相关机制见：

  1. Systrace 基础知识 - Vsync 解读
  2. Android 基于 Choreographer 的渲染机制详解

上面的生产者、消费者还是有些抽象，我们换成 App 和 SurfaceFlinger 来看。在本文旧设备的 Layer BufferQueue 路径里，App 是生产者，SurfaceFlinger 一侧是消费者：App dequeue、绘制并 queue；SurfaceFlinger 在合成流程中 acquire，在下游不再需要旧内容时 release。release 不等于 SurfaceFlinger CPU 合成函数一返回就能立刻覆写，HWC/GPU 仍可能持有依赖。

新系统不能照搬这个进程边界。Android 16 的 BLASTBufferQueue在客户端创建队列和消费者，再通过 SurfaceControl Transaction 向 SurfaceFlinger 提交 Buffer。缓冲上限受生产者、消费者、异步模式等约束，还会涉及刷新率和工作时长；“三缓冲”不代表所有窗口始终分配或占用恰好三个 Buffer。

那么，这个队列到底需要几个 Buffer 才能运转？下面分别用一、二、三个图像 Buffer 来看流水线如何重叠。图中的 Front/Back 是角色，不是固定槽号；A/B/C 是复用的存储，不是永不变化的帧编号。“CPU 渲染”在硬件加速场景主要包含记录和提交 GPU 命令，不能理解为 CPU、GPU、SurfaceFlinger 永远各自占一块像素 Buffer。图中的屏幕行表示显示出的内容，也不保证直接扫描的就是 App 那块内存，实际还可能经过合成目标或 HWC。

Single Buffer

只有一块图像存储时，生产者写入与消费者读取需要协调，不能按一般多缓冲队列的方式随意重叠。

若直接扫描的同一块存储还在被写入，屏幕可能读到新旧混合内容，形成撕裂。单纯错过某个渲染期限并不必然导致撕裂；正确同步的多缓冲系统通常会延迟呈现或继续显示旧内容。

“单缓冲已经不再使用”也过于绝对。Android 10/API 29 起可用的 低延迟 front-buffer 绘制适用于手写等小范围更新，同时需要处理撕裂风险；它不是普通全屏 View 渲染的通用替代。

Triple Buffer

再增加一块可用存储，可以让部分 CPU 提交工作与前一帧 GPU/消费工作重叠，减少等待旧 Buffer 归还造成的空转。若一块正在消费、另一块还在 GPU 绘制，第三块可能可用；这不等于始终有两个空闲 Buffer，也不能让尚未完成的 GPU 结果提前可用。

下图中，第二个周期可以先准备 C，第四个周期因此有 C 可显示；第二个周期仍重复 B。原图底部第 4 条沿用了双缓冲说明，应以这里的 显示 C 为准。第五周期 SurfaceFlinger 行同时画出 B 和 A，只能视为简化示意，不能据此认定两帧都在同一次显示刷新中呈现。

把两图放在一起，这个模型的重复旧内容次数从两次减少到一次。它解释了可用 Buffer 增多为什么有时有帮助，不是“三缓冲能消除所有卡顿”的保证。

Triple Buffer 的作用

缓解掉帧

三缓冲提供额外周转空间，可以吸收短暂的生产或消费波动。效果取决于哪一段在等待、何时释放，以及此前是否有尚未呈现的有效内容；不能把所有被掩盖的 App 延迟都归为 GPU 问题。

上图仍是前面的旧样本。它说明应结合队列看生产与消费，不能只凭计数与合成 Slice 宣布按时呈现。持续超出处理能力时，队列里的余量终会用完。

减少主线程和渲染线程等待时间

双缓冲时，生产者可能要等上一块 Buffer 释放才能继续。图里的 B 要在下游不再使用、依赖满足后才能复用。App 与 SurfaceFlinger 的 Vsync 相位可能不同，不能把“两者总同时收到 Vsync”当作这个现象的前提。

在旧 HWUI 路径上，RenderThread 的 dequeueBuffer 变长，还可能让主线程后续同步等待。下面的图展示了这种关联，具体阻塞点仍需结合线程状态和 fence/Binder 信息确认：

第三块 Buffer 有时能缩短这类等待，但三块都在使用、消费速度不足或 fence 未满足时，仍可能出现背压与 dequeue 等待。主线程何时被 RenderThread 解除阻塞也依赖 HWUI 路径，不能把整段 DrawFrame 都算作主线程同步等待。

降低 GPU 和 SurfaceFlinger 瓶颈

这里“降低”的是缓冲不足造成的额外等待，不是提高 GPU 或 SurfaceFlinger 的计算能力。GPU 绘制由提交的命令和依赖推进，不是等 SurfaceFlinger 想使用某块 Buffer 时才临时开始。额外缓冲可以改善重叠，但无法消除持续的 GPU 过载、长合成或调度问题。

下面两图保留了原案例中的 SurfaceFlinger Binder 线程等待和 App RenderThread 长 dequeueBuffer。它们是排查消费端背压的线索；仅凭这组图与附件文件名，不能证明一次受控的“双缓冲改三缓冲后问题基本消失”实验。

内存与延迟代价

额外 Buffer 要占用图形内存，实际大小受 stride、格式、压缩和分配方式影响。生产过快还会积压尚未呈现的内容，增加输入到显示的延迟；这类情况可表现为 FrameTimeline 的 Buffer Stuffing。即使输出节奏平稳，交互也可能更迟钝。是否保留、替换或丢弃排队内容，取决于队列模式及呈现策略，不能假定所有 Buffer 必定逐个显示。

因此，评估缓冲策略应同时比较帧间隔、目标呈现时间、输入延迟、等待位置和内存，而不是只看 FPS 或已分配 Buffer 数。

图里的 Buffering stats 是旧统计格式。Android 9 SurfaceFlinger按 OccupancyTracker 接受的活动分段累计时间：

  • Active time：纳入统计的活动时间，单位秒，不是应用完整运行时间。
  • Two buffer：没有记录到队列占用超过 1 的分段时间占比。
  • Double buffered / Triple buffered：平均队列占用分别小于 1、介于 1（含）和 2（不含）的分段时间占比。

这几列不是实时分配数量，也不是三项互斥的 Buffer 使用百分比。Two buffer 与后两列可以重叠；Triple buffered 为 0，不能证明从未分配过第三块图形内存。OccupancyTracker 源码还会筛选统计分段，因此没有一行记录也不能填成零使用。

所以此标签值为 0 时允许扩展，值为 1 时不扩展；不是只改了默认值。这个 Android 10 结论不能概括“所有 Android P 之后的版本”。Android 16 的 BLAST 路径会从 SurfaceFlinger 获取最大 acquired 数，并结合其他队列限制；SurfaceFlinger 对该数量的计算还涉及刷新率及 App/SF 工作时长。
