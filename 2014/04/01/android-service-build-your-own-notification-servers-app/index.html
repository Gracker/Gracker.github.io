2026-10-13 更新：本文记录的是 Android 4.3 之前通过无障碍事件观察通知的旧方案，这条通用通知中心实现路线已过时。Android 4.3（API 18）起提供专门的 NotificationListenerService，第 4 节补充 Android 7.0（API 24）及以上的最小监听示例。旧代码仅用于理解历史实现，不保证取得完整通知列表。

1.辅助性服务实战介绍

上一篇文章介绍了什么是 Accessibility 以及简单的使用，这一篇文章就来讲讲如何使用Accessibility服务来创建一个简单的Android通知中心。Android中通知中心是一个系统层面的服务，负责显示应用和系统发来的通知（Notification，比如USB插入、选择输入法、未接来电、截图、天气信息、新闻推送等等）。在android4.3之前，一般的第三方应用是无法获取Notification list的（在Android4.3之后，有了一个新的接口,NotificationListenerService.getActiveNotifications(),可以获取当前的Notification）。但是利用Accessibility服务可以监听到各种事件的特性，可以开发一个第三方的通知中心，实现与系统通知栏类似的功能。

下面保留原有无障碍方案的实现过程。示例中的布局资源由原工程提供；它不是完整 Android 工程。新的通知中心应使用第 4 节的专用接口。

RemoteViews 是远程布局描述，不能直接传给 addView()；需要先调用 apply() 得到 View。Notification.contentView 在 API 24 已废弃，现代标准模板通知也可能没有这个字段，因此它不能用于还原所有通知。上述代码只保留了原文的展示方式及失败处理。

要模拟完整的通知中心，还是要费一番功夫的：更新、移除、排序、用户交互和进程重启都得处理。这里因为公司项目保密，没有贴出完整实现，有兴趣的同学可以私下和我交流。

3.总结和问题

AccessibilityService的实战就讲到这里，这一篇博文也是拖了一段时间才写完的，也算是为前一段时间的项目做个了结。

原项目当时遇到的限制包括：

  1. 无障碍事件不能提供完整的当前通知列表，更不能还原已被清除的历史通知。
  2. 当时的数据只保存在内存里，服务被杀掉后就丢了。我试过用 db4o 这类对象数据库保存整个通知对象，没走通。需要持久化的话，可以把文本、包名、时间等必要字段存进自己的数据库；整个 Notification/RemoteViews 不适合作为稳定的持久化格式。
  3. 并非所有系统变化都会产生可见的通知事件，例如 USB 状态应使用对应系统 API 观察，不能靠通知内容完整推断。
