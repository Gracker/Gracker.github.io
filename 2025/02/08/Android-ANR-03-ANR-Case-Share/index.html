ANR(Application Not Responding)，应用程序无响应，简单一个定义，却涵盖了很多 Android 系统的设计思想

首先，ANR 属于应用程序的范畴。这不同于 SNR(System Not Respoding)，SNR 反映的问题是系统进程(system_server)失去了响应能力，而 ANR 明确将问题圈定在应用程序。SNR 由 Watchdog 机制保证，具体可以查阅 Watchdog 机制以及问题分析; ANR 由消息处理机制保证，Android 在系统层实现了一套精密的机制来发现 ANR，核心原理是消息调度和超时处理

其次，ANR 机制主体实现在系统层。所有与 ANR 相关的消息，都会经过系统进程(system_server)调度，然后派发到应用进程完成对消息的实际处理，同时，系统进程设计了不同的超时限制来跟踪消息的处理。 一旦应用程序处理消息不当，超时限制就起作用了，它收集一些系统状态，譬如 CPU/IO 使用情况、进程函数调用栈，并且报告用户有进程无响应了(ANR 对话框，部分 Rom 不显示 ANR 对话框，而是直接闪退到主界面)

然后，ANR 问题本质是一个性能问题。ANR 机制实际上对应用程序主线程的限制，要求主线程在限定的时间内处理完一些最常见的操作(启动服务、处理广播、处理输入)， 如果处理超时，则认为主线程已经失去了响应其他操作的能力。主线程中的耗时操作，譬如密集 CPU 运算、大量 IO、复杂界面布局等，都会降低应用程序的响应能力

最后，部分 ANR 问题是很难分析的。有时候由于系统底层的一些影响，导致消息调度失败，出现问题的场景又难以复现。 这类 ANR 问题往往需要花费大量的时间去了解系统的一些行为，超出了 ANR 机制本身的范畴。有一些 ANR 问题很难调查清楚，因为整个系统不稳定的因素很多，例如 Linux Kernel 本身的 Bug 引起的内存碎片过多、硬件损坏等。这类比较底层的原因引起的 ANR 问题往往无从查起，并且这根本不是应用程序的问题，浪费了应用开发人员很多时间，如果你从事过整个系统的开发和维护工作的话会深有体会。所以我不能保证了解了本章的所有内容后能够解决一切 ANR 问题，如果出现了很疑难的 ANR 问题，我建议最好去和做 Framework、驱动和内核的朋友聊聊，或者，如果问题只是个十万分之一的偶然现象，不影响程序的正常运行，我倒是建议不去理它

ANR 常见原因

对于 ANR 的原因，通常要做到 ：大胆假设，小心求证 。发现异常的地方提取之后，先假设是这里的问题导致的，然后以这个假设为出发点，看前后的 Log 看看是否能支持自己的假设，如果不能，那么换一个点.

以下按等待位置列排查方向；出现某个操作不等于已经 ANR，最终要连接到具体超时合同。Activity 生命周期慢通常通过阻塞输入等路径引发 ANR，并没有适用于所有生命周期回调的统一独立计时器。

问题出在当前进程

  1. 死锁
  2. 主线程调用 thread 的 join()方法、sleep()方法、wait()方法或者等待线程锁的时候
  3. 主线程阻塞在 nSyncAndDrawFrame，等待 RenderThread 的同步点
  4. 主线程耗时操作，如复杂的 layout，庞大的 for 循环，IO 等
  5. 主线程被子线程同步锁 block
  6. 主线程等待子线程超时
  7. 主线程 Activity 生命周期耗时，拖慢输入响应或首帧
  8. 主线程 Service 生命周期函数执行超时
  9. BroadcastReceiver.onReceive() 未及时返回，或 goAsync() 后未及时完成 PendingResult
  10. 渲染线程耗时
  11. 耗时的网络访问
  12. 大量的数据读写
  13. 数据库操作
  14. 硬件操作（比如 Camera)
  15. Binder 服务进程的线程池饱和，导致关键同步请求排队（不是 Binder 对象数量有统一上限）
  16. 工作线程异常退出后，业务等待条件未完成；普通 Thread.join() 在目标线程结束后会返回，不能把线程终止本身当作永久等待原因
  17. Dump 内存操作
  18. SharedPreferences 加载/写入或生命周期中的待落盘工作拖慢关键线程

问题出在远端进程或者系统

  1. 与 SystemServer 进行 Binder 通信，SystemServer 执行耗时
  2. 方法本身执行耗时导致超时
  3. SystemServer Binder 锁竞争太多，导致等锁超时
  4. 等待其他进程返回超时，比如从其他进程的 ContentProvider 中获取数据超时
  5. Window 错乱导致 Input 超时
  6. ContentProvider 进程死亡可能使依赖调用失败或影响客户端存活，取决于依赖类型；进程死亡与 ANR 要分别判断
  7. 整机低内存
  8. 整机 CPU 占用高
  9. 整机 IO 使用率高
  10. SurfaceFlinger 超时
  11. 系统冻结功能出现 Bug
  12. system_server Watchdog 超时属于另一种系统故障检测，可能与应用 ANR 同时出现，不能直接称为同一种 ANR
  13. 整机触发温控限制频率

ANR 案例：Broadcast 超时导致 ANR

当时用户正在迁移数据，广播里已经起了工作线程，还是报了 ANR。一开始没看出问题，是因为以为耗时工作放到子线程就不会影响广播完成；后来才注意到这里调用了 goAsync()。完整广播 reason、工作线程栈和 finish() 时间已缺失，下面两行只显示数据库升级窗口获得焦点，不能单独证明广播超时原因。

从代码机制看，goAsync() 允许 onReceive() 返回后继续处理当前广播，不限于有序广播，也不会重新开始计时或延长为无限期。只开一个线程而不保留广播的处理生命周期，也不能保证进程一直存活。需跟踪 PendingResult 是否及时完成、任务是否排队过久或漏走结束分支，而不是一概称为“onReceive 函数本身执行超时”。

旧文注释中“10 秒/30 秒或更久”和 JobIntentService 只能作为历史阅读材料。当前诊断按版本和 FLAG_RECEIVER_FOREGROUND 区分：Android 13 及以下常见 10/60 秒，Android 14 起可按 CPU 饥饿延长到 10–20/60–120 秒；OEM 可调整。预算包括启动/调度等待和异步工作，不只是工作函数运行时间，详见官方广播 ANR 诊断。

主线程进行数据库读写

这张栈能确认主线程正在 getWritableDatabase() 的连接打开/日志模式设置路径，同时持有若干 Java 锁；它不是一条已定位的慢业务 SQL。Native 帧有 usleep/nanosleep，可能涉及 SQLite 的锁等待重试，但多个 ??? 缺少符号，尚不能确认具体 busy handler 或持锁连接。SQLite busy timeout 确实允许锁忙时睡眠重试，不能反过来把任意 SQLite 睡眠都认定成同一原因。

应补齐数据库打开、初始化/升级、事务与连接的时间线，找占用锁的连接/进程；把打开和迁移等阻塞工作移出主线程，并避免 UI 再同步等它完成。增加 busy timeout 只会延长等待，不是消除 ANR 的办法；也不要凭这张栈直接改 WAL 模式。若没有 ANR reason 和持续时间，这里只能标为风险现场，不能证明独立一次 ANR。

Binder 数据量过大

这些行记录的是较大的 Binder reply，size388568 等是 Parcel 数据字节数；不是交易数量，也不是耗时。日志本身不证明交易失败、进程崩溃或 ANR。

还有版本差异：AOSP Android 10 Binder.checkParcel 的检查受默认关闭的 CHECK_PARCEL_SIZE 控制，门槛是 800 * 1024 字节；Android 15 同处仍如此。此处几个值低于该门槛，因此不能把这份旧设备日志说成该 AOSP 默认实现的直接输出，需查设备分支的阈值/记录方式。

TransactionTooLargeException 文档说明 Binder 事务缓冲区由进程内在途事务共享（文档标为 1 MB），不是每次调用独享 1 MB。优化时减小/分页返回内容，大数据用合适的文件描述符或共享数据通道，并核对并发事务；还要用等待时长证明它是否影响本次 ANR。

Binder 通信失败

先按设备内核的日志格式解码，不要一看到 transaction failed 就归因内存不足。以 Linux v4.14 binder.c 为格式参照，1698:2362 是发出交易的 PID:TID，29189/-3 是协议返回码/附加错误，size100-0 是数据和 offsets 区字节数，line3042 是内核源码错误路径的行号，不能跨版本直接查同一行。

该版本 UAPI 中，29189（0x7205）是 BR_DEAD_REPLY，不是 BR_FAILED_REPLY；errno 定义 中 -3 对应 ESRCH，-22 对应 EINVAL。这只提供解码方向，不证明该设备就是 v4.14；尤其最后一行返回码/错误组合，需要设备源码和前序 driver 日志确认。

继续核查目标进程死亡、Binder 节点/映射和错误分支，再结合客户端异常、重试及等待时间判断影响。失败可能很快返回，本身并不等于 ANR；也不能据此直接增加 Binder 线程池或断言 payload 太大。
