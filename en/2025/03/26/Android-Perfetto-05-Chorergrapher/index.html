This article introduces Choreographer, a class that App developers may not frequently encounter but is critically important in the Android Framework rendering pipeline. We will cover the background of its introduction, a brief overview, partial source code analysis, its interaction with MessageQueue, its application in APM (Application Performance Monitoring), and some optimization ideas for Choreographer by mobile phone manufacturers.

Choreographer coordinates pending frame callbacks with display timing; it does not itself set the screen refresh rate. At 120 Hz, the interval is about 8.33 ms. Meeting a frame deadline also depends on CPU scheduling, GPU work, buffers, and composition. Apps request callbacks as needed rather than redraw on every physical Vsync. This article also distinguishes what FrameCallback, FrameMetrics, gfxinfo, Looper, and Perfetto can observe.

The Essence of Main Thread Execution

Much Java work on the main thread is dispatched by Looper through Handlers. MessageQueue queues and retrieves messages rather than executing business logic. nativePollOnce also processes file-descriptor events, including Vsync reception; not every main-thread operation is a Java Message. These images show waiting and dispatch in the captured examples.

Evolution

A dequeueBuffer wait can involve available buffers, consumer release, or fences. The image does not establish a fixed SurfaceFlinger consumption rate for every app; a traditional framebuffer description is not universal to modern displays.

Choreographer is available from API 16. Vsync pacing and buffering help organize rendering without guaranteeing a stable frame rate. BLAST later changes the buffer/transaction path, discussed below.

For users, a stable frame rate is a good experience. For example, when playing Honor of Kings, compared to frequent fluctuations between 60 and 40 fps, users feel better when it is stable at 50 fps.

This is an intuitive description of experience. Presentation cadence matters too: a fixed 60 Hz display cannot present 50 fps at equal integer-refresh intervals, so it is not a universal ranking for every device.

Introducing Choreographer

Choreographer gives due animation and traversal callbacks an opportunity to run in relation to display timing. A software Vsync notification still depends on the owning Looper’s scheduling; a hardware interrupt does not directly execute Java drawing.

This older 60 Hz diagram uses 16.6 ms, not a universal end-to-end budget. Its RenderThread “GPU” label is inaccurate: RenderThread is a CPU thread organizing/submitting work, with asynchronous GPU execution. UI, RenderThread, GPU, and SurfaceFlinger stages can overlap.

At 120 Hz, adjacent refreshes are about 8.33 ms apart; scheduling determines the actual work deadlines. See the 90 Hz article for refresh-rate versus frame-rate context.

Introduction to Choreographer

Choreographer coordinates callbacks registered with it, not all Handler messages. Framework work is processed in Input, Animation, Insets Animation, Traversal, and Commit order when callbacks are due. These are execution phases, not Linux thread priorities.

DisplayEventReceiver provides requested software Vsync timing. Timely app, RenderThread, GPU, and SurfaceFlinger completion still needs separate observation; using Choreographer and BLAST does not guarantee stable 60/90/120 fps. Monitoring boundaries are discussed below.

Diagrams help explain the mechanism, but here I will mostly use Perfetto and MethodTrace. Placing CPU, SurfaceFlinger, SystemServer, and app activity on a timeline and following the code makes their interactions easier to see. I will use a few diagrams, then work through traces; what they show still depends on what was recorded.

These historical Perfetto images show scrolling Settings. Green Running segments are CPU scheduling states, not presented frames; slices can include waits.

  1. The VSYNC-app counter toggles to indicate software Vsync cadence, annotated around 8.33 ms here. High/low levels are not durations of “Vsync executing”; do not mistake a whole square-wave cycle for one refresh interval. Match the producer’s definition.
  2. Follow doFrame, DrawFrame, buffer submission, and SurfaceFlinger dependencies, while accounting for overlapping threads/frames. Adding UI and RenderThread wall durations does not yield final frame latency.
  3. BLAST submits buffers with transactions. Submission does not prove GPU completion or presentation; inspect fences, composition, and presentation evidence.

Now zoom in on one main-thread frame to see where Choreographer sits and how it organizes the callbacks. The arrows locate that work chain. The old “queueBuffer means GPU starts” annotation is not valid: GPU submission/execution has no such fixed one-to-one relationship with queueBuffer. The end of the main-thread slice is not final presentation time either.

Choreographer’s Workflow

  1. getInstance() obtains the default thread-local instance on a thread with a Looper, initializing its Handler, DisplayEventReceiver, and callback queues.
  2. Due work requests Vsync. A file-descriptor event reaches onVsync() through JNI, which posts an asynchronous Message.
  3. When Looper dispatches it, run() calls doFrame() to handle timing, due callbacks, and diagnostic markers.
  4. Input → Animation → Insets Animation → Traversal → Commit run in order. Traversal may measure/layout/draw and synchronize with RenderThread; not every frame repeats every operation.
  5. RenderThread/GPU work, BLAST submission, and SurfaceFlinger composition can overlap this sequence. Commit is not a GPU-completion or presentation callback.
  6. Remaining animation/scroll work registers another callback. A single FrameCallback is not an indefinitely repeating callback.

This older MethodTrace helps locate calls, not establish identical signatures or all phases on every frame.

Source Code Summary

  1. getInstance() returns the default instance for the current Looper thread. It is not process-global or a ban on other internal Choreographer instances on that thread.
  2. Binder control, BitTube events, native FD callbacks, and Java asynchronous Messages are distinct steps, not direct Java execution of a hardware interrupt.
  3. The five-phase order lets due input/animation changes precede traversal. COMMIT is not a GPU fence or presentation notification.
  4. ListView/RecyclerView layout, binding, scrolling, and prefetch can occur through different paths. ViewHolder reuse is not a separate Choreographer phase or proof that one component is always faster; inspect its library version and trace.
  5. FrameCallback is removed after one invocation. Re-registration sustains animation; scheduling coordination does not guarantee timely callbacks or presentation of every buffer.

APM and Choreographer

Distinguish callback cadence, Window/HWUI work, SurfaceFlinger presentation, and one Looper dispatch. They are different metrics. FrameInfo is hidden internal data, not a stable reflection-based app interface.

  • API 16 FrameCallback: observes callback cadence; a long interval suggests delay, not measured display fps.
  • API 24 FrameMetrics: delivers window frame reports. The listener’s dropCountSinceLastInvocation counts lost reports, not display drops. Copy the reused metrics object before deferred processing.
  • API 33 postVsyncCallback: supplies FrameData timelines, deadlines, and expected presentation information. It is one-shot and predictive, not proof of presentation. See Choreographer.
  • gfxinfo/FrameTimeline: read version-specific HWUI output; Android 12+ FrameTimeline relates expected/actual work and presentation for jank analysis when its data source is collected.
  • Looper/IdleHandler: dispatch wall time and queue idleness aid diagnosis, but do not cover GPU/presentation. IdleHandler is not an end-of-frame callback.

Use framestats (internally backed by FrameInfo) for Monitoring

Use adb shell dumpsys gfxinfo <packagename> framestats, replacing the package. This is the original historical StatusBar output, not a new capture:

Parse the CSV by its own header. Timestamp fields differ from durations such as DequeueBufferDuration/QueueBufferDuration; units are ns, with monotonic rather than calendar time. In this older format, OldestInputEvent=9223372036854775807 and NewestInputEvent=0 are unrecorded-input sentinels, not values for calculating input latency.

FrameCompleted marks completion in that HWUI path, not physical presentation. Summary categories such as Missed Vsync and Slow UI can overlap and must not be summed as independent frames. This sample is not Android 16’s FrameInfo layout.

Use SurfaceFlinger for Monitoring

On older implementations, find a layer with adb shell dumpsys SurfaceFlinger --list, then query its latency, for example adb shell 'dumpsys SurfaceFlinger --latency "actual layer name"'. Bare --latency does not select an app; implementation and permissions vary.

In Android 10 FrameTracker, the first line is refresh period and the columns are desired present, actual present, and frame ready times in ns. Its ring has 128 slots but the dump iterates 127, not 128 guaranteed new valid frames. Identify zero and pending-fence INT64_MAX records as invalid/incomplete.

The old ceil((C - A) / refresh_period) uses ready minus desired time without actual presentation. It is not a general dropped-frame formula; refresh changes, pipeline deadlines, and missing values also matter. Prefer FrameTimeline frame/presentation correlation for modern analysis.

Use SurfaceFlinger PageFlip Mechanism for Monitoring

Obsolete interface—historical explanation only. Android 10’s private transaction 1013 returned the default display’s page-flip count under system UID/HARDWARE_TEST checks, not app fps. Android 16 returns NAME_NOT_FOUND for the same code. The original transact-then-readInt snippet ignored failure and is no longer presented as a usable monitoring example.

These are separate version excerpts, not one switch. Use FrameMetrics or FrameTimeline for the intended measurement. Unsupported, denied, or missing data must not become 0 fps. See Android 16 SurfaceFlinger.

Choreographer’s Own Dropped Frame Calculation Logic

This is an older simplified excerpt. jitterNanos is start delay relative to the supplied frame time. Dividing by the interval estimates missed scheduling opportunities, not the current doFrame duration or final presentation drops. Android 16 uses the event interval and handles zero-interval cases.

SKIPPED_FRAME_WARNING_LIMIT defaults to 30 and is read from the property at class initialization. No warning does not mean no jank, and changing its threshold does not fix jank.

BlockCanary

BlockCanary historically used Looper MessageLogging to observe dispatch boundaries. The older skeleton below illustrates their placement; newer implementations may use loopOnce. This is not an installation or maintenance recommendation for the library.

Dispatch wall time includes blocking and scheduling delay, not just CPU work. It does not cover all nativePollOnce FD handling, GPU work, or presentation. Many short messages can also delay a frame. Logging costs work and must be coordinated with other users of the same Looper logger.

MessageQueue and Choreographer

A synchronization barrier changes queue eligibility, not CPU priority. In Android 10 MessageQueue.next(), a barrier at the head (null target) causes a search for the next asynchronous message, whose due time is still checked. This does not preempt a running callback or create another thread.

Framework code uses the hidden postSyncBarrier()/removeSyncBarrier() methods. Message.setAsynchronous(boolean) is public from API 22, and Handler.createAsync() from API 28; the older hidden-API claim was wrong. Without an obstructing barrier, the asynchronous flag does not automatically move a message to the front, and cross-Handler ordering dependencies still matter.

Manufacturer Optimizations

System manufacturers can change framework code and try optimizations at this level. I cannot share that code, but I can outline the ideas. If you are interested, we can discuss them privately.

These are ideas I was considering at the time, not default AOSP behavior or validated benefits on every build. Changes must preserve input/lifecycle order, animation timebases, and buffer/fence contracts, with latency, presentation, power, and compatibility measured.

Input Event Optimization

Choreographer already has CALLBACK_INPUT, used by ViewRootImpl for batched input. Vendors may use more input state to schedule earlier, but must distinguish reception, batching, and app callbacks, validating ordering, resampling, and input-to-presentation latency.

Background Animation Optimization

Stop animation updates when they are invisible and unnecessary for the product, using lifecycle/visibility information. Vendor throttling needs similar care: background does not automatically make every callback useless, especially with multi-window, picture-in-picture, or state progression. This historical image shows dense doFrame work that I labeled as a background case; it does not independently establish visibility, power cost, firmware configuration, or the app’s current behavior.

Frame Drawing Optimization

A vendor can explore earlier composition scheduling in selected scenarios. That does not let a display present at arbitrary times: buffer/fence dependencies, display deadlines, and power constraints still apply. Earlier composition alone is not proof of fewer missed frames.

App Launch Optimization

If queued work delays critical startup messages, first identify unrelated work and waits, then consider controlled scheduling. Arbitrary front-of-queue movement can break lifecycle/input order or starve work. Validate first-frame/interactivity and regressions, not just an earlier message timestamp.

Animation Callback Front-loading

There may be slack after main-thread work, but that does not prove CPU idleness; other messages, threads, and GPU work can continue. Earlier animation calculation must preserve frameTime, property-update, and input-sampling consistency. It is a specific framework strategy, not an automatic jank reduction.

Frame Interpolation

This is closer to vendor pre-rendering or prediction of later animation states than a universal definition of frame interpolation. doFrame has scheduled-state, monotonic-time, and callback-queue constraints. Calling it twice does not establish two generated, submitted, or presented frames, nor image-based motion interpolation.

OverScroller predicts from current velocity and bounds, but new input, boundaries, layout, or content changes can invalidate that prediction. Any advance work needs cancellation, correct timing, buffer/power accounting, and presentation validation. Touch-up does not fix all later frame content.

High Refresh Rate Optimization

When the active display mode is 120 Hz, refreshes are about 8.33 ms apart rather than 16.67 ms at 60 Hz; app frame rate may differ. Evaluate deadlines, presentation cadence, and energy instead of treating the whole pipeline as a fixed single-thread budget. Vendor priorities include:

  1. Performance analysis and optimization of large apps
  2. Game high frame rate cooperation
  3. Logic of mutual switching between 120 fps, 90 fps and 60 fps
