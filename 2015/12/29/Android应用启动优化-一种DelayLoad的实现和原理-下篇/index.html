ViewRootHandler 继承 Handler，在这个标签中没有显式传 Looper。默认 Handler 绑定的是创建它的当前线程 Looper，不会自动选择 mainLooper。此普通 Activity 路径在主线程创建 ViewRootImpl，所以最终使用主 Looper；若当前线程没有 Looper，默认构造会抛异常。

所以在本文旧版、UI 线程、首次 attach 的路径下，外层 Runnable 被下一次 performTraversals() 转交到主消息队列；等当前调用栈返回后才有机会执行。这解释了第一层 post 的去向，但还没有解释第二层为何有时能跨过另一次 traversal。

5. UpdateText

前一篇的评论区有人问：为什么还要在 run 方法里面再 post 一次，直接执行 updateText 不行吗？这个问题还得接着往下看。

上篇观察到双重 post 后的 updateText 位于后一次 traversal 之后。这个现象在旧源码中有对应条件，但原因不能缩成“EGL 初始化必定导致两次遍历”。

在 android-5.1.1_r1 中，原先没有 Surface、本次 relayout 得到有效 Surface 时会设置 newSurface = true。源码注释说明，这次先暂缓绘制并再安排 traversal，以便 WindowManager 得知待显示的窗口；硬件 renderer 初始化也在该分支中。接下来 cancelDraw、窗口可见性、skipDraw 等还会影响是否绘制，所以“两次”不是所有启动都满足的计数。

另一个条件是同步屏障。scheduleTraversals() 安排 traversal 时会插入屏障：

doTraversal() 在进入本次 performTraversals() 前移除对应屏障：

MessageQueue 取消息时，若队首是 target 为 null 的屏障，就继续找异步消息，暂不分发屏障后的普通同步消息。Choreographer 的 VSYNC 消息标为异步，可以越过它；“异步消息”仍可在同一个主线程运行，不等于后台线程。

一种与原文现象相符的旧版队列排列，可以这样追踪外层任务 A 与 updateText 任务 C：

  1. 第一次 traversal 把暂存的 A 放进主消息队列。
  2. 同一次 traversal 因 newSurface 等条件安排下一次 traversal，并插入屏障 B；A 已排在 B 前。
  3. A 得到执行，再用普通 Handler 投递 C；C 排在 B 后，因此暂时不能分发。
  4. 异步帧消息运行，下一次 doTraversal() 移除 B 并执行 traversal。
  5. 此次主线程调用栈返回后，C 才有机会执行。此时 GPU、SurfaceFlinger 和显示端仍可能在处理该帧。

这里必须同时满足相关版本、未 attach 的投递路径、A/B/C 顺序、普通同步 Handler，以及确实安排了后续 traversal。原图没有完整队列日志，不能据图把这一排列证明为每次启动的必然过程。已 attach、改用异步 Handler 或其他调度状态都会改变结果；应用不应直接操作这些内部屏障 API 来制造“首帧后”回调。

7. 2026 年补充

  • Android 16 / android-16.0.0_r1：DecorView 已是 com.android.internal.policy.DecorView 独立类。未 attach 的 View 将动作保存在自己的 HandlerActionQueue，在 dispatchAttachedToWindow 中转交 Handler，不能沿用本文 ThreadLocal RunQueue 的全部推导。API 28 起的 Handler.createAsync 可越过同步屏障，但不是用于启动延迟的后台执行器。
  • Android 12 / API 31 起：系统 SplashScreen 与旧的 StartingWindow/主题预览分析有新的 API 边界。使用官方 SplashScreen 迁移方案及 windowSplashScreenBackground、postSplashScreenTheme 等相应属性；单改旧 windowBackground 不能概括完整配置，独立 SplashActivity 还可能导致双重启动画面。保留启动画面并不会减少真实初始化时间。
  • 工具更新：Android Device Monitor 在 Android Studio 3.1 弃用、3.2 移除；层级检查使用 Layout Inspector，系统时间线使用 Perfetto/System Trace，方法调用分析使用当前 Profiler。文中历史截图不作为这些工具当前界面的说明。插桩式 Method Trace 和调试日志有开销，适合定位调用关系，不能直接当无干扰启动基准。
  • 按条件选回调：尺寸就绪使用布局回调；API 29 的帧提交回调也不保证像素已显示。具体示例见上篇。性能验收同时看初始显示、完整可用状态及后续帧；不要用 traversal 次数或某个 Runnable 的结束代替呈现证据。
