技术复核（2026-10-13）：本文保留 2015 年的视频摘录和示意图。过度绘制的概念仍然适用；下文补充默认颜色表的版本依据、透明混合的例外和删除背景的前提，不把颜色变浅直接当成性能收益。

当时的视频简介：

One of the most problematic performance problems on Android is the easiest to create; thankfully, it’s also easy to fix.

OVERDRAW is a term used to describe how many times a pixel has been re-drawn in a single frame of rendering. It’s a troublesome issue, because in most cases, pixels that are overdrawn do not end up contributing to the final rendered image. As such, it amounts to wasted work for your GPU and CPU.

Fixing overdraw has everything to do with using the available on-device tools, like Show GPU Overdraw, and then adjusting your view hierarchy in order to reduce areas where it may be occurring.

OverDraw概念

视频开头作者举了一个例子，说如果你是一个粉刷匠，你应该会知道，给墙壁粉刷是一件工作量非常大的工作，而且如果你需要重新粉刷一遍的话(比如对颜色不满意),那么第一次的粉刷就白干了. 同样的道理，如果一个不透明区域完全覆盖了前面画出的内容，前面的部分绘制就可能没有贡献。如果你想兼顾高性能和完美的设计,那么你的程序可能会出现一个性能问题:OverDraw!

Overdraw（过度绘制） 指同一帧里，同一个像素被重复绘制。例如下面重叠的卡片，不透明卡片下面被完全遮住的部分可能做了无用功；但不能把“发生重叠”一律视为浪费。半透明内容、阴影和抗锯齿边缘仍需要底下的颜色参与混合，直接删掉底层会改变画面。实际工作量也受裁剪和渲染器优化影响。官方概念说明

2015 年，Google 推出了关于 Android 性能优化的短视频系列 Android Performance Patterns，原播放列表在 YouTube。官方当年的配套课程介绍也记录了这个系列。

技术复核（2026-10-13）：本文保留 2015 年的选题说明和观看经历。早期视频仍可用于理解渲染问题；旧工具、Google+ 入口及“16ms”说法需要按下面的版本条件阅读。

过度绘制、VSYNC、主线程与 RenderThread 的协作仍然值得学习，但帧间隔不是永远 16ms。60Hz 对应约 16.67ms，90Hz 约 11.11ms，120Hz 约 8.33ms；实际产帧截止时间还要看系统调度和 trace，不能把一个固定阈值套到所有设备与场景。

要调查的问题 今天的入口与适用条件
View / Compose 的层级和属性 用 Layout Inspector 检查可调试应用；它也支持 Compose 重组/跳过信息，不能把层级检查等同于帧耗时测量
快速观察绘制阶段和过度绘制 开发者选项里的 Profile GPU/HWUI Rendering、Debug GPU Overdraw；柱形图是 CPU 侧绘制阶段信号，不是纯 GPU 执行时间，也不能覆盖所有自建渲染路径。官方说明
具体哪些帧错过期限 使用 Perfetto 的 FrameTimeline，要求 **Android 12 / API 31+**；再结合已采集到的线程、调度和 SurfaceFlinger 轨道定位
滑动或页面切换是否退化 Macrobenchmark FrameTimingMetric 从 AndroidX Benchmark 1.1.0 提供；frameOverrunMs 要求 **API 31+**，与 frameDurationCpuMs 的口径不同

Hierarchy Viewer、Traceview 所属的旧 Android Device Monitor已在 Android Studio 3.1 弃用、3.2 移除。方法级分析使用当前 Profiler，层级检查用 Layout Inspector。做 Macrobenchmark 时按项目配置要求使用接近发布状态的 non-debuggable、profileable 目标应用，并固定设备与操作场景。

Android Performance Patterns is a collection of videos focused entirely on helping developers write faster, more performant Android Applications. On one side, it’s about peeling back the layers of the Android System, and exposing how things are working under the hood. 这些视频的时间虽然很短，但是信息量却非常大，有些他一句话带过的内容，我们却需要花费很多的时间去研究他的原理，或者研究一个调试工具如何使用。也就是说，这一系列视频并没有真正教你如何去优化你的应用，而是告诉你关于Android性能优化你需要知道的知识，这样你去优化你的Android应用的时候，知道该用什么工具，该采取什么样的步骤，需要达到什么样的目标。

Java的内存泄露的特点

  • Java 内存泄漏常见的特征是：可达，无用。对象还被保留着，业务上却已经用不到了。
  • 需要把对象的预期生命周期与实际保留它的引用路径对照，不能只看对象大不大、数量多不多。
  • 可以复用却反复创建对象，会增加分配和 GC 开销；如果旧对象能正常回收，这是分配浪费，不一定是泄漏。OOM 也可能来自一次过大的正常分配。

MAT简介

MAT介绍

MAT(Memory Analyzer Tool)，一个基于 Eclipse 的内存分析工具，是一个快速、功能丰富的JAVA heap分析工具，它可以帮助我们查找内存泄漏和减少内存消耗。使用内存分析工具从众多的对象中进行分析，快速的计算出在内存中对象的占用大小，看看是谁阻止了垃圾收集器的回收工作，并可以通过报表直观的查看到可能造成这种结果的对象。

MAT 有 Eclipse 插件和独立的 Eclipse RCP 应用。独立版不要求先安装完整 Eclipse IDE，但仍需要兼容的 Java 运行环境。Android HPROF 是否需要转换，取决于导出格式和分析器支持，不取决于 MAT 是插件还是独立安装。
