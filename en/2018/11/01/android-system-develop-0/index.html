Setting Up the Android System Development Environment

Whether you are an Android App developer or a System developer, having a foundational understanding of the Android system is extremely beneficial. I recently set up a development environment at home and decided to share the process for anyone interested.

The general steps involved are as follows:

  1. Installing Ubuntu
  2. Configuring Ubuntu
  3. Installing Essential Software
  4. Configuring Network Access (Optional)
  5. Downloading AOSP Code
  6. Setting Up the Build Environment and Compiling Pixel Code
  7. Flashing the Device
  8. Modifying and Compiling Framework, Services, and Res

Version note — reviewed October 13, 2026: The original is a 2018 environment record. Its screenshots show Ubuntu 18.04.1, PLATFORM_VERSION_CODENAME=Q, and aosp_sailfish-userdebug, but no complete manifest pins the original master checkout. The Pixel workflow remains historical. The new example uses Android 16 tag android-16.0.0_r1, Ubuntu 22.04 x86_64, and Cuttlefish x86_64. It is not presented as the latest release or as a way to flash Android 16 onto the original Pixel.

Recommended Hardware

The old “512 GB SSD and a Pixel” advice needs context. For a modern workstation, the current AOSP requirements list 64-bit x86 Linux, at least 400 GB of free disk space, and 64 GB RAM. A nominal 512 GB disk does not necessarily have that much free space; multiple checkouts and outputs require more. These are planning guidelines for modern builds, not universal limits for every old branch. Reading source needs less, and running this Cuttlefish example additionally requires usable KVM. A physical phone is optional.

1. Installing Ubuntu

Ubuntu 18.04’s standard security maintenance ended in May 2023; extended maintenance has separate conditions. See the Ubuntu release lifecycle. This update uses Ubuntu 22.04 LTS instead of the old 18.04.1 mirror ISO.

  1. Obtain an amd64 image from the official Ubuntu 22.04 release directory and verify it against the published checksums.
  2. Create a bootable USB drive and back up existing data before repartitioning.
  3. Install on a suitable Linux host. A VM can work with enough disk and memory, but running Cuttlefish also requires KVM/nested virtualization to be available inside it. Being able to compile in a VM does not prove it can run the virtual device.

This was my desktop at the time. Do not treat these Linux instructions as a native macOS or Apple Silicon build procedure.

2. Configuring Ubuntu

Choose an input method and editor to suit your workflow. Vim can be installed with sudo apt install vim. Obtain adb and fastboot through Android Studio’s SDK Manager or SDK Platform-Tools. AOSP builds also produce host tools; confirm which copy your shell uses before mixing installations:

Physical-device access on Linux also requires USB debugging authorization and suitable device permissions. Establish connectivity before deployment.

3. Installing Essential Software

I listed VS Code, Android Studio, and Meld for editing and comparing files. Wine, WPS Office, and the input method were my desktop preferences, not AOSP build dependencies. Install what you need; the build dependencies appear below.

4. Configuring Network Access (Optional)

Use a stable source-access path for your environment. The Repo tool’s own download location and the AOSP manifest/project mirrors are separate; changing only the manifest URL may not solve every connection problem.

5. Downloading AOSP Code

The official download guide supports selecting a branch or tag with -b. This example pins android-16.0.0_r1, listed in the Android version/build table. Omitting the branch, as the old article did, does not reproduce its historical checkout.

6. Setting Up the Build Environment and Compiling Pixel Code

The old Pixel sailfish screenshots and the new Cuttlefish example are different targets. Match the product, source, proprietary binaries, and outputs; do not combine their steps.

Install JDK

Installing openjdk-8-jdk is not a general requirement for modern AOSP. The pinned Android 16 build selects its Java toolchain, with envsetup.sh setting ANDROID_JAVA_HOME/JAVA_HOME; do not force it to use system JDK 8. Follow the relevant branch’s requirements for older versions. Building the AOSP tree is also different from building an app with Android Studio’s Gradle tooling.

Install Dependencies

For the selected Ubuntu 22.04 environment, use the official Linux package list:

This corrects the old lib32z-dev name and stops carrying forward obsolete package lists such as lib32ncurses5-dev. Other distributions and older Android branches need their own matching dependencies.

Download Pixel Drivers

Historical Pixel workflow: proprietary hardware binaries must match the device codename and Android build ID. The release driver page lists those combinations. Do not combine the latest preview binaries with arbitrary source. Follow the package instructions and license terms when extracting into the corresponding source root, normally under vendor/. The original article did not record complete archive versions, so the screenshots cannot establish a matching release tag.

The android-16.0.0_r1 envsetup source has removed the old interactive menu: argument-free lunch fails. The three-part selection specifies product, release configuration, and build variant. In this tag, aosp_current maps to bp2a; it does not move the checkout to today’s release. userdebug supports platform development, while production user builds do not provide the same debugging access by default.

m invokes the build, and -j8 allows up to eight parallel jobs rather than requiring exactly eight CPU threads. Reduce concurrency if memory is insufficient. A progress screenshot does not establish full build success.

If using CI downloads instead, obtain the images and cvd-host_package.tar.gz from the same build. Verify actual startup, ADB connectivity, and changed behavior; compilation alone does not establish runtime success.

7. Flashing the Device

This section requires a physical-device target with matching source, proprietary binaries, and images. Do not flash the Cuttlefish images onto a Pixel. The original instructions omitted unlocking and data-loss prerequisites.

Back up data, confirm OEM unlocking is supported, authorize USB debugging, and verify the selected product matches the phone. Follow the official Fastboot procedure to enter the bootloader and unlock if required. Unlocking erases user data and normally needs confirmation on the device; the exact procedure is model-specific.

The original fastboot devices screenshot establishes tool visibility only:

In the correctly selected device build environment, the original command was:

The official first-flash example uses fastboot flashall -w; -w wipes /data. Omitting it does not guarantee cross-version data compatibility or prevent other steps such as unlocking from erasing data. Do not mix partition images from different devices or builds.

The screenshot records that command’s writes, not successful OS startup or functional tests. Dynamic partitions, fastbootd, AVB, and A/B slots on modern targets require their matching device procedure, not the old screenshot’s partition list.

8. Modifying and Compiling Framework, Services, and Res

Complete a full build of the same tree and target before incremental work. Directory names are not module names, and a module build does not necessarily regenerate a flashable image.

Recommended IDEs

  • Java/Kotlin: Android Studio can edit the source, but AOSP is not a normal Gradle project. Use the branch’s supported project-generation tooling, such as AIDEGen, for indexing and dependencies.
  • C/C++: use a familiar editor such as VS Code with matching compilation information. Source Insight and Eclipse were historical preferences, not build requirements.

Compiling Framework

The Chinese original’s mmm framework/base was missing an s; the old directory form was mmm frameworks/base. Do not assume that old entry point applies to Android 16. The pinned tag’s installable non-APEX framework module is:

Its module definition uses the installed stem framework. A separate module named framework is build-only; its name does not make it the deployable jar. Code owned by an APEX must be built through the appropriate module.

Root and Remount

The old successful output came from a debug build. It does not apply automatically to a production user build, and bootloader unlocking does not guarantee adb root:

Android 16 debugging may use OverlayFS for a writable layer. Follow the same-tag remount instructions on a test device or virtual device configured for system modification:

-R may arrange required verity-state changes and a reboot. These are debugging settings, not production-device recommendations. Resolve failures before assuming partitions are writable.

Push Changes

adb sync system updates system files from the current build output. It does not guarantee that other partitions, APEX packages, boot images, or preoptimized artifacts are updated. For a compatible, small system-file change on the same build, use separate steps:

Check each result. If synchronization fails, restore stopped Android services with adb shell start and resolve the error. Here, stop/start controls Android services, not the terminal shell. Changes involving initialization, the bootclasspath, or other partitions need the appropriate full rebuild/deployment procedure.

After reboot, verify the actual file or version marker and test the changed function. OverlayFS overrides have OTA limitations and can remain relevant after image flashing, so confirm the effective content. Command success is only part of validation.
