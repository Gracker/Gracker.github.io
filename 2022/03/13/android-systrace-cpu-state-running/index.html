本文是 Systrace 线程 CPU 运行状态分析技巧系列的第二篇，主要分析了 Systrace 中线程的 Running 状态出现的原因和 Running 过长时的一些优化思路。

本系列的目的是通过 Systrace 这个工具，从另外一个角度来看待 Android 系统整体的运行，同时也从另外一个角度来对 Framework 进行学习。也许你看了很多讲 Framework 的文章，但是总是记不住代码，或者不清楚其运行的流程，也许从 Systrace 这个图形化的角度，你可以理解的更深入一些。Systrace 基础和实战系列大家可以在 Systrace 基础知识 - Systrace 预备知识 或者 博客文章目录 这里看到完整的目录

Running 时间长

显示方式

旧 Systrace 通常把线程的 Running 状态显示为绿色，表示线程正在某个逻辑 CPU 上运行。新录制可使用 Perfetto 调度轨道，以状态和调度事件为准，不只看颜色。

这里要区分三种时间：一次函数区间的经过时间（wall time）、线程实际被调度运行的时间，以及等待 CPU 的 Runnable 时间。函数区间很长，不代表始终在执行；它可能包含等待锁、Binder、I/O 或调度。反过来，Running 也不等于每个周期都在完成有效指令，缓存未命中、内存访问停顿、中断等仍会影响解释。

先选定影响目标场景的区间，把跨越边界的调度片段裁剪后再统计，不要把嵌套函数耗时重复相加。本文没有附完整 Trace 或测试程序，下面六类都是需要进一步验证的原因，不是某台设备已经复现的结论。

原因 1: 代码本身复杂度高，执行耗时久

先检查工作量是否过大：重复计算、算法复杂度、循环次数、分配与复制，都可能增加运行时间。平台库或系统调用也可能成为热点，但不能仅凭函数名把问题归因于厂商修改。

优化建议：用接近发布的构建，在同一场景、输入和设备条件下，对照 Android Studio Profiler 或 simpleperf 的调用栈与调度数据。采样权重不是调用次数，也不是每次函数的精确耗时；缺失符号、回溯限制和采集开销需要一起考虑。

需要给已知代码补区间时，使用 API 18 起提供的 Trace.beginSection() / Trace.endSection()。同步区间必须在同一线程配对、正确嵌套，使用 try/finally 保证异常时也结束。这个区间记录的是经过时间；跨线程异步任务不能随意用一对同步 begin/end 包住。

原因 2: 代码以解释方式执行

看到 Compiling 不能判断业务代码正在解释执行。以 Android 12.0.0_r3 的 ART JIT 编译器为例，JIT compiling 以及 Compiling OSR、Compiling optimized、Compiling baseline 标记包围的是编译工作。它可能带来 CPU 开销，但仍需看所在的线程、调用栈和编译状态，才能解释业务线程为何慢。这里的 JIT “baseline” 也不是应用提供的 Baseline Profile 文件。

ART 从 Android 7 起采用 AOT、JIT 与解释执行的混合方式。新安装应用可能已有安装时编译或配置文件，不能统一视作“没有 odex，所以全部解释执行”。dex2oat 的结果还取决于编译过滤器与 profile，运行过工具不等于每个方法都已 AOT。

现在可以这样验证：

  1. 明确测试的是首次安装、冷启动还是已经预热的执行，并固定构建、输入和温度等条件。
  2. 对关键路径生成并正确交付 Baseline Profiles，减少相关代码首次执行时的解释/JIT 成本。Startup Profiles 则供构建阶段优化 DEX 布局，两者用途不同。
  3. 用 Macrobenchmark 显式比较 CompilationMode。None 是不预编译，运行时仍允许 JIT；Full 也不保证比 Partial 快，代码体积和指令缓存压力可能改变结果。不把手动编译后的单次变快当作线上收益证明。

频繁 JNI 交互、数据转换或反射也可能增加成本，但需要先测量实际热点。JNI 可参考官方性能建议，减少不必要的跨边界调用与数据编组，而不是把使用某种语言特性本身判成问题。

原因 3: 线程跑小核，导致执行时间长

CPU 密集工作在较低能力的核心上可能需要更久，但小核并不是专门留给「非 UX 线程」的核心。系统会结合负载、能耗、允许的 CPU 集合和热状态选择运行位置；内存或 I/O 受限的工作也不一定因换大核而明显变快。

先对照实际核心拓扑、调度轨道与同一时间的频率信息，再判断核心选择是否是瓶颈。普通应用不要把绑核或 SchedBoost 当成通用保证：它们可能不可用，过窄 affinity 还会增加 Runnable 等待，详见 Runnable 篇。

对于可报告目标与实际工作时长的持续负载，可评估 Android 12 / API 31 起的 PerformanceHintManager。它向系统提供提示，实际效果仍取决于设备支持与策略，不直接指定核心。

原因 4: 线程所跑的大核运行频率太低

低频可能是负载变化、能耗策略或热限制的结果，不能从一个频率数值就断言升频不够积极。先把频率事件与对应核心、线程运行窗口对齐，核对该频率信号的含义；请求频率或采样读数不一定等于整段时间的实际时钟。CPUFreq 策略还可能由多个核心共享，参见 Linux CPUFreq 文档。

优化建议：

  1. 应用先减少不必要的计算，检查换核心或频率变化前后同一工作量的耗时。
  2. 有适用负载时使用系统公开的性能提示接口，不依赖私有锁频接口。
  3. governor、频率上限或平台 boost 参数属于系统调试范围。受控实验可以帮助区分原因，但锁频结果不能直接代表用户环境；平台修改还需同时验证功耗、温度和持续性能。

原因 5: 温升导致 CPU 关核、限频

热管理可能通过限制频率、功率或其他资源降低发热，具体机制因设备而异，不能假定所有手机都会关核。先验证问题窗口是否出现热限制，再追查热源；一段长 Running 或一个低频值本身不是证据。

外因包括环境温度和日晒，内因可能来自 CPU、GPU、Modem、相机、充电等。对照同一工作负载、设备初始温度、充电状态和持续运行时间，避免把冷机与热机结果直接比较。若后台或前台存在无必要的计算，优先减掉；必要工作则考虑降低并发、分辨率或质量等级等适合业务的调整。

应用可用 PowerManager 的热状态接口（API 29 起）及 thermal headroom（API 30 起）辅助适配，具体设备可能不完整支持或返回不可用结果；它们不是通用摄氏温度读数。参见 PowerManager 和 Thermal API 指南。

平台调优应依据自身散热、功率和温度约束验证。竞品对比可以提供线索，但不能据此直接放宽保护阈值，或把短时跑分提高等同于持续体验改善。

原因 6: CPU 算力弱

相同频率下，不同微架构、缓存、内存系统和指令路径的性能可能不同。MIPS（Million Instructions Per Second）不是跨架构、跨程序的通用性能排名；更高指令吞吐也可能只是执行了更多工作。应以目标任务的完成时间、CPU 时间、能耗和正确性比较。

优化思路有两条：

  1. 构建与编译：应用开发者也能检查 release/R8 配置、Native 编译优化和 profile 使用情况。按工具链文档做受控对比，不盲目堆优化参数；某个厂商编译器的宣传不能代替当前应用的测量证据。
  2. 代码与数据访问：先用采样找到热点，设备支持且权限允许时，再结合硬件性能计数器理解周期、指令和缓存行为。

计数器分析要确认 PMU 事件定义、计数范围与分母，注意计数器多路复用和不同核心上的可比性。cache-misses 并非每台设备都代表相同缓存层级，较高 miss 率也不自动证明它就是主要瓶颈。参见 simpleperf 事件与统计说明。

  • 若访问局部性确实是瓶颈，可减少无必要复制、调整数据布局与访问顺序，再复测。
  • 不用「复杂指令多」代替性能分析；算法、分支、向量化、指令依赖和内存停顿都可能影响执行。
  • 业务缓存命中率与 CPU 硬件缓存 miss 率是不同指标。缓存需要控制容量与失效策略；减少对象反复分配、释放也应结合内存和 GC 数据，避免用更高内存占用换来新的问题。
