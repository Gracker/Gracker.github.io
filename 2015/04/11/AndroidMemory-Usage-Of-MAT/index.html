MAT简介

MAT介绍

MAT(Memory Analyzer Tool)，一个基于 Eclipse 的内存分析工具，是一个快速、功能丰富的JAVA heap分析工具，它可以帮助我们查找内存泄漏和减少内存消耗。使用内存分析工具从众多的对象中进行分析，快速的计算出在内存中对象的占用大小，看看是谁阻止了垃圾收集器的回收工作，并可以通过报表直观的查看到可能造成这种结果的对象。

MAT 有 Eclipse 插件和独立的 Eclipse RCP 应用。独立版不要求先安装完整 Eclipse IDE，但仍需要兼容的 Java 运行环境。Android HPROF 是否需要转换，取决于导出格式和分析器支持，不取决于 MAT 是插件还是独立安装。

MAT工具的下载安装

当前下载入口为 Eclipse MAT Downloads。本次核查页面提供 1.17.0，独立版最低要求 Java 21，并区分操作系统和 CPU 架构。这个要求是运行 MAT 本身的要求，不是要求被分析的 Android 应用使用 Java 21。

下面的下载和安装截图来自旧版 MAT 1.4 时期，保留用于解释三种安装方式：

  • Update Site 这种方式后面会有一个网址：MAT 1.17.0 对应 https://download.eclipse.org/mat/1.17.0/update-site/ ，安装过Eclipse插件的同学应该知道，只要把这段网址复制到对应的Eclipse的Install New Software那里，就可以进行在线下载了。

  • Archived Update Site 这种方式安装的位置和上一种差不多，只不过第一种是在线下载，这一种是使用离线包进行更新，这种方式劣势是当这个插件更新后，需要重新下载离线包，而第一种方式则可以在线下载更新。
  • Stand-alone Eclipse RCP Applications 这种方式就是把MAT当成一个独立的工具使用，不必先安装 Eclipse IDE，适合平时使用 Android Studio 的同学。Android HPROF 的转换步骤见后文。

下载安装好之后，就可以使用MAT进行实际的操作了。

Android(Java)中常见的内存与资源使用问题

Android内存

使用MAT工具之前，要对Android的内存分配方式有基本的了解，对容易引起内存泄露的代码也要保持敏感，在代码级别对内存泄露的排查，有助于内存的使用。

Android 应用通常在各自的进程中运行，应用也可以配置多个进程；不能把“一个应用”固定等同于“一个虚拟机实例”。Dalvik 属于早期实现，Android 5.0 / API 21 起默认使用 ART，见 ART 兼容说明。

进程的 Java heap 有容量限制，继续分配可能触发 OutOfMemoryError；系统也可能在内存压力下回收进程。这些现象不等于系统已经判定存在内存泄漏。一次过大的正常分配同样可能 OOM，而长期保留无用对象即使尚未 OOM，也可能已经是泄漏。应用多占用的内存会增加全系统压力，不能说一定不影响其他进程。Android 内存管理

Bitmap 的回收要区分版本和所有权

旧文的“用完就 recycle”不能作为所有版本、所有 Bitmap 的统一规则。官方记录的像素存储位置为：Android 2.3.3 / API 10 及以前在 native 内存，Android 3.0–7.1 / API 11–25 在托管堆，Android 8.0 / API 26 起在 native heap。Bitmap 内存管理

官方对 API 10 及以前曾建议谨慎使用 recycle()。现在仍只有在明确拥有这个 Bitmap、确定没有 View、缓存或其他任务继续使用它时，才能手动回收；提前回收后再绘制会出错。图片库或复用池管理的 Bitmap 应遵循其所有权规则。

把某个变量设为 null 只移除这一条引用，其他强引用仍可能保留对象；即使已经可以回收，也不保证立刻 GC 或立即降低进程 RSS。对于 API 26+ 的 Bitmap，Java 包装对象的 shallow size 更不能当作全部像素内存。

其他

资源释放应与获取时的生命周期配对。例如只在界面可见期间需要的监听，可以在 onStart() 注册、onStop() 注销；属于整个 Activity 实例的资源按实例生命周期管理。系统杀进程时不保证调用 onDestroy()，不要依赖它保存关键用户数据。Activity 生命周期

使用MAT进行内存调试

获取HPROF文件

HPROF 保存堆快照中的对象、类与引用关系。本文讨论的普通 Android heap dump 主要回答“这一刻谁还活着”，通常不提供每次分配的时间和完整调用栈；追查分配过程应另外录制 allocation 数据，而不是从快照推断完整历史。

当前入口：Android Studio Profiler

按 Capture a heap dump 的流程，选择 **Analyze Memory Usage (Heap Dump)**，以 debuggable / complete data 方式运行目标应用，复现问题后采集。查看实例、Retained Size、Fields 和 References，再从 Past Recordings 导出 .hprof。仅有 profileable 不等于可以获得同样完整的 heap dump 数据。

抓取本身会暂停应用并产生额外内存开销。对比多次操作后的快照时，要固定场景并考虑 GC 时机；一个大对象或一条引用路径本身不证明泄漏。

MAT中一些概念介绍

要看懂MAT的列表信息，Shallow heap、Retained Heap、GC Root这几个概念一定要弄懂。

3.3.1 Shallow heap

Shallow size 是对象自身在托管堆中的大小，不包含它引用的其他对象。对象头、基本类型字段、引用字段、运行时布局和对齐都会影响它；对象数组保存引用，基本类型数组保存对应元素。不能把 Java 成员都说成引用，也不能把 Java 的 byte[]、char[] 称作 native 分配。

Histogram 按类汇总的 Shallow Heap 是该类所有实例 shallow size 的总和，排序可以切换；排在前面的类型取决于具体快照，未必总是 byte[] 或 char[]。MAT 大小定义

3.3.2 Retained Heap

对象 X 的 retained set，包括 X 以及只有经过 X 才能从 GC Roots 到达的对象；retained heap 是这个集合中所有对象 shallow size 的总和。这描述的是当前对象图中的保留关系，不能直接等同于 native 内存或进程 RSS。

如果 A、B 都能独立从 GC Roots 到达，又共同引用数组 D，那么删除 A 不会让 D 不可达，D 就不计入 A 单独的 retained heap；对 B 也是如此。这不是指标失效，而是共享所有权的结果。如果 D 没有其他根路径，同时移除集合 {A, B} 才会让 D 不可达。可以对选中的对象集合做 Retained Set 查询，不能只把各对象 retained size 相加，也不能把 Group by package 当作自动算出了整个集合的精确 retained size。

Dominator Tree 使用支配关系：从根到 Y 的每条路径都经过 X，才说 X 支配 Y；树中父节点是直接支配者。例如只有根通过 A 到达 B、C，且 B、C 都引用 D 的菱形图，A 支配 B、C、D，它们可同为 A 的直接子节点。这里没有修改实际引用关系，树边也不意味着 Java 字段引用。Dominator Tree 定义

要查看原始引用，可右键选择 List Objects：

  • with outgoing references：这个对象引用了谁。
  • with incoming references：谁引用了这个对象。

GC Root

GC Roots 是可达性分析的起点，可以来自活跃线程的局部引用、JNI 引用、运行时保留的类等，具体类型取决于运行时和 dump 格式。不能简单说“JVM 自己就是一个 GC Root”。MAT 还可能用特殊根类型保留原本不可达的对象，要看对应的 root 类型。MAT GC Roots

对象没有保活路径后才可能被回收，回收时机由 GC 决定；“引用不可达”不等于这一刻已经归还内存给操作系统。分析路径时还要区分强、软、弱和虚引用。

Path to GC Root

在 Histogram 或 Dominator Tree 中选择实例后，可以右键查看它的 GC Root Path：

引用类型会影响对象是否被保活，不能只按“引用强弱”推断一个固定的回收时间：

  • Strong Reference：从 GC Roots 强可达的对象不会作为垃圾回收；只清除其中一条强引用未必足够。
  • SoftReference：回收器按内存需求决定何时清除，不能承诺“内存够就一直留着”。Android 官方建议一般缓存使用可控制容量的 LruCache，不要依赖软引用的回收时机。
  • WeakReference：对象成为弱可达后，GC 在处理引用时清除相应弱引用；不是一失去某条强引用就同步回收。如果仍软可达，也不属于弱可达。
  • PhantomReference：get() 始终返回 null，可配合 ReferenceQueue 观察回收相关的通知并安排清理。它不替代显式 close()，也不是让业务在 finalize() 后按时执行的保证。

查强引用泄漏时，通常先排除 weak/soft/phantom 等 referent 路径，再根据问题检查完整引用图。with all references 会显示非强引用路径，不能把看到的每条路径都当成阻止 GC 的证据。Path to GC Roots 参数
