Version note (reviewed October 2026): These historical cases include logs from 2020. The exact ROM/app versions and complete traces are unavailable. Rendering mechanisms are checked against android-10.0.0_r47; updates use android-15.0.0_r1 and current documentation. These source baselines do not identify the original devices’ builds. Some spacing, line endings, and timestamps are incomplete; missing values are not reconstructed.

Identify type and impact with Android Vitals or field monitoring, then align bugreports, EventLog, main/system logs, and Perfetto covering the timeout window. Direct /data/anr access requires permissions. API 30+ ApplicationExitInfo contains historical exits; traces may be missing, and exit time is not ANR start time. See part two.

The abridged 2015 quotation below is retained as historical context. Attribution to an app does not establish an app-side cause, and ANRs are not confined to the main thread. Low incidence alone does not justify ignoring a problem. Each case below distinguishes observed waits from causes that still need evidence.

ANR (Application Not Responding) is a simple definition that covers many Android system design philosophies.

First, ANR belongs to the application scope. This differs from SNR (System Not Responding), which reflects issues in the system process (system_server). SNR is managed by the Watchdog mechanism, while ANR is managed by the message handling mechanism at the system layer through message scheduling and timeout handling.

Second, the ANR mechanism is primarily implemented in the system layer. All ANR-related messages are scheduled by system_server and dispatched to the application process. The system uses various timeout limits to track message processing. If an app fails to respond within these limits, the system collects diagnostics (CPU/IO usage, thread stacks) and reports that the process is not responding.

Third, ANR is essentially a performance issue. The mechanism limits the app’s main thread, requiring it to handle common operations (starting services, processing broadcasts, input) within fixed timeframes. Time-consuming operations in the main thread (heavy calculations, heavy I/O, complex layouts) reduce responsiveness.

Finally, some ANR issues are very difficult to analyze. System-level issues like Linux kernel bugs, memory fragmentation, or hardware failures can cause message scheduling failures that are hard to reproduce and diagnose.

– From duanqz

Common Causes of ANR

For ANRs, the approach is bold hypotheses, careful checks. Pick an unusual event, suppose it caused the problem, and read the surrounding logs to test that idea. If the evidence does not support it, try another lead.

The lists below identify places to investigate. An operation is not itself an ANR: connect it to the timed-out contract. Slow Activity lifecycle work can block input and other progress; there is no single independent ANR timer for every Activity callback.

Issues Within the Current Process

  1. Deadlocks.
  2. Main thread calls thread.join(), sleep(), wait(), or waits for a thread lock.
  3. Main thread waits at nSyncAndDrawFrame for a RenderThread synchronization point.
  4. Time-consuming operations on the main thread, such as complex layouts, massive for loops, IO, etc.
  5. Main thread is blocked by a sub-thread’s synchronized lock.
  6. Main thread times out waiting for a sub-thread.
  7. Slow Activity lifecycle work delays input or the first frame.
  8. Main thread Service lifecycle method execution timeout.
  9. BroadcastReceiver.onReceive() does not return promptly, or goAsync() work does not finish its PendingResult in time.
  10. RenderThread is time-consuming.
  11. Time-consuming network access.
  12. Application reads and writes a large amount of data.
  13. Database operations.
  14. Hardware operations (such as Camera).
  15. A Binder service process’s thread pool is saturated, queuing a critical synchronous request; this is not a universal limit on Binder objects.
  16. A worker fails without completing a business-level wait condition. Ordinary Thread.join() returns when the target terminates; termination itself does not imply an indefinite join.
  17. Dump memory operations.
  18. SharedPreferences loading/writes or pending persistence work at lifecycle transitions delay a critical thread.

Issues in Remote Processes or the System

  1. Binder communication with SystemServer, and SystemServer execution is time-consuming.
    1. The method itself takes a long time to execute causing timeout.
    2. Too much lock contention in SystemServer, resulting in lock wait timeout.
  2. Timeout waiting for other processes to return, such as getting data from other processes’ ContentProvider.
  3. Window state confusion leading to Input dispatch timeout.
  4. A ContentProvider process death may fail dependent calls or affect client survival, depending on the dependency type. Process death and ANR are distinct outcomes.
  5. System-wide low memory.
  6. System-wide high CPU usage.
  7. System-wide high IO usage.
  8. SurfaceFlinger timeout.
  9. Bug in system freezing function.
  10. A system_server Watchdog timeout is a separate system-failure detector. It may coincide with app ANRs without being the same event.
  11. The device triggers thermal control frequency limitation.

Mechanically, goAsync() keeps the current broadcast active after onReceive() returns. It is not restricted to ordered broadcasts and does not restart the deadline or allow unlimited time. Starting an untracked thread alone does not guarantee process survival. Investigate late/missing PendingResult completion and worker queue delay, rather than automatically calling this a slow onReceive() body.

The older comment’s “10 seconds/30 seconds or more” wording and JobIntentService reference are historical guidance. Current diagnosis distinguishes version and FLAG_RECEIVER_FOREGROUND: common limits are 10/60 seconds through Android 13, and 10–20/60–120 seconds from Android 14 depending on CPU starvation, with OEM variations. Startup/scheduling and asynchronous work consume the budget too. See broadcast ANR diagnosis.

Anomalous Log Examples

Main Thread Database Operation

This stack establishes main-thread database opening/journal-mode configuration through getWritableDatabase(), while holding Java monitors. It does not identify a slow business query. Native usleep/nanosleep may involve SQLite lock-retry behavior, but unresolved ??? frames do not identify the busy handler or owning connection. SQLite busy timeout supports sleep-and-retry on lock contention; that does not make every SQLite sleep the same cause.

Correlate database open, initialization/migration, transactions, and connection ownership. Move blocking opening/migration work off the main thread without making the UI synchronously wait for it. Increasing busy timeout lengthens waiting; it does not remove the ANR risk. Do not change WAL mode from this stack alone. Without an ANR reason and duration, this is a risky snapshot, not proof of a separate ANR.

Large Binder Payloads

These lines report large Binder replies. Values such as size388568 are Parcel data bytes, not transaction counts or durations. They do not by themselves prove transaction failure, process death, or ANR.

Version matters: AOSP Android 10 Binder.checkParcel uses an 800 * 1024 byte threshold behind the default-disabled CHECK_PARCEL_SIZE; Android 15 retains this check. The listed values are smaller, so this historical device output cannot be attributed directly to that default implementation. Inspect its device-branch logging policy.

The TransactionTooLargeException documentation describes a process buffer shared by in-flight transactions, currently documented as 1 MB—not 1 MB reserved for each call. Reduce/page responses, use an appropriate file-descriptor or shared-data channel for large data, and account for concurrency. Its relevance to an ANR still requires timing evidence.

Binder Communication Failure

Decode the device kernel’s format before attributing transaction failed to memory exhaustion. Using Linux v4.14 binder.c as a reference, 1698:2362 is the issuing PID:TID, 29189/-3 is the protocol return code/additional error, size100-0 gives data and offsets bytes, and line3042 locates a kernel error path. Source line numbers are not portable across builds.

In that UAPI, 29189 (0x7205) is BR_DEAD_REPLY, not BR_FAILED_REPLY; the errno definitions map -3 to ESRCH and -22 to EINVAL. This does not identify the device as v4.14. In particular, verify the final line’s return-code/error combination against its kernel and earlier driver logs.

Inspect target-process death, Binder node/mapping state, and the failing branch; then correlate client exceptions, retries, and waits. A transaction may fail promptly without causing ANR. These lines do not justify increasing the Binder thread pool or blaming oversized payloads.
