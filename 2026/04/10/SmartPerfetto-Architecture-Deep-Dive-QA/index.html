Q1：为什么不用 Claude Code 的标准 Skill 系统，而要自建 YAML Skill？

提问背景： Claude Code 的 Skill 系统支持 scripts/ 目录放确定性脚本，避免 LLM 泛化。既然可以用 scripts/ 执行固定的 SQL，为什么还要自建一套 YAML Skill 系统？YAML Skill 能不能理解成一个让性能工程师按预定义规则执行 SQL 的工具？

关键区分：两套 Skill 不在同一个层面

Claude Code Skills 和 SmartPerfetto YAML Skills 解决的是不同阶段的问题：

这是本项目当时的分工，不是标准 Skill 的能力边界。Claude Code Skills 可被用户或模型调用，Agent SDK 也可按配置加载项目 Skills（见官方 SDK Skills 文档）；脚本可以参数化并返回 JSON。SmartPerfetto 选择 YAML，是把查询、输出 schema 和组合执行统一交给自己的后端引擎，而让运行时的查询与展示合同集中维护。

即使只看「确定性执行」，YAML Skill 有几个针对性设计

1. 参数化 SQL，不是固定脚本

性能分析的 SQL 不是写死的——同一个 Skill 需要接受不同的参数（进程名、时间范围、帧 ID 列表）：

这是省略输入声明的教学片段。thread_state 直接使用 utid，没有 track_id；按半开窗口裁剪，避免漏掉窗口开始前已进入的状态或累计窗口外时长。排除 dur <= 0 的未完成/无效区间，缺失状态不当作零。调用端先解析并校验 UTID 和纳秒边界，再由引擎替换；YAML 本身不消除注入风险。Python/Node 脚本也可以提供同样的参数与校验合同。

2. 自描述的输出格式（DataEnvelope）

每个 step 声明输出列名、类型和单位，前端按 DataEnvelope 合同格式化。duration 不一定永远显示为 ms；时间线跳转还需要有效身份、时间单位及相应 clickAction。脚本若返回相同的结构化 JSON，也可以复用渲染，区别在于谁统一维护这个合同。

3. 可组合（composite + iterator）

一个 composite Skill 可以引用多个 atomic Skill，iterator 可以遍历数据行逐帧分析。这种组合在 YAML 中是声明式的，Skill Engine 负责编排执行。scripts/ 方式要实现同样的组合需要自己写编排逻辑。

4. 面向性能工程师，不是面向开发者

提问者说对了：YAML Skill 可以理解成一个让性能工程师按预定义规则贡献分析逻辑的工具。性能工程师知道该查什么 SQL、该看什么指标，但不一定会写 TypeScript。YAML 格式让他们直接定义 SQL 查询和输出格式，不需要碰后端代码。开发热加载需确认服务端已重载定义；新 step、渲染或执行语义仍可能要改代码。

对比总结

维度 标准 Skill + scripts/ SmartPerfetto YAML Skill
本项目运行位置 当时主要用于开发；也可接入 Agent SDK Express 后端 Skill Engine
调用方式 用户或模型调用 Skill，再执行脚本 Agent 通过 invoke_skill
参数化 脚本可定义类型、参数与校验 引擎提供模板替换与输入合同
输出格式 可为 JSON、表格或文本 DataEnvelope
前端渲染 接入结构化输出合同后可渲染 复用已有 renderer
组合能力 脚本/工具编排 composite、iterator 等引擎能力
贡献门槛 熟悉脚本及合同 复用现有能力时写 YAML + SQL

引擎模板支持 ${param|default}；竖线表示模板的默认值分隔符。两种方案可组合，YAML 是本项目维护成本与执行合同的选择。

Q2：「确定性 + 灵活性混合」具体是怎么实现的？

提问背景： 文章说「已知场景用 Strategy 文件约束必检项，但每个阶段内的具体查询和深钻方向由 Claude 自主决定」。这个约束和自主之间的边界在哪里？具体是怎么做到的？

三层机制配合

这个混合设计靠三层机制配合实现：Strategy 文件定义「必须做什么」，启用的 Planning Gate 要求「先提交计划再执行」，Verifier 事后检查文字与状态中的风险信号。

第二层：Planning Gate — 强制先计划，但不限制计划内容

启用了 analysisPlan 引用时，execute_sql 与 invoke_skill 的 MCP 入口要求先调用 submit_plan 提交分析计划。没有提交计划就调用 execute_sql 或 invoke_skill 会被直接拒绝：

关键点在于：Gate 只要求计划存在，不要求计划和 Strategy 的阶段完全对应。 计划仍需满足 submit_plan 的参数 schema；符合结构时可以调整阶段划分——它可以把 Phase 1 和 1.5 合并，可以加入 Strategy 没提到的额外步骤，也可以根据初步数据调整深钻方向。

提交计划时，系统会做场景感知的关键词检查（比如滑动场景检查计划中是否提到了「帧」「jank」等词），但这只是 warning 级别——计划即使不包含这些词也会被接受。

这个设计的目的是：要求 Claude 在调用受保护入口前提交计划（规划纪律），但不限制它怎么想（规划自由）。

这不是所有内部查询的全局锁：预处理、信息查询和工具内子查询不等于上述入口。Quick 未传该引用时不启用 gate。计划存在只证明提交了结构化数据，不证明模型“想清楚”或步骤已执行。

第三层：Verifier — 多维度事后检查

计划和执行之间可能有偏差——Claude 可能提交了计划但实际跳过了某个关键步骤。Verifier 在分析结束后做多维度事后检查，以启发式行为检查为主，同时补充计划/假设/场景完整性校验：

a) 场景完整性检查——分析输出是否覆盖了场景的核心内容：

b) 假设状态检查——已记录假设是否仍为 formed；状态变更不证明证据充分。

c) 因果链深度检查——CRITICAL/HIGH 级别的 findings 是否包含足够的因果连接词和机制性术语（启发式文本匹配）。

d) 可选的 LLM 复核——用独立的 Haiku 模型做证据支撑度验证（可关闭）。

如果检查发现 ERROR 级别问题，会触发 Correction Prompt 让 Claude 补做。

注意 Verifier 不检查 Claude 的计划阶段是否匹配 Strategy 的阶段编号——它检查的是「关键分析动作是否体现在输出中」，不是「计划格式是否正确」。

快照 verifySceneCompleteness 的输入是 findings 与 conclusion 拼接的 allText。hasDeepDrill 使用 hasAnalysisTool || hasKnowledgeDrill，仅出现 lookup_knowledge 等文字也可能满足条件；注释声称“真实调用”不改变实现。因果连接词、模型写下的 evidence 和 resolved 状态都不足以证明真实采证或因果成立。第三层模型审查也可跳过、超时，最多两次 correction 不保证补齐。

完整的约束光谱

把三层机制叠在一起，不同阶段的约束强度形成了一个光谱：

阶段 Strategy 语气 Planning Gate Verifier 检查 约束强度
Phase 1（概览） 建议 需要计划 不单独检查 中
Phase 1.5（架构分支） 建议 — 不检查 低
Phase 1.7（根因分支） 建议+条件 — 不检查 低
Phase 1.9（根因深钻） 🔴 必须/禁止 — 匹配输出中的深钻相关文字 高

而 general.strategy.md（未匹配到场景时的 fallback）则完全是软指引：只给了一个按用户关注方向的路由决策树（CPU → cpu_analysis，内存 → memory_analysis），没有任何必须执行的阶段。general 仍受工具、权限、预算及已启用的 gate/verifier 约束。

Q2 小结

Strategy 表达分析要求，Planning Gate 在启用时检查计划存在，Verifier 提供事后风险提示。具体查询仍可由模型选择，但“描述做过”与“日志证明执行并返回有效数据”必须分开。

Q3：Agent 和 Workflow 最大的区别在哪里？Agent 的能力边界在哪里、由什么决定？

提问背景： 我们在建设 Agent 的过程中，从最初默认 Agent 有能力理解并决策一切给它的 Skill，到现在几乎在 Skill 中写死了一棵决策树，这中间踩坑的出发点都是：「我们认为 Agent 有 xx 能力，但它没有」，导致其输出偏离我们的预期，于是我们不断地给 Skill 加边界，最后变成了一个写死的 Workflow。

本质区别：决策权在谁手里

Agent 和 Workflow 不是两个工具、两个框架——它们是同一个光谱的两端：

维度 Workflow Agent
控制流 开发者在代码中写死 if/else LLM 自主选择下一步
工具选择 预定义执行顺序 LLM 根据数据按需选择
分支条件 代码中的条件判断 LLM 推理判断
失败处理 try/catch + 重试逻辑 LLM 自我反思 + 换方向
可预测性 确定性高 不确定性高
适应新场景 需要开发者加分支 可以自主探索

但工程实践中，几乎没有人处在光谱的任何一端。 Workflow 可提供通用查询、动态路由和拒绝/升级分支；Agent 的可靠性也随任务与约束变化。实际落地的系统都在光谱的某个中间位置。

你们踩坑的根因：对 Agent 能力做了全局假设

「默认 Agent 有能力理解一切 → 发现它做不到 → 不断加约束 → 变成写死的 Workflow」——这个路径的根本问题在于：对 Agent 的能力做了全局一刀切的判断。

但 Agent 的能力在不同环节差异巨大：

能力维度 本项目的分工考虑 该交给谁
意图理解（用户想干什么） 可辅助识别，歧义需处理 Agent（但简单场景可以用关键词匹配替代）
计划制定（分几步做、先做什么） 需任务级验证 需要约束框架：Strategy 文件给框架，LLM 填细节
数据收集（该查什么） 需任务级验证 半自主：Skill 定义了查什么，Agent 决定顺序和参数
数据推理（看到数据后归因） 不能由模型自评证明正确 Agent 提出解释，证据校验约束归因
精确计算（数值统计） 使用可复算程序 工具系统（SQL / Skill Engine）
自我评估（知道自己对不对） 不能独立作为验收 外部 Verifier，不信任 Agent 自评

Agent 能力边界的决定因素

模型能力、任务分布和预算会影响结果；下面讨论本项目可以直接改善的三个工程因素，不把它们当作完整的能力公式：

1. 观测能力——Agent 能”看到”什么数据

同一个模型，给它 scrolling_analysis Skill 的 L2 结构化帧数据 vs 让它自己写 SQL 查原始表，分析质量差距非常显著。Agent 可分析的范围受到数据工具的约束。SmartPerfetto 用 164 个 YAML Skill 封装了领域专家的查询逻辑，Agent 通过 invoke_skill 拿到的是处理过的、结构化的分析数据，而不是原始的百万行 trace 事件。

2. 约束框架——Agent 在什么范围内决策

不约束的 Agent 像一个没有任务清单的实习生——知识够但不知道该先做什么。Strategy 文件、Planning Gate、Verifier 多层机制共同定义了 Agent 的决策边界：Strategy 告诉它「至少要做什么」，Planning Gate 强制它「先想后做」，Verifier 事后检查「分析是否充分」（启发式检查 + 假设闭环 + 场景完整性 + 可选的 LLM 复核）。

3. 反馈质量——Agent 做错后能否被纠正

Agent 的 findings 中存在相当比例的问题（浅层归因、假阳性、遗漏关键步骤）。单纯依赖模型自我纠错效果有限。SmartPerfetto 用多层验证 + 外部纠错 prompt 来闭环：

补充：Strategy 文件就是 SOP，这没问题

有人会指出：scrolling.strategy.md 读起来就像一份 SOP（标准作业程序）——有编号的 Phase、条件表、必做项、甚至直接写了 invoke_skill("scrolling_analysis", {...})。这和「在 Skill 里写死决策树」有什么区别？

数据收集部分借用了 Workflow 的组织思路。 Strategy 文件就是 SOP，它把领域专家的分析经验写成了步骤要求；实际调用仍由模型驱动，只有引擎执行的查询/分支才是程序控制。这是故意的。

关键在于理解 SOP 覆盖了什么、没覆盖什么：

SOP 能覆盖的（数据收集）——Strategy 文件干的事：

SOP 未完全覆盖的（推理归因）——Agent 的价值所在：

不同场景的 SOP 程度不同：

Strategy 文件 SOP 程度 原因
scrolling.strategy.md 高 — Phase 编号 + 条件表 + 必做项 滑动分析方法论最成熟，常见数据收集路径较明确
startup.strategy.md 中高 — 有 Phase 结构，深钻方向更开放 启动场景更多样（冷/温/热、不同瓶颈）

general.strategy.md 低 — 只有路由决策树，无必做项 未匹配场景，先使用通用探查规则

scrolling.strategy.md 是 SOP 程度最高的，因为滑动分析方法论最成熟。general.strategy.md 几乎没有 SOP，因为用户问题完全不可预测。

所以正确的理解是：SmartPerfetto = 「SOP 驱动的数据收集 + Agent 驱动的推理归因」。

SOP 解决「分析滑动问题至少要看哪些数据」——这个问题有确定性答案，用 SOP 是对的。Agent 解决「拿到数据后怎么推理因果、怎么组织结论」——具体实例随 trace 变化，可以结合规则、统计和模型推理。

回到你们担心的“Skill 最后变成了 Workflow”：先看每条规则的适用条件和证据，不必把采用 Workflow 本身视为退化。可以固定可靠的数据收集和诊断规则，在尚未覆盖的问题上开放探索。

这种分工不意味着 SOP 不能处理推理。聚类、严重帧排序、规则诊断和输出格式都可由程序实现，经过验证的确定性诊断也可以是有价值的结果。重点是区分观察、规则判断与假设，并保留来源，而不是为了叫 Agent 就禁止工具产出结论。

Q3 小结

Agent 与 Workflow 的差别主要是决策权如何分配；可靠性要在目标任务上测量。按失败类型决定哪些步骤交给程序、哪些允许模型探索，并保留证据不足时的退出路径。

Q4：Agent 的架构需要从业务视角进行改进吗？

提问背景： Agent 的架构有过不同的设计和演进——从最初的 ReAct 架构，到 LangGraph 的节点式架构，不同的 Agent 架构设计会给它带来怎样的影响？在搭建自己的业务 Agent 时，是否需要考虑架构对 Agent 性能的影响？例如 SmartPerfetto 是在 Claude Agent SDK 的基础上基于业务理解加入了不同的 Skill 加载模式。

三种主流架构的本质差异

这三个名称不处在同一层，也不是互斥路线。ReAct 是推理与行动交替的模式，LangGraph 是有状态图编排框架，Claude Agent SDK 是提供 Agent 循环和工具集成的运行库。

Q5：性能 AI 智能体应该如何做好场景识别？

提问背景： 想做场景识别、路由到正确的 Skill，在建设这部分的时候应该更多基于「用户原声」还是「日志」，或者有什么更好的方法？场景识别的几条路径各有问题：代码匹配（关键词匹配会导致筛选结果过大或过小）、LLM 理解（LLM 的理解不一定准确）、日志还原（能筛选有无滑动，但不一定是用户关注的问题）。

SmartPerfetto 的做法：三层信号、分工明确

SmartPerfetto 的场景识别依赖三层信号配合，每层解决不同的问题：

Layer 1：用户原声（关键词匹配，<1ms）

关键词定义在每个 Strategy 文件的 YAML frontmatter 中，不是硬编码在 TypeScript 里：

为什么当时选择关键词匹配？

  1. 成本：这一步不调用模型；<1ms 是历史目标/观察，LLM 的延迟与 token 消耗也随模型、网络及提示变化，没有固定 500ms/500 tokens。
  2. 可复查：同样的规则与输入便于重现分类路径，但确定性不等于正确。
  3. 适用范围：明确的场景词可以快速路由；否定句、多意图和追问仍可能误匹配，需要验证与纠正路径。

关键词匹配不够的地方怎么办？

关键词匹配的确有边界——当用户说「这个 app 为什么慢」时，关键词无法确定是启动慢还是滑动慢。SmartPerfetto 的处理方式是：匹配不到就 fallback 到 general 场景，让 Agent 在 general 策略的路由决策树中自主选择方向。

这个设计的核心思路是：不要试图在入口处 100% 准确分类，而是让准确的情况走快速路径（关键词 → Strategy），不确定的情况走探索路径（general → Agent 自主路由）。

Layer 2：Trace 数据——架构检测（确定性代码）

场景分类只解决了「用户想分析什么」，但同一个场景（如滑动）在不同渲染架构下的分析路径完全不同：

架构 渲染管线 分析差异
Standard Android UI Thread → RenderThread → SurfaceFlinger 主线程 + RenderThread 双线分析
Flutter TextureView 1.ui → 1.raster → JNISurfaceTexture → RenderThread updateTexImage 双出图管线，需要分析 Flutter engine 线程 + 纹理桥接
Flutter SurfaceView 1.ui → 1.raster → BufferQueue → SurfaceFlinger 单出图管线，不经过 RenderThread
WebView CrRendererMain → Viz Compositor Chromium 渲染管线，线程名不同

检测结果被注入到 system prompt 中（通过 arch-flutter.template.md 等模板），Agent 看到架构信息后选择对应的分析工具。

对提问中三条路径的评价

1. 代码匹配（关键词）：可以用，但要设计好兜底

提问者说「关键词匹配会导致筛选结果过大或过小」。SmartPerfetto 的经验是：

  • 优先级排序为多个命中决定顺序：ANR(1) > startup(2) > scrolling(3)，同时命中多个关键词时取优先级最高的
  • Compound patterns 补充更具体的匹配模式：/启动.*慢/ 比单独匹配「启动」更精确
  • general 兜底处理没有命中的情况：匹配不到就不猜，交给 Agent 自主探索

2. LLM 理解：不建议用在分类入口，可以用在兜底路径

LLM 分类在 SmartPerfetto 中放在 general 场景的自主路由阶段，不放在 Layer 1。此时 Agent 已经拿到了 trace 数据，可以结合数据做更准确的判断。

3. 日志还原：适合做 Layer 2 的补充信号

日志能告诉你「trace 中有什么」（有无滑动事件、有无 ANR），但不能告诉你「用户关心什么」。SmartPerfetto 的数据完整性探测就是这个角色——它不参与场景分类，但为 Agent 提供数据可用性信息。

排序只解决多个命中时“选哪个”，不证明选对；compound pattern 优先仅在同一个 scene 内，较高优先级的宽关键词仍可能抢先。general 只兜住未命中，兜不住误命中。需要区分用户意图与数据中发生的事；是否在入口使用 LLM 应按准确率、延迟和成本评估。场景分类器不用 LLM，不等于相邻的 quick/full 复杂度分类也不用。

Q5 小结

意图路由、架构识别和数据可用性是三个不同问题。关键词分类可复查但会误命中；架构分数和三行表探测也只是线索。保留校正路线，并用目标进程、时间窗和实际数据确认后续分析条件。

Q7：每一轮的 Prompt 是怎么拼接的？

提问背景： 大模型 Agent 的输出质量很大程度取决于 system prompt 的设计。SmartPerfetto 在每次分析时是如何构造 prompt 的？不同场景、不同轮次之间 prompt 有什么变化？token 预算怎么控制？

总体设计：四层分层拼接 + 缓存优化

buildSystemPrompt() 在一次分析开始或部分纠错路径中组织上下文；不是每次模型调用工具后都重建整份 system prompt。设计原则是把相对稳定的内容放前面，变化频繁的内容放后面，以增加可复用前缀。

但“超过 1024 tokens 就自动缓存”是旧源码注释中的过度简化，不能当作 API 合同。官方 Prompt caching 文档区分自动缓存配置与显式断点：需要相应请求配置/SDK 行为，满足模型的最小长度及前缀匹配、有效期等条件。当前文档提供默认 5 分钟及可选 1 小时 TTL；不是 SDK 会话的生命周期。

原稿 4000/800/400 cached tokens 与 ~80%/18%/~8% savings 没有 usage 记录支撑，也把缓存比例和价格节省混在一起。缓存不会减少模型要处理的逻辑内容；应分别读 cache_creation_input_tokens、cache_read_input_tokens 和普通 input/output，再按当时模型的价格计算实际成本。下图 token 数仅为结构说明的估算。

多轮对话中 Prompt 的变化

项目在准备上下文时检查本地 sessionMap 的 SDK ID 与更新时间。SDK_SESSION_FRESHNESS_MS = 4 * 60 * 60 * 1000 是应用自己的新鲜度判断，不能据此声称 Anthropic 端会话统一四小时过期。

  • 项目认为可 resume：省略手动注入的 previousFindings/conversationSummary，仍加入 notes、实体和计划等可用内容。但这个判断不等于 SDK 已成功恢复。
  • 项目认为过旧或不可用：手动加入部分 findings 和摘要；摘要/条数限制意味着历史可能丢失细节。
  • 纠错轮：检测到 auto-compact 时可将 system prompt 软预算降至 3000；没有时复用原 prompt。自动压缩后的历史不等于原始全量消息。
