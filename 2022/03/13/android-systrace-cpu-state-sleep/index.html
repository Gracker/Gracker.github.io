Linux 中的 Sleep 状态是什么

TASK_INTERRUPTIBLE vs TASK_UNINTERRUPTIBLE

不处于 Running / Runnable 的线程不一定在睡眠，还可能停止、被跟踪或已经退出。这里讨论三种常见等待语义，并非 Linux 状态的穷尽分类：

  • TASK_INTERRUPTIBLE：可被等待条件满足或符合条件的待处理信号唤醒。
  • TASK_UNINTERRUPTIBLE：等待不会仅因普通信号或 SIGKILL 到达而结束；信号可能保持待处理，直到等待返回后再处理。
  • TASK_KILLABLE：TASK_WAKEKILL | TASK_UNINTERRUPTIBLE 的组合，可响应内核判定的致命信号，典型为 SIGKILL。TASK_WAKEKILL 是状态标志，不是另一种独立睡眠机制。

图 1 是简化状态模型。旧 Systrace/Perfetto 中，Sleep 常对应可中断睡眠，Uninterruptible Sleep 对应不可中断等待及其显示分类；颜色随查看器和主题变化。睡眠期间线程不在 CPU 上执行，唤醒后才有机会被调度。

“不可中断”不等于永远无法唤醒，也不等于关掉硬件中断：完成事件、显式唤醒，或所用等待接口支持的超时，都可能令线程恢复。比如 Linux 的 wait_event_timeout 可以在不可中断等待中使用超时。参见 Linux 6.12 等待接口与 Linux 5.10 状态定义。

Looper 等待消息、用户态 futex 等待常表现为 Sleep，但不能把所有 Java/Native 锁或网络操作都归成同一种内核状态。具体取决于调用路径、等待接口与时刻。主线程空闲等消息通常是正常行为，不应为了减少白色区间而忙轮询。

TASK_UNINTERRUPTIBLE 作用

这里的“可中断”主要涉及等待对信号的响应，不能把 POSIX signal、softirq 和硬件 IRQ 混为一谈。硬中断/softirq 的执行上下文与用户态信号处理不同；睡眠线程也不是一边睡眠一边处理硬中断。

内核选择不可中断等待，是因为相应操作没有按普通信号提前退出的语义，或要等某个内核条件完成。它与禁止抢占、关闭本 CPU 中断是不同机制；TASK_UNINTERRUPTIBLE 本身不会关闭中断控制器。

I/O 完成、部分内核锁、页等待和驱动同步都可能涉及此类状态，但不是所有 I/O、网络访问或锁等待都会进入 D。应查目标内核的实际等待函数；可对照 Linux 5.10 源码，而不要把一个不断变化的 latest 链接当成旧截图的精确实现。

分析时候的注意点

首先要认识到 TASK_INTERRUPTIBLE、TASK_UNINTERRUPTIBLE 状态的出现是正常的，睡眠占比高不一定是问题：空闲线程可以长期等消息。只有等待推迟关键操作或错过期限时，才需结合具体依赖排查。 分析问题以及做优化的时候需要牢牢把握两个关键点，它类似于内功心法一样:

  1. 原因的排查方法
  2. 优化方法论

你需要知道是什么原因导致了这次睡眠，是主动的还是被动的？如果是主动的，通过走读代码调查是否是正常的逻辑。如果是被动的，故事的源头是什么？ 这需要你对系统有足够多的认识，以及分析问题的经验，你需要经常看案例以增强自己的知识。

以下把 TASK_INTERRUPTIBLE 称之为 Sleep，TASK_UNINTERRUPTIBLE称之为 UninterruptibleSleep，目的是与 Systrace 中的用词保持一致。

初期分析 Sleep 与 UninterruptibleSleep 状态的经验不足时你会感到困惑，这种困惑主要是来自于对系统的不了解。你需要读大量的框架层、内核层的代码才能从 Trace 中找出蛛丝马迹。Trace 只覆盖已采集的事件，Systrace 的 wakeup_from 也不能直接解释为锁拥有者或完整业务依赖。只有广泛的系统运行原理做为支持储备，再结合 Trace 工具分析问题，才能做到准确定位问题根因。否则就是我经常说的「性能优化流氓」，你说什么是什么，别人也没法证伪。反复折磨测试同学复测，没测出来之后，这个问题也就不了了之了。

本文没办法列举完所有状态的原因，因此只能列举最为常见的类型，以及典型的实际案例。更重要的是，你需要掌握诊断方法，并结合源代码来定位问题。

诊断方法

通过 wakeup from tid: ***查看唤醒线程

在 Runnable 篇中已区分睡眠结束与获得 CPU 执行机会：被唤醒后，线程可能仍要等待调度。除线程间唤醒外，定时器、设备完成事件和中断路径也可能唤醒任务；可运行状态还可能来自抢占、让出 CPU 或新任务入队，不是只有原文所列的两种情况。

wakeup from tid 提供调度事件中记录的唤醒上下文。它不一定是业务上的生产者，也不直接证明谁持有锁。中断上下文中的当前线程、代理唤醒、多个等待者以及事件缺失，都可能让简单的 tid 归因误导分析。

图中的红字是历史说明，需修正其中“Running instead 一定显示高优先级线程”的结论：该字段只能辅助查看当时运行的其他任务，不证明其优先级更高或它就是根因。图中的 wakeup from tid: 14116 也只是继续追查的线索。

当前 Perfetto 可结合 sched_switch、sched_waking 和线程状态详情检查唤醒来源；相关表还可能提供 waker_utid、irq_context 等字段。只有采集具备这些信息时才能使用，缺失值不代表没有唤醒者。参见 调度事件与 thread_state 表。

其他方法

  1. 调用栈与 off-CPU 分析：普通 CPU 采样主要观察线程运行时的栈，不会记录睡眠期间的完整执行流。simpleperf 的 --trace-offcpu 在目标内核、权限和版本支持时，可以结合调度切换记录离开 CPU 时的栈；它也不是每个函数入口/出口的全量记录。参见 simpleperf 官方说明。
  2. 事件关联：时间对齐用于找候选，再用 Binder 事务、futex 地址、业务标识、内核栈或源码确认。两个事件同时发生，不足以证明因果。

排查等待时，优先回答“在等什么条件、由谁推进、何时满足、满足后又等了多久才运行”，而不是仅寻找一段颜色相近的时间线。

耗时过长的常见原因

  • Binder：同步调用可能等远端排队、执行与回复，需沿事务关联分别看服务端是否在运行、等待锁或等待 CPU。oneway 不按同步回复方式等待，不能把所有 Binder 区间套同一解释。
  • Java / futex 锁与条件等待：可能来自应用或系统服务的共享状态竞争，也可能是正常的条件等待；futex 是机制，不等于每次都在等某个 mutex。沿具体锁、条件与依赖线程核查。
  • 主动等待：定时器、信号量、消息队列等等待可能是必要的节奏控制。先确认它是否推迟了关键结果，不能把所有 Sleep 都优化掉。
  • 图形 fence 等待：fence 可能关联 GPU、显示或缓冲区使用，不等于 GPU 一直在执行重负载。确认生产者、提交时刻与 signal 时刻，再考虑降低 Shader、分辨率或纹理负担；提升 GPU 频率不是普通应用的通用修复。参见 AOSP 同步框架。

UninterruptibleSleep 状态分析

诊断方法

先确认是 D 类等待，再查是否有 I/O 标志和阻塞函数。这些是采集可能提供的附加信息，并非每段 UninterruptibleSleep 天生都有：

  1. I/O wait 标志可能是 0、1，也可能未采到。
  2. Block reason 依赖内核 tracepoint、采集配置、符号与解析支持。

UninterruptibleSleep 分为 IOWait 与 Non-IOWait

这里的 I/O wait 是线程在对应事件中记录的内核标志，不是“发生了任意 I/O”的完整判定，也不等于 CPU 使用统计中的 iowait 百分比。iowait=0 只表示该处未标为 I/O 等待，不能排除整个上层操作涉及 I/O；缺失字段更不能当成 0。

Page cache 未命中可能引发读盘，但缓存命中也可能需要等页锁、写回或其他同步；一次系统调用也可能穿过多个运行与等待区间。Non-IO 的候选包括内核锁、页或驱动条件等待，不能直接翻译为“必定在等内核锁”。

IOWait 常见原因与优化方法

1. 主动IO 操作

可能的来源包括同步读写、fsync、文件系统元数据、多个任务竞争存储，以及实际配置的 swap 后端。需要结合 I/O 大小、访问模式、请求延迟、队列与错误数据区分；不能从一段 D 状态直接断言碎片、闪存老化或剩余空间不足。

优化方法

  • 应用先减少关键路径上的同步 I/O，合并无必要的小请求，合理批量处理；异步化后仍需确认没有把等待挪到另一个关键依赖上。
  • 预读适合有可预测局部性的访问，过量预读会占带宽和内存。应比较目标负载，而不是默认把 Readahead 调大。
  • Page cache 回收、系统文件驻留和存储维护策略属于平台层面配置。不要把 PinFile 或锁住大量页面当作普通应用的通用方案，它们也会挤压其他工作可用的内存。
  • I/O benchmark 只能说明其测试条件下的能力；真实场景还受缓存、温度、后台负载与文件系统影响。

Swap-in 不一定读物理存储。Android 常使用 RAM 中的压缩 zRAM，解压也有 CPU 成本；配置了 backing device / writeback 的 zRAM 才可能涉及后端存储。应查实际配置，参见 Android 内存管理与 zRAM 文档。

2. 低内存导致的 IO 变多

文件页缓存可以减少重复读取。内存压力增大时，缓存淘汰、缺页、回收与写回可能增加等待，但不能概括为“低内存时几乎所有 I/O 都直接访问磁盘”。还要区分文件页、匿名页、干净/脏页与 swap 后端。

优化方法

  • 减少关键路径同步 I/O，按实际访问模式组织数据与预读。
  • 避免无界业务缓存、大量短命分配和不必要的常驻内存。
  • 平台结合回收、缺页、存储和内存压力事件，区分正常缓存利用与影响任务完成的压力；不以“空闲 RAM 越多越好”为目标。

系统中的内存是被各个进程所共用。当app 只考虑自己，肆无忌惮的使用计算资源，必然会影响到其他程序。这时候系统还是会回来压制你，到头来亏损的还是自己。 不过能想到这一步的开发者比较少，也不现实。明文化的执行系统约定，可能是个终极解决方案。

Non-IOWait 常见原因

  • 回收或页等待：内存压力可能引入锁竞争、页等待或写回，既可能表现为 Non-IO，也可能涉及 I/O；需看实际栈与事件。
  • Binder 内核路径：某些内核操作或锁竞争可能产生此状态，但同步 Binder 等回复常表现为普通 Sleep，不能仅凭调用量下结论。
  • 其他内核锁、驱动或完成条件：Non-IO 只是继续分类的起点，按阻塞位置和依赖链定位。

系统调度与 UninterruptibleSleep 耦合的问题

如果已证实线程在等待某把锁，而锁拥有者又长时间 Runnable，调度延迟就会延长等待；优先级反转是其中一种可能情况。但首先要证明拥有者关系，不能由 Non-IO 或 wakeup from 直接推出。

先缩短临界区、避免持锁做耗时工作，并检查依赖线程为何未运行。Linux 有适用于特定锁的 RT-mutex / PI-futex 优先级继承，但并非所有 mutex、rwsem 或 futex 等待都自动具备 PI。它也不能替代正确的锁设计；无需一开始就把问题归为只能修改调度器解决。
