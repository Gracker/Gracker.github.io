onTrimMemory(int level) 从 Android 4.0（API 14）提供，用于提示应用在合适的时机减少不必要的内存占用。合理缩减缓存有助于系统保留更多后台进程，但不能保证应用不被终止，也不能保证下次返回一定更快。

本文仍用问答方式介绍回调的作用、接入和资源清理。重点是按资源的用途决定保留什么、释放什么，并确保返回界面时能够恢复。

技术复核：2026-10-13。 Android 14（API 34）起不再发送五种旧内存压力级别，相关常量在 API 35 弃用；UI_HIDDEN 与 BACKGROUND 仍可用于状态变化时的缓存管理。下文的 Launcher/Contacts 代码按 AOSP android-4.4.4_r2 核对，作为历史例子保留，并补上适用于当前回调的缓存示例。

0. OnTrimMemory回调的作用？

回调通过 level 提供清理线索。它不等于“每次剩余 RAM 变化就通知”，也不是“进程即将死亡前最后一次保存数据的机会”。只减少自己不再需要的资源，不要为了响应一个级别破坏正在运行的业务。

当前仍使用的两个级别均从 API 14 提供：

级别 含义与处理方向
TRIM_MEMORY_UI_HIDDEN 当前进程不再显示 UI，可缩减只用于界面的可重建缓存；后台播放等工作仍可能继续。
TRIM_MEMORY_BACKGROUND 进程进入后台 LRU 状态，可以进一步释放容易恢复的资源；不能仅据此断言设备已严重缺内存。

下面五项只用于理解旧系统代码，API 34 起不再通知，API 35 标为弃用：

历史级别 引入版本 历史含义
TRIM_MEMORY_RUNNING_MODERATE API 16 进程仍在运行时，设备开始出现内存压力。
TRIM_MEMORY_RUNNING_LOW API 16 运行中的进程收到更高内存压力提示。
TRIM_MEMORY_RUNNING_CRITICAL API 16 运行中的进程收到严重内存压力提示。
TRIM_MEMORY_MODERATE API 14 进程接近后台 LRU 列表中部。
TRIM_MEMORY_COMPLETE API 14 进程接近后台 LRU 列表尾部。

这些旧提示也不保证“应用不会被杀”。处理级别时采用适合自己策略的阈值比较，不要假定一定依次收到所有级别。依据 ComponentCallbacks2 和 Android 16 对应源码。

1. 哪些组件可以实现OnTrimMemory回调？

Application、Activity、Service、ContentProvider 提供 onTrimMemory(int level)，继承这些组件时可按需覆写，并遵守父类调用约定。

这里要区分两种 Fragment：

  • 旧 android.app.Fragment 有这个回调，从 API 14 提供；该系统 Fragment API 在 API 28 弃用。
  • 当前 androidx.fragment.app.Fragment 没有同名的可直接覆写回调。可由宿主或统一的缓存管理器处理，也可以显式注册独立的回调对象，按相应作用域注销。不要把系统 Fragment 的方法清单直接套到 AndroidX。

普通类只是实现 ComponentCallbacks2，不会因此自动收到系统通知；还需要用 Context.registerComponentCallbacks() 注册，并在其作用域结束时 unregisterComponentCallbacks()。使用 Application 级注册会延长回调对象的持有期，不能随意把 Activity 或 View 留在里面。方法名是小写开头的 onTrimMemory，不是 OnTrimMemory。

2. OnTrimMemory回调中可以释放哪些资源？

架构阶段就应明确资源所有权、容量预算和恢复成本。适合清理的通常是不用的内存缓存、可重建的预览、已经结束用途的监听或异步请求。不要清掉尚未保存的用户状态，也不要释放后台业务仍在使用的数据。

磁盘缓存和内存缓存要分开：删除缓存文件主要释放存储空间，不等于回收 Java 堆，回调里也不适合做大量同步磁盘 IO。仅把 View 设成 GONE 不会让 View 对象消失；要检查父容器、监听器和任务队列的持有关系。Fragment 的 View 引用还应遵循其自身 View 生命周期，不能全部等到 trim 回调。

在主线程创建和管理这个对象，通常由 Application 持有。若它的作用域短于进程，结束时调用 dispose()，同时停止再向它提交任务或数据；不要在切换每个 Activity 时反复注册新对象。入缓存后不应由外部随意 recycle()，evictAll() 只移除缓存的引用，不会回收其他使用方仍持有的 Bitmap。

清空不等于暂停生产数据，仍要取消不再需要的预取或忽略过期结果，避免后台任务马上把缓存填回。需要更平滑的恢复体验时，可以按实测改为缩减预算或分层保留；不要把“隐藏就清空所有缓存”推广到播放、上传或其他业务缓存。接口细节见 LruCache。

3. OnTrimMemory和onStop的关系？

onStop() 针对一个 Activity；TRIM_MEMORY_UI_HIDDEN 针对当前进程不再显示 UI。进程内从 Activity A 切到 B 时，A 可以停止，但整个进程仍有可见 UI。多进程应用还需分别判断，不能把一个进程的回调当成全应用可见性广播。

属于单个页面可见期的资源，可以跟随 onStart/onStop 成对管理；跨页面共享且有容量上限的缓存可以由更长生命周期的缓存管理器统一处理。并非所有 UI 资源都必须等 UI_HIDDEN 才释放。

不要依赖“UI_HIDDEN 总在 onStop 之前调用”的顺序。 它们是不同范围的通知，公开接口没有给出可用于同步业务逻辑的统一先后保证。清理应可重复执行、能恢复，也不能依赖 trim 回调作为进程结束前必达的钩子。

4. OnTrimMemory和OnLowMemory的关系？

onLowMemory() 是更早的粗粒度低内存通知。旧文把它与 COMPLETE 相比，是为了说明历史清理强度，并不是两者触发条件完全相同。

从 API 34 起 onLowMemory 不再调用，API 35 标为弃用，参见 ComponentCallbacks。因此不能将其作为现代系统收不到旧 trim 压力级别时的替代。当前应结合仍支持的状态回调、组件生命周期和日常缓存预算管理内存。

5. 为什么要调用OnTrimMemory？

更准确地说，是为什么要响应这个回调。手动传入一个 level 只是在执行本地清理方法，不会向系统声明已经进入对应的进程状态。

减少不用的占用有助于系统保留后台进程，但回收策略还取决于组件状态、依赖关系与全局压力，不是一个固定的“LRU 从低到高、先杀大进程”规则。原文的“保留进程就是热启动、固定快 2–3 倍”也不成立：进程还在而 Activity 需要重建时，仍可能经历温启动；缓存清理过多又会增加恢复成本。

启动应区分冷、温、热状态，并在同一设备、版本和操作路径上测量，参见 应用启动时间。降低存活内存和减少下次恢复耗时，需要一起权衡。

6. 有哪些典型的使用场景？

6.1 常驻内存的应用

Launcher 等长时间运行的应用，可以清理当前不用的预览页和界面缓存，并保留快速重建能力。但“桌面、电话、安全中心”等名称不等于进程不会被终止；是否常驻及其优先级取决于系统角色和实现。应响应系统通知和自身生命周期，不要靠业务代码反复手动调用回调保活。

6.2 有后台Service运行的应用

音乐、下载等场景中，UI 不可见时后台工作仍可能需要数据。可以缩减只用于展示的封面或预览缓存，但不能一并释放播放器、传输缓冲或仍在使用的连接。

Service 也不保证进程常驻；按当前后台执行与前台服务规则安排工作，内存策略由各资源的实际用途决定。验证时覆盖退到后台、返回界面、内部页面切换和配置变化，并记录实际收到的级别；不要在 Android 14+ 等待已停发的五种旧压力回调来证明清理生效。
