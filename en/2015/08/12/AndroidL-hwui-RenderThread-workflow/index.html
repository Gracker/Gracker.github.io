Preface

These are my notes from learning how hwui’s RenderThread works in Android 5.0. I haven’t covered every detail; I wanted to trace the main flow so that, next time I hit a problem, I would know where to look.

I captured the first RenderThread Draw during app startup with Systrace, as shown below. It helps show the execution order on that thread, but the end of a DrawFrame slice is not the moment pixels appear on screen: GPU work, buffer consumption, composition, and presentation still matter. A StartingWindow may appear during startup; this CPU slice alone does not establish when it disappears.

Version note (reviewed 2026-10-13): This preserves the Android 5.0 workflow and uses AOSP android-5.0.0_r1 as its source baseline. The original screenshots include device-side instrumentation, so event names need not match AOSP exactly. Incomplete excerpts below have been filled in and aligned with this tag. The old OpenGLRenderer, DisplayListRenderer, and EGL details are historical; the final section covers Android 16 counterparts and FrameTimeline from Android 12. The scope is hardware-accelerated View rendering, not every custom Surface renderer.

1. syncFrameState

syncFrameState prepares frame state on RenderThread: it processes layer updates, synchronizes the node tree, prepares textures, and advances animations.

The UI thread and RenderThread use staged rendering state. This does not copy a complete Java View tree into a second tree: Java RenderNode holds a native node through mNativeRenderNode, and that native node contains both mStagingProperties / mProperties and mStagingDisplayListData / mDisplayListData.

prepareTree pushes staging state into the rendering state in MODE_FULL: dirty properties are updated, and display-list data can be transferred by pointer rather than deeply copied every frame. canUnblockUiThread comes from info.prepareTextures; it determines whether the UI thread may be released early, not whether synchronization or GPU rendering has universally “succeeded.” For example, this version’s prepareSubTree disables the flag when ownedBitmapResources are present, so false alone does not prove that the texture cache ran out of space.

2.4 swapBuffers

CanvasContext::swapBuffers() calls EglManager::swapBuffers(), which invokes eglSwapBuffers(mEglDisplay, surface) and handles errors such as an invalid surface. The consumer still needs to acquire the buffer, and SurfaceFlinger/HWC must compose and present it. Buffer handoff also involves synchronization fences: returning from swap is neither proof of GPU completion nor proof that the pixels are already on screen.

Summary

Since I’m a bit lazy and my summarizing skills don’t quite match Luo’s, I’ll follow his outline here, with the technical boundaries clarified against AOSP 5.0:

  1. The UI thread records View drawing state, submits a DrawFrameTask, and waits. RenderThread synchronizes native RenderNode staging state and handles textures, layers, and animations.
  2. When info.prepareTextures permits early release, the UI thread is signaled before the drawing branch; otherwise it is signaled afterward. That branch may also skip drawing. Neither path is a notification of GPU completion or final presentation.
  3. The default deferred path processes offscreen layers that need updates and renders the window into a graphics buffer obtained through the Surface/BufferQueue producer interface. The buffer is submitted to its consumer; for this application window, SurfaceFlinger/HWC then compose and present the result.

Step 2 enables overlap: while RenderThread processes the current frame, the UI thread may begin preparing the next. The threads still have synchronization and resource dependencies, so early unblocking cannot guarantee that the next frame meets its deadline.

In the Android 4.x View/HWUI path discussed here, display-list recording and playback were mainly CPU work on the UI thread, rather than split across this RenderThread. The UI thread had to finish its current drawing call before handling subsequent work. GPU and SurfaceFlinger work could still be asynchronous; the whole graphics system did not run on the Main Thread alone. The historical trace below illustrates the UI-side work:

RenderThread queuing, GPU backlog, and BufferQueue backpressure can still affect later frames.

2026 Update: Following the Pipeline Today

  • Android 16 / AOSP android-16.0.0_r1: DrawFrameTask still posts work, synchronizes state, and conditionally releases the UI thread. Queue interfaces, frame metadata, and trace names have changed. This tag emits DrawFrames <vsyncId> and carries deadline and interval information; the 5.0 signatures and a fixed frame budget are not current contracts.
  • Rendering backends: CanvasContext dispatches through IRenderPipeline to SkiaOpenGLPipeline or SkiaVulkanPipeline, depending on configuration. Do not assume every device uses GLES. Even an internal method named swapBuffers in the Vulkan pipeline is not eglSwapBuffers. The old OpenGLRenderer/DeferredDisplayList analysis above remains historical.
  • Android 12 / API 31 onward: Perfetto FrameTimeline provides Expected/Actual tracks, jank types, and app-to-SurfaceFlinger frame relationships. An app Actual slice ends at the later of GPU completion and buffer posting, which still differs from final presentation; follow the corresponding SurfaceFlinger/DisplayFrame to inspect the display outcome. If those tracks were not captured, a DrawFrame CPU slice alone cannot establish full frame latency or a dropped-frame count.

The original sequence is still a useful way to investigate, provided the questions remain separate: is the UI thread recording display lists or waiting for synchronization? Is RenderThread waiting to be scheduled, preparing textures/drawing, or waiting for a buffer? Have the GPU and display stages completed their work? This identifies the stage to optimize instead of attributing every long slice to onDraw().
