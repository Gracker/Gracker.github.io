正文

这篇 Input 文章可与 Perfetto 5：Choreographer 渲染流程、Perfetto 7：MainThread 和 RenderThread 一起读。排查时先定位事件进入系统、选择目标、写入 InputChannel、App 接收与处理、完成确认，再关联需要更新的帧和实际呈现。输入确认完成与画面显示完成是两条不同的边界。

Choreographer 篇已经区分了 Looper 消息分发与 native FD 回调。输入通道可读时也会通过 native Looper 进入 Java，因此不能把所有输入都理解成一个普通 Handler Message。本文主要讨论触摸 MotionEvent；按键 KeyEvent 的焦点选择、策略拦截与回退处理另有分支，Home/Back 也不能概括成必定交给当前 App 的普通按键。

典型触摸路径是：

  1. 触摸控制器按设备策略采样，经驱动形成内核输入事件；硬件采样、报告、InputReader 被调度的频率不必一一相同。
  2. EventHub 读取事件，InputReader 按设备/mapper 处理坐标、动作等，再通知后续分发链。
  3. InputDispatcher 根据事件类型、显示、窗口触摸区域、手势状态和策略选择目标连接；不是向所有“注册输入的 App”广播。
  4. App 接收后按适用路径立即或批量处理。UI 状态变化可能促成下一帧更新，请求会合并，不是每个输入都对应一个新帧。

时间轴从左到右，但比较的是已对时的事件/区间边界，跨线程的先后关系并不能单独证明因果。仍要对照 channel、序号、调用栈和调度信息。我希望大家在看基于 Systrace 的源码流程分析之后，脑子里有一个图形化的、立体的流程图，你跟的代码走到哪一步了，在图形里也能快速定位。

Input in Systrace

以下保留桌面单指滑动案例：通常从 DOWN 开始，经过若干 MOVE，以 UP 或 CANCEL 结束；多指还会有 POINTER_DOWN/POINTER_UP，不能把所有手势都固定为 Down-Move-Up。

原图中的 InputReader 和 InputDispatcher 是 system_server 的 native 线程。其余标记需要分别理解：

  1. InputReader 处理 EventHub 读入的数据，触摸路径使用 Motion 通知，按键使用 Key 通知。
  2. InputDispatcher 选择目标并维护分发状态。队列和名称属于该版本实现，厂商及新系统埋点可能不同。
  3. oq: 是某个 Connection 的 outbound 队列计数，连接可能对应窗口或 monitor，一个 App 可以有多个窗口/连接。
  4. wq: 记录已成功发布、仍待 finished 协议处理的条目；不是“只有业务返回 true 才算成功”。
  5. aq:pending 是 ViewRootImpl 待取出的输入队列计数，不等于全部正在处理/等待确认的输入数。
  6. deliverInputEvent 是 App 分发处理的跟踪区间，不是内核唤醒时刻；需要另看 sched_wakeup/sched_switch。
  7. 旧查看器的 Input Response / Rendering Response 是交互分析分组，不是通用硬件触摸到屏幕的直接测量。
  8. 手指抬起后，满足手势/速度条件时可以继续 fling；并非每次 UP 必触发 fling。

下面先看 DOWN。MOVE 的批处理、历史采样和重采样差异会影响时序，不能当作可忽略的小差异。

InputDown 事件在 App 的工作流

普通 DOWN 通常不走 MOVE 的批量等待路径，可以在输入通道可读后进入分发；这不取决于“系统有没有 VSync”。主线程忙、可运行但未获 CPU 或其他输入阶段等待时，仍可能延后。

App 的 Pending 队列

原图说明“处理完变 0”过于简化。Android 9 ViewRootImpl.doProcessInputEvents()在取出一个 QueuedInputEvent 后，先减小 pending 计数，再调用 deliverInputEvent()。所以计数归零时，该事件可能正在处理、等待异步阶段或尚未回传 finished；主线程阻塞在 native 通道读取之前时，这个 Java 队列也不一定先堆起来。

主线程处理 Input 事件

图中可见 native poll → InputEventReceiver → ViewRootImpl 输入阶段 → DecorView/Activity/View 分发。这是该事件的路径，不表示所有类型都经过同一组 stage，也不能从 MethodTrace 插桩时长直接推正常运行成本。

关键知识点和流程

正常路径可以概括为：Reader 通知 Dispatcher → 事件进入 inbound/pending → 选择目标并进入各连接 outbound → 发布成功后进入 wait → App 处理 → 通过同一输入通道返回 finished 序号和 handled 状态 → Dispatcher 处理确认并清理或按策略继续。

数据和确认主要走 InputChannel socket 协议，不是每个触摸都用 Binder 回调 Java InputManagerService。handled=false 也可以是一次合法处理结果，finished 不等于 UI 已经重绘。异常连接清理也可能让队列减少，因此要结合连接状态读计数。

InputReader

以 AOSP android-9.0.0_r1 为源码参照：EventHub 监听输入设备 FD 及设备变化；每轮读出的 RawEvent 由 mapper 处理。该版本缓冲数组容量为 256，指 RawEvent 容量，不是 256 个完整手势、采样率或所有版本固定常量。触摸形成 NotifyMotionArgs/MotionEntry 路径，Key 才是 NotifyKeyArgs/KeyEntry。

InputDispatcher

Reader 的 listener 通知可能使 Dispatcher 入队并唤醒，但策略过滤和其他唤醒来源也存在。下图的具体 Runnable 选区显示唤醒来自 TID 25669（图中 Reader），不能将此推广到每一次 Dispatcher 唤醒：

Android 9 Dispatcher分别处理 Key 与 Motion。Key 常围绕焦点窗口和按键策略；触摸还要命中测试、维护手势目标、处理 split/cancel 等情况。下面旧图中的 dispatchKeyLocked、findFocusedWindowTargetsLocked、publishKeyEvent 明确是 Key 分支，不能直接替代本文的触摸路径。

deliveryTime 在这版 startDispatchCycleLocked() 尝试发布条目时设置；不是硬件采样时刻，也不能不顾后续等待把最初进入 dispatchOnce 的时间当成所有事件统一的投递时刻。WOULD_BLOCK 等背压/错误需要单独处理，不能先假定已经进入 wait。策略命令还可能通过命令队列在合适的锁边界执行。

InboundQueue

notifyKey 与 notifyMotion 经相应检查后可封装并入队。取出条目成为 mPendingEvent 后，iq 计数可以减少，但该事件仍可能等待目标或继续分发，所以 iq=0 不代表系统输入工作全做完。

OutboundQueue

这是每个 Connection 待发布的条目队列；同一输入可能按规则有多个目标，也可能被过滤。一个进程有多个窗口，monitor 又有独立用途，不能把 Connection 简化成“一 App 一个队列”。下图选中的是 StatusBar 连接，值为 1，不是 Launcher 的所有输入数。

WaitQueue

发布成功后，Dispatcher 将条目从 outbound 移入 wait。App 的 finishInputEvent(event, handled) 经 native InputConsumer 发送确认；Dispatcher 按连接和序号处理后再移除相应条目，必要时还涉及回退策略。详见 InputTransport 和 InputEventReceiver。

wait 长时间增长是调查线索，原因可能是 App 未获调度、处理耗时、MOVE 批量等待、确认传送/处理或连接问题。长度不等于时长，也不是 ANR 判据。 下图来自 sample.tencent.mat... 的另一份列表案例，选区 32.276 ms，一个计数值为 8；不能把它当成桌面那份 Trace 或八个事件都尚未进入 App。

整体逻辑

原图来自 Gityuan 博客，包含 KeyboardInputMapper/notifyKey；它是历史阅读线索，不是 Android 16 所有触摸输入的精确调用链。现代源码仍需按自己版本跟踪。

Input 刷新与 Vsync

那么，是不是屏幕采样率越高越好？先区分触摸采样率、输入报告/调度频率、显示刷新率和 App 实际帧率。120Hz 的周期约 8.33ms，160Hz 为 6.25ms；原文的 120Hz“8ms”只是粗略近似，且这些不是今天所有设备的固定规格。

我当时在图中把设备标为 160Hz，但 Reader 工作间隔还受报告批次和调度影响。WaitQueue 短暂积累也不等于 App 永远不消费。批量 MOVE 可在 Choreographer INPUT 阶段按帧时间消费，DOWN/UP 等不能用同一规则概括。

多个采样点不等于只留最新、其余全丢。 MotionEvent 的 batching 合同允许一个 ACTION_MOVE 携带多个历史样本；应用可先读 getHistoricalX/Y() 和历史时间，再读当前样本。Android 9 InputConsumer.consumeBatch/consumeSamples()会选取合适时间范围的样本、加入 MotionEvent history，并维护对应确认序号链；启用重采样时还会根据帧时间和样本估计位置。

因此不能从 60Hz 显示推出“120Hz 触摸足够”，也不能从 90Hz 推出“必须 180Hz”。更高采样可能减少部分输入等待或提供更细数据，也可能增加功耗/处理负担；2/3 个样本交替成批本身并不证明 UI 必抖。要结合事件时间、历史点/重采样、实际呈现与端到端延迟做对照，不要求采样率必须恰好为刷新率两倍。

Input Reader 状态

Raw 与 Cooked 坐标分开：例中 raw (660, 1338) 转为 cooked (659.389, 1337.401)，反映映射/校准后的结果。PhysicalWidth 这里明确是 px，不是毫米；unknown range 不等于零范围。External Stylus 的 9223372036854775807 是该旧状态中的无有效截止时间等哨兵，不能当成真实输入时刻。

InputDispatcher 状态

重点区分 FocusedApplication 与 FocusedWindow、各显示的触摸目标、窗口列表、monitor 通道与连接。MonitoringChannels 不是每个 Window 的普通输入通道清单；下面也只是摘录。DispatchFrozen 是分发状态，不是后来的 cached-app freezer 状态。

这份输出有 3 个 MOVE 等待项，age 为从事件时间到 dump 时刻的差，wait 为从该条目的 deliveryTime 到 dump 时刻的差；都不是画面响应总耗时。5000.000ms 是这里报告的分发超时设置，不是所有设备、所有 ANR 类型的统一规则。官方输入分发 ANR 说明给出的默认值为 5 秒，也讨论无焦点窗口等场景；判断时需关联超时日志、目标窗口和阻塞原因，不能把 3 个待确认事件直接叫 ANR。

新版本中怎么继续查

AOSP Android 16 的 InputDispatcher已有 Perfetto 输入事件追踪后端，但该标签明确要求 userdebug/eng 构建并开启相应 feature flag。不能承诺普通 user 设备只开一个开关就有 android.input.inputevent 数据。

支持并采到相关 ATrace 时，Perfetto 的 android.input 模块可进一步拆分发送、接收、处理和 ACK 往返；结构化 android.input.inputevent 则有独立数据来源和字段。两者不能混为一套必定存在的数据。输入到帧的关联还可能缺失或属于推测，ACK 往返不是物理触摸到屏幕的完整时间；缺数据记为不可用，不能当零延迟。
