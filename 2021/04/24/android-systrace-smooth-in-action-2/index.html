不同的人对流畅性(卡顿掉帧)有不同的理解，对卡顿阈值也有不同的感知，所以有必要在开始这个系列文章之前，先把涉及到的内容说清楚，防止出现不同的理解，也方便大家带着问题去看这几篇问题，下面是一些基本的说明

  1. 对手机用户来说，卡顿包含了很多场景，比如在 滑动列表的时候掉帧、应用启动白屏过长、点击电源键亮屏慢、界面操作没有反应然后闪退、点击图标没有响应、窗口动画不连贯、滑动不跟手、重启手机进入桌面卡顿 等场景，这些场景跟我们开发人员所理解的卡顿还有点不一样，开发人员会更加细分去分析这些问题，这是开发人员和用户之间的一个认知差异，这一点在处理用户(或者测试人员)的问题反馈的时候尤其需要注意
  2. 对开发人员来说，可以先按 流畅度（画面节奏不连贯）、响应速度（操作后等待过长）和 稳定性（崩溃、ANR 等）整理反馈。这些现象可能重叠；点击没有响应不一定是稳定性故障，需要结合输入、应用状态和日志进一步分类。
  3. 技术上，这三类问题并不是同一个 Message 超时机制的不同阈值。主线程长任务会同时影响输入和绘制，但 GPU、SurfaceFlinger、显示链路、线程调度或远端服务也可能造成延迟。ANR 由具体输入/组件等超时规则触发，崩溃则另有异常或信号等原因；不能仅凭一次长 Message 判定它们。
  4. 流畅性这个系列主要是分析流畅度相关的问题，响应速度和稳定性会有专门的文章介绍，在理解了流畅性相关的内容之后，再去分析响应速度和稳定性问题会事半功倍
  5. 流畅性这个系列主要是讲如何使用 Systrace (Perfetto) 工具去分析，之所以 Systrace 为切入点，是因为影响流畅度的因素很多，有 App 自身的原因、也有系统的原因。而 Systrace(Perfetto) 工具可以从一个整机运行的角度来展示问题发生的过程，方便我们去初步定位问题

历史案例说明（2026-10-14 核查）：原案例使用小米 10 Pro、MIUI 12.5.3 和文中所列桌面版本，不能代表当前 MIUI/HyperOS。保留截图与当年的体验记录，技术结论按附件重新收窄，并补充事件级核对。前面的 Bilibili 示意图是另一案例。旧 Chrome/Traceview 操作入口已更新；Android 12（API 31）及以上的新采集可结合 FrameTimeline，旧附件不包含这类数据。

Systrace 分析卡顿问题的套路

使用 Systrace / Perfetto 分析卡顿，可以按下面的顺序收集证据：

  1. 复现并记录条件：保留操作步骤、复现概率、系统/应用版本、显示模式、温度和电量状态，再采集 trace。对比其他设备时尽量保持内容、输入和缓存等条件一致。
  2. 用支持该格式的工具打开：优先尝试 Perfetto UI 的 Open trace file。旧 HTML 的内嵌查看器、chrome://tracing 和 “Open With Legacy UI” 不是跨浏览器版本的稳定入口；无法导入时，保留原文件并使用支持相应旧格式的查看器。本文未重新验证旧内嵌 UI 的兼容性。
  3. 建立上下文：先定位操作区间、目标进程和窗口/Layer。确认是否预期持续更新，不能把静态画面或主动限帧当作掉帧。
  4. 检查整机线索：结合调度、CPU 频率及限制、温控、内存压力和 I/O 事件。低频不能单独证明温控；CPU 轨道很密不等于持续高利用率；lmkd 活动、HeapTaskDaemon 或 Block I/O 也不能单独证明低内存。缺少事件时保留未知。
  5. 定位应用工作：检查 UI Thread、RenderThread 和可用 GPU 数据，并把墙钟时长拆成 Running、Runnable 和阻塞。下面 Bilibili 图选区为约 110.05 ms，有多次 inflate 和绘制，值得检查；截图不足以指定应优化哪个 View，更不代表 MIUI 这次问题。

下面另一选区是 23.526 ms。函数色块颜色不等于卡顿等级，旧 Frames 行的 F 标记也只是查看器按其规则生成的线索；不能把绿/黄/红与真实呈现结果一一对应。

60/90/120 fps 的目标间隔约为 16.67/11.11/8.33 ms。这些周期用于理解节奏，实际帧期限还受调度、流水和显示模式影响。

  1. 关联合成与呈现：下两图有 SurfaceFlinger 工作空档和 BufferTX 计数变化，提示应继续追踪目标窗口。没有合成工作可以是没有更新；有合成工作也可能只更新其他 Layer。计数语义须按该系统实现核对，不能只由空白或归零确认最终掉帧。

  1. 沿依赖查原因并验证：长 Runnable 是等 CPU，长 Binder 调用还要跟到远端执行/等待；不能一概写成应用执行慢。Android 12+ 有相应数据时，用 FrameTimeline 关联预期/实际呈现，再回查 CPU/GPU 和依赖。提出修改后，在相同条件下重复采集，比较帧期限、延迟和副作用，才能判定优化有效。

App 掉帧的原因非常多，有 APP 本身的问题，有系统原因导致卡顿的，也有硬件层的、整机卡的，这个可以参考下面四篇文章，不同的卡顿原因在 Systrace 中会有不同的表现

使用 Systrace 分析卡顿问题的案例

Systrace / Perfetto 能展示进程、线程和系统之间的时序关系，帮助形成归因假设。应用与系统的影响可能叠加，不一定能二选一；trace 中没有源码级栈或硬件数据时，应保留相应限制。

继续深入时，可以结合源码、Android Studio CPU Profiler 或支持目标版本的采样/自定义 trace。原文提到的 Traceview 已弃用，官方建议 Android Studio 3.2 起改用 CPU Profiler。方法插桩会改变执行开销，不能把不同采集方式的耗时直接当作优化前后差值。

所以本文更多地是讲如何发现和分析卡顿问题，至于如何解决，就需要后续自己寻找合适的解决方案了，比如对比竞品的 Systrace 表现、优化代码逻辑、优化系统调度、优化布局等

案例说明

个人在使用小米 10 Pro 的时候，在桌面滑动这个最常用的场景里面，总会有一种卡顿的感觉，10 Pro 支持 90Hz，本文场景以 90 fps 为目标，但不代表每帧实际都达到 90 fps，所以一旦出现卡顿，就会有很明显的感觉(个人对这个也比较敏感)。之前没怎么关注，在升级 12.5 之后，这个问题还是没有解决，所以我想看看到底是怎么回事

抓了 Systrace 之后分析发现，这个卡顿场景是一个非常好的案例，所以把这个例子拿出来作为流畅度的一个实战分享

建议大家下载附件中的 Systrace，对照文章食用最佳

  1. 鉴于卡顿问题的影响因素比较多，所以在开始之前，我把本次分析所涉及的硬件、软件版本沟通清楚，如果后续此场景有优化，此文章也不会进行修改，以文章附件中的 Systrace 为准
  2. 硬件：小米 10 Pro
  3. 软件：MIUI 12.5.3 稳定版
  4. 小米桌面版本：RELEASE-4.21.11.2922-03151646

这些是我当时记录的测试条件。附件没有完整 build fingerprint 或 APK 身份信息，不能独立复核精确固件/桌面版本，也不能由 MIUI 版本号直接推断底层 Android 版本。小米官方 FAQ 可确认机型支持 90 Hz 和 Snapdragon 865；当前设备表现需重新测试。

因此图里的“全是绿色，一直 Running”过于绝对。主要时间确实在执行，但仍有切出 CPU 的区间。任务工作量、运行核心/频率、缓存和内存访问、驱动工作等都可能影响这一段；先保留候选原因。

回到渲染线程

这个 DrawFrame 的墙钟时长为 16.519 ms，前一个为 5.974 ms，本段约为前一段的 2.77 倍。但“桌面滑动看起来简单”“已经松手”不能证明每帧执行相同工作；图中还有动态壁纸，Launcher 内部绘制和驱动状态也未完全展开。

到底是这一帧做了更多工作，还是同样的工作跑得慢了？长片段里 prepareTree 约 4.165 ms，flush commands 约 4.656 ms，它们是墙钟区间，不能再与包含它们的父区间相加。要区分更多工作与相同工作跑得慢，还需要调用栈、绘制内容/命令量、缓存和受控对比。

分析 CPU 区域的信息

查看 CPU （Kernel 区域，这部分的基础知识可以查看 Android Systrace 基础知识 - CPU Info 解读 和 Android Systrace 基础知识 – 分析 Systrace 预备知识）这两篇文章

本段附件能确认 RenderThread 运行在 CPU 2 和 CPU 0。机型资料 说明 Snapdragon 865 为 4 个小核、3 个大核、1 个超大核；但 Linux CPU 编号与核心类型的对应仍需设备 topology/capacity 数据，不能从编号大小推广到其他机型。下面沿用我当时对本机 CPU 0–3 为小核的映射，单独保留这个前提。

图中频率事件值为 1,804,800 kHz，即 1.8048 GHz；附件里 CPU 0/2 在目标片段开始前最后一次 frequency 事件也为该值，片段内未记录新的频率变化。它是所记录的频率状态，不是对每个瞬间硬件执行速率或 CPU 利用率的测量；“最高频率”还需结合本机频率表和限制确认。

图中的 Clock Frequency Limits 表示频率约束变化。所选最小值 1,075,200 kHz、最大值 1,804,800 kHz 不能直接证明所有 CPU Boost 已结束；Power HAL、cpuset、利用率约束及厂商策略可能没有完整记录。应把“Boost 结束”保留为原图的推断。

我当时的猜想是：这些较长帧主要跑在小核上，可用 CPU 能力不足以赶上目标节奏。附件支持“长片段与 CPU 0/2 驻留有关联”，但不能仅靠相关性锁定调度器根因。

复核还发现，紧接目标帧的 DrawFrame 为 9.170 ms，在 CPU 0 上 Running 3.890 ms、CPU 5 上 4.554 ms，不是立刻全程回到大核；附件另有 3.843 ms 和 5.809 ms 的短 DrawFrame，Running 均在 CPU 0。这里的“短”只指 RenderThread 区间，不等于已证实按时呈现。它们足以说明不能用“正常帧都不跑小核”概括整份 trace，也不能用一帧小核跑得快就否定所有容量问题。

验证这个假设，需要比较同类工作量、频率、核心驻留、调度等待和温控条件，再用支持该平台的受控实验改变策略，观察帧期限与延迟是否改善。关于频率与调度能力的区别，可参考 Linux CPUFreq 和 Capacity Aware Scheduling；这些通用说明不代表 MIUI 的完整内核实现。

到这里，可以确认的是：RenderThread 主要在我当时认定的小核上执行的长片段，是一个有证据的优化调查方向；具体调度策略是否为根因，尚缺控制变量验证。

厂商可以在有对应源码、权限和回归条件时检查迁移决策、频率约束与功耗策略，评估帧延迟、温升、续航及其他任务公平性。应用开发者先核查自己的绘制工作和可用性能接口；不能把“调迁移阈值”作为普通应用可直接执行的通用修复。竞品 trace 只能帮助提出假设，无法从轨道形状直接推知其私有调度算法。

Triple Buffer 在这个场景发挥了什么作用？

Triple Buffer 能增加生产与消费重叠、缓冲部分短时波动，但不能缩短 GPU 工作或消除持续瓶颈，且可能增加内存和排队延迟。队列里的旧内容也不一定应该留到下个周期显示。

下面这张图来自 Matrix 示例（SurfaceFlinger PID 510），不是本次 MIUI 附件（PID 990）。图内“已经合成但还未消费”等表述不准确，应理解为已提交、仍待消费者选择；计数也不是已完成渲染的所有 Buffer 数量。

28306.224466 queue 区间标记 3:618，随后计数 1
28306.234435 queue 区间标记 0:619，随后计数 2
28306.235906 acquire 区间标记 0:619，随后计数 0

这里是该厂商 trace 的标签；按槽位/连续编号解释，事件支持 618 未被 acquire、619 被选中。完整厂商源码未提供，仍不能仅凭这些标记断定具体分支及每张图的最终呈现。

作为机制参考，AOSP android-11.0.0_r1 的 BufferQueueConsumer::acquireBuffer 可按期望呈现时间、Buffer 时间戳和 frame number 等条件跳过旧项，再 acquire 后续项，最后记录队列长度。因此 2→0 可以是一次 acquire 过程中“跳过旧项并取走新项”的结果；这不是它必然有 bug 的证据。

队列深度减少后，后续生产波动可能更容易暴露，但不能反推“只要保留旧帧，这次一定不卡”。旧帧的期望显示时间、内容位置和输入时效可能已经不合适；保留它也可能增加延迟。需要在同等条件下比较显示节奏与响应时间。

下图保留原分析标注：它展示又一次长 RenderThread 片段及队列/SurfaceFlinger 空档，但图内“前面不丢弃就不会掉帧”是未经实验验证的反事实假设。

滚动位置也不是必然预先算好、以后每帧固定加一个步长。常见动画按帧时间/已过时间求位置；漏掉一个显示时机后，下一张可能直接反映更新的时间点。保留旧位置可以减少某次位移，但也可能把画面拖在输入之后。应同时观察位置、时间和实际呈现，不能只凭 Buffer 数量判定 Triple Buffer 有副作用。

用一个固定显示间隔的示意说明视觉差异，offset 表示某元素的水平位置，数字不是附件测量值：

  1. 规则推进：2→4→6→8→10→12。
  2. 旧内容重复后，较旧位置仍依次显示：2→4→6→6→8→10→12。序列更长，可能积累延迟，不是“更流畅”的保证。
  3. 重复后追上较新位置：2→4→6→6→10→12。会出现更大的相邻位移，但保留了较新的状态。

哪种策略更合适，取决于动画时间语义、目标呈现时刻和延迟要求。这个例子解释“停顿后跳跃”的感知可能性，不证明 MIUI 附件实际显示过这些位置，也不能独立给出关闭丢弃策略的修复建议。
