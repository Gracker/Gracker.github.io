不同的人对流畅性(卡顿掉帧)有不同的理解，对卡顿阈值也有不同的感知，所以有必要在开始这个系列文章之前，先把涉及到的内容说清楚，防止出现不同的理解，也方便大家带着问题去看这几篇问题，下面是一些基本的说明

  1. 对手机用户来说，卡顿包含了很多场景，比如在 滑动列表的时候掉帧、应用启动白屏过长、点击电源键亮屏慢、界面操作没有反应然后闪退、点击图标没有响应、窗口动画不连贯、滑动不跟手、重启手机进入桌面卡顿 等场景，这些场景跟我们开发人员所理解的卡顿还有点不一样，开发人员会更加细分去分析这些问题，这是开发人员和用户之间的一个认知差异，这一点在处理用户(或者测试人员)的问题反馈的时候尤其需要注意
  2. 对开发人员来说，可以先按 流畅度（画面节奏不连贯）、响应速度（操作后等待过长）和 稳定性（崩溃、ANR 等）整理反馈。这些现象可能重叠；点击没有响应不一定是稳定性故障，需要结合输入、应用状态和日志进一步分类。
  3. 技术上，这三类问题并不是同一个 Message 超时机制的不同阈值。主线程长任务会同时影响输入和绘制，但 GPU、SurfaceFlinger、显示链路、线程调度或远端服务也可能造成延迟。ANR 由具体输入/组件等超时规则触发，崩溃则另有异常或信号等原因；不能仅凭一次长 Message 判定它们。
  4. 流畅性这个系列主要是分析流畅度相关的问题，响应速度和稳定性会有专门的文章介绍，在理解了流畅性相关的内容之后，再去分析响应速度和稳定性问题会事半功倍
  5. 流畅性这个系列主要是讲如何使用 Systrace (Perfetto) 工具去分析，之所以 Systrace 为切入点，是因为影响流畅度的因素很多，有 App 自身的原因、也有系统的原因。而 Systrace(Perfetto) 工具可以从一个整机运行的角度来展示问题发生的过程，方便我们去初步定位问题

版本说明（2026-10-14 核查）：本文是 2021 年 MIUI 案例的问答补充，保留原图。下文颜色规则核对的是附件自带的旧查看器，不是所有 Systrace/Perfetto 版本的统一合同；HWUI 同步与统计以 AOSP android-11.0.0_r1 为参考。旧截图的完整固件/查看器版本未记录。Android 12（API 31）及以上的新采集，可结合 FrameTimeline 和支持该版本的基准指标，不能把旧圆点颜色当成现代呈现结果。

Systrace (Perfetto) 工具的基本使用如果还不是很熟悉，那么需要优先去补一下上面列出的 Systrace 基础知识系列，本文假设你已经熟悉 Systrace(Perfetto)的使用了

Systrace 的 Frame 颜色是什么意思？

这里说的是旧查看器 Frames 行中的 F 圆点，不是函数色块。点击圆点会高亮查看器关联的 UI/RenderThread 区间，关联结果受 trace 内容和查看器实现影响。

原文按当前屏幕“一个/两个 Vsync 周期”解释颜色并不准确。附件 xiaomi_launcher.html 自带的 AndroidAuditor 使用固定阈值 16.67 ms（常量 EXPECTED_FRAME_TIME_MS），按顺序判断：

圆点类别 附件内嵌查看器的条件
红（TERRIBLE） frame.totalDuration > 33.34 ms
黄（BAD） 未满足红色条件，且满足以下任一项：totalDuration > 16.67 ms；或存在估计 deadline 且 frame.end 晚于它
绿（GOOD） 上述条件均未满足

totalDuration 是查看器构造的线程时间区间之和，不是单个 doFrame 的时长，也不是 Running CPU 时间。RenderThread 结束还可能取 queueBuffer/交换缓冲区片段结束，不能当作 GPU 完成或实际呈现。deadline 来自旧查看器对 Vsync 的估计，不是直接测得的物理显示时刻；因此不能在 90 Hz 下把红色阈值改读成约 22.22 ms。

绿帧

绿帧表示没有触发这份查看器的 BAD/TERRIBLE 规则，不保证一个实际 Vsync 周期内完成，更不能保证用户看到的画面没有卡顿。原图箭头说明按上述规则修正。

黄帧

黄帧可能因为累计区间超过固定 16.67 ms，也可能只是错过查看器估计的 deadline。不能由黄色反推“耗时一定介于本机 1–2 个 Vsync 周期”，它只是继续检查的线索。

红帧

在这份内嵌查看器中，红帧表示构造出的 totalDuration 大于 33.34 ms。它提示较长的应用侧工作/等待区间，仍需关联合成和呈现；没有红色也不代表满足 90/120 Hz 的帧期限。

没有红帧就没有掉帧？

不一定。需要把应用提交、GPU 完成、SurfaceFlinger 选图/合成和显示呈现关联起来，不是“只看 SurfaceFlinger，不看 App”。SurfaceFlinger 有工作或没有工作，都不能单独判定目标窗口是否按时更新。可先看 Triple Buffer 的边界说明；Android 12+ 有对应数据时结合 FrameTimeline，并区分应用完成期限与实际呈现。

出现黄帧但是不掉帧的情况

某段应用工作较长时，之前已提交且及时就绪的内容有可能维持显示更新；但这取决于队列和呈现时序，不是开启 Triple Buffer 就能保证按时呈现。多排队也可能提高输入延迟，Buffer 数量并不固定由刷新率决定。这里的“没有掉帧”需要呈现证据，不能仅靠黄色或 SurfaceFlinger 连续工作确认。

出现黄帧且掉帧的情况

下图标出了连续两个黄点，量尺 28.432 ms 跨越所选区间，不是每一帧各耗时 28.432 ms。原文称“第一个卡、第二个不卡”，但附件没有完整的逐帧呈现关联，不能仅凭这张图作这个精确分类。可确认的是第一段 RenderThread 较长，后一帧主线程又发生等待；两段存在依赖，详见下节及 实战 2 的事件核对。

主线程为何要等待渲染线程？

UI 与 RenderThread 之间需要交接本帧状态，RenderThread 又是串行处理绘制任务的线程。若前一项工作尚未结束，后一个同步任务可能排队，使主线程等待。Sleep 表示线程在等待某个事件或条件，不能仅凭状态确认等待对象；还要结合调用区间、唤醒者和源码。

AOSP android-11.0.0_r1 的 DrawFrameTask 中，postAndWait() 把任务投到 RenderThread 后等条件变量。run() 先执行 syncFrameState()，若 canUnblockUiThread 为 true 就提前唤醒 UI；否则在后面的 draw/等待分支之后才唤醒。因此，“sync 结束后总会立即 unblock”少了条件，unblock 也不代表 GPU 或屏幕完成。

本附件对应区间如下（时间为 trace 秒）：

事件 起止 墙钟时长
前一个 RT DrawFrame 28306.209230 → 28306.225749 16.519 ms
后一帧 UI doFrame 28306.217610 → 28306.229642 12.032 ms
后一个 RT DrawFrame 28306.225780 → 28306.234950 9.170 ms
后一个 RT syncFrameState 28306.226040 → 28306.229560 3.520 ms

这组时序符合“RT 前项工作延后下一次状态同步、UI 随后结束”的解释，但没有完整等待栈时，不能把 doFrame 的全部 12.032 ms 都记成等待，也不能仅靠同一时间附近的事件证明每个唤醒的因果关系。更多背景见 MainThread 与 RenderThread。

为什么一直滑动不松手，就不会卡？

我当时在这个版本上的感觉是，按住时较流畅、松手后更容易察觉卡顿。这不是按住就永远不会卡的规则。输入阶段的性能策略、速度和绘制工作都可能不同。

原图展示了一段频率限制，所选 CPU 4 policy 的上/下限约为 2,419,200 / 1,056,000 kHz。它不能单独证明所有 Boost 持续有效、RenderThread 只在 CPU 4–6 上执行或画面没有卡顿。

复核 xiaomi_launcher_scroll_all_the_time.html 的 PID 3553/TID 3690，共提取到 110 个完整 DrawFrame；其中 19 个区间有 CPU 0–2 上的 Running 记录。完整附件包含手势起止等阶段，不能凭文件名把每一帧都归为持续按住；但“这份 trace 的 RT 从不跑小核”已不成立。精确比较还需先用输入事件划定阶段，再核对核心映射、工作量、帧期限和呈现。

我当时记下的 120 ms Boost timeout 没有对应 PerfLock 请求、配置或到期事件证据，无法从这张频率限制图直接反算，也不是 Android 通用常量。保留为当年的待核对参数；持续输入可能续期请求，但需要厂商实现和事件记录才能确认。

如果不卡，怎么衡量性能好坏？

如果这个场景不卡，那么我们怎么衡量两台不同的机器在这个场景下的性能呢？

可以先用 dumpsys gfxinfo 查看目标进程的 HWUI 统计。它不是全屏所有 Layer、游戏自建渲染器或用户感知的完整评分；版本和渲染路径不同，字段与口径也可能不同。

  1. 确定目标包名、显示模式、操作距离/速度、内容、预热状态和温度。先预热，再在测量开始前 reset 一次；不需要机械执行 2–3 次 reset。
  2. 以原小米桌面包名为例（其他应用需替换），清空统计：
  1. 执行预先定义的操作，结束后及时保存输出，避免混入后续动画：
  1. 检查进程/窗口、Stats since、总帧数和输出是否实际重置、是否覆盖测试区间；空输出或缺指标不能按 0 处理。AOSP android-11.0.0_r1 的 ThreadedRenderer 识别 reset/framestats 参数，但厂商结果仍需实测。本次未连接设备执行命令。

字段应这样理解：

  • Janky frames：HWUI 按该版本规则统计的次数/比例，不是肉眼卡顿次数。AOSP 11 会比较经处理的总时长与帧间隔，并有 flag、dequeue 等处理；Frame deadline missed 是另外的分类计数，不能与总 Janky frames 等同。
  • 95th percentile：帧时长的 P95 估计，不是“95% 的值”或流畅率。该版本由直方图桶计算，精度和样本量要一起看。
  • HISTOGRAM：时长桶与次数，例如 5ms=11 是该桶中有 11 帧，不是逐帧原始序列；GPU HISTOGRAM 是另一组统计。
  • PROFILEDATA：最近保留帧的分阶段数据，不保证覆盖 reset 以来所有帧。按输出列名、单位和 Flags 解读，不硬编码列号；时间戳与 duration 字段不能混用。

实现可参考 AOSP 11 JankTracker 和 ProfileData。现代重复测试可用 Macrobenchmark 的 FrameTimingMetric，其中 frameOverrunMs 在 Android 12（API 31）及以上可用；同时观察帧时长尾部、呈现节奏、输入延迟和功耗，而非只看一个平均数。

在这两份截图的 HWUI 统计中，小米的 Janky 比例和帧时长尾部更高。但总帧数、软件实现、内容/壁纸、操作时长与温控条件未完全对齐，也没有重复试验，所以不能升级为两台机器的总体性能排名。High input latency 是分类计数，69/44 不是毫秒，分类项也不应直接相加当作全部卡顿数。

GPU 数据同样不能概括成“小米全面更好”：小米 GPU P95 为 3 ms，比 OPPO 的 5 ms 低，但 P99 为 8 ms，反而更高。分位数不是同一帧的配对数据，不能用总 P95 减 GPU P95 来算 CPU 耗时；单凭这些汇总也不能排除 GPU/fence 问题。CPU 瓶颈判断需要对应帧的调度、绘制和 GPU 完成证据。

为什么录屏看不出来卡顿？

录屏与肉眼观察可能不一致，但“90 fps 录成 60 fps 就一定看不出卡顿”不成立：

  1. 采集节奏不同：90 Hz 屏幕每约 11.11 ms 刷新，60 fps 视频每约 16.67 ms 取样，短暂停顿可能被漏采或改变形态；较长停顿仍可能清楚可见。采样也可能引入新的不均匀节奏。
  2. 录屏不是拍摄屏幕发光：例如 Android MediaProjection 经虚拟显示与 Surface 输出内容，它不等于物理面板的完整扫描结果。录制/编码还可能改变系统负载；应对比开启与关闭录屏的行为。
  3. 播放链路不同：视频实际时间戳、可变帧率、播放器丢/重复帧和播放设备刷新率都会影响观察。“小米播放时自动切到 60”是我当时在设备上的观察，缺少录像文件和显示模式记录，不能当作所有手机通用行为。

需要核验时，保留原视频及帧时间戳，并与同一次 trace、显示模式和操作时间对齐。外部高速相机更接近拍到实际屏幕，但也需考虑曝光、采样率、滚动快门和时钟同步；不能仅凭一段看起来流畅的视频证明没有卡顿。
