Hardware Acceleration vs. Software Acceleration

Many people confuse hardware acceleration with Hardware Layer in Android. Enabling hardware acceleration does not automatically give every View an explicit hardware layer. Before discussing layers, let’s look at hardware acceleration.

The original background articles remain historical reading: Android Hardware Acceleration Principles and Implementation and Understanding Android Hardware Acceleration for Beginners. Check the official Android guide for API support.

For View drawing, the software path rasterizes primarily on the CPU; hardware acceleration lets HWUI use the GPU for drawing. The CPU still handles layout, records drawing commands, and submits work. Skia also has GPU backends, so its presence does not establish software rendering.

View hardware acceleration arrived in Android 3.0 (API 11) and is enabled by default for apps targeting API 14 or later. Application, Activity, and Window configuration, as well as software layers on individual Views, affect the actual path. The articles above cover the code and principles. Here I want to take another angle and walk through those differences in the traces I used at the time.

Summary

  1. Hardware acceleration changes the View drawing path; it does not remove CPU work. RenderThread visibility alone is not an app-wide acceleration test.
  2. Software Views or windows can coexist with hardware-accelerated windows. App drawing and system composition are separate stages.
  3. Hardware acceleration usually suits modern View UIs, but its benefit depends on workload, resources, and device. Two screenshots cannot establish that it is always faster.
  4. Check unsupported drawing operations against the Android API version. Where needed, use a software layer on the affected View instead of disabling acceleration for the whole app.

Software Layer vs. Hardware Layer

Software Layer and Hardware Layer refer to offscreen pixel caches for a View. They are distinct from SurfaceFlinger composition layers and from the hardware-acceleration setting for an entire window.

A View has three layer types:

  1. LAYER_TYPE_NONE: no extra explicit View pixel layer.
  2. LAYER_TYPE_SOFTWARE: draw View content through the software path into a Bitmap, including inside a hardware-accelerated window.
  3. LAYER_TYPE_HARDWARE: use a GPU offscreen layer in a hardware-accelerated View hierarchy; otherwise behave as a software layer.

LAYER_TYPE_NONE

This is the default. It does not disable hardware acceleration or require all work to start from scratch: the hardware path can still reuse drawing commands recorded in RenderNodes/display lists.

LAYER_TYPE_SOFTWARE

How is a software layer implemented? In simple terms, it caches the View content in a Bitmap. This allocation fragment comes from Android 9 View.java; its variables belong to the surrounding framework code:

Invalid content requires a redraw. An existing Bitmap of the same dimensions can be reused; redraw does not necessarily mean destruction and reallocation.

The role of Software layer:

  1. In software rendering, a layer can apply opacity, color filtering, or blending to a View and its children as a group.
  2. In hardware rendering, it can handle local operations unsupported by that version’s hardware path; caching stable content may also reduce repeated drawing.
  3. Frequent updates incur software redraws and texture-upload work in the hardware path. A software layer is not a universal animation optimization.

LAYER_TYPE_HARDWARE

A hardware layer draws View content into an offscreen GPU resource for later window drawing. FBO is a useful description for an OpenGL backend, not a universal implementation across Android versions and Skia GL/Vulkan backends. The View hierarchy must be hardware accelerated; otherwise the layer behaves as a software layer.

The role of Hardware layer:

Hardware layers can apply blending effects to a group and reduce repeated drawing of stable, complex content during translation, alpha, scale, or rotation animations. Caching also affects clipping and sampling in rotation or 3D transforms; it does not guarantee sharper or faster scaling.

ObjectAnimator cancellation also invokes the end callback. Do not let overlapping animations manage the same View’s layerType. Since API 16, withLayer() lets ViewPropertyAnimator restore the type captured at the call when the animation ends or is canceled:

Transform-only changes may reuse cached content. Text changes, child additions/removals, or other content invalidation require redraws. Reallocation depends on dimensions, resource state, and backend; “the FBO is destroyed” is not a valid general description.

Summary

  1. Software and hardware layers use different pixel-caching paths. Choose based on supported drawing operations and measured cost.
  2. Hardware layers may benefit property animations of stable, complex content; compare against the default NONE path.
  3. Restore the previous type afterward instead of retaining an unnecessary layer. Graphics resources may be released later or reused internally; process memory need not drop immediately.

Debugging Tools

Some historical systems expose “Show hardware layers updates” in developer options. Its location and availability vary by version and vendor; it is not necessarily under Accessibility.

It highlights updated layer regions, not necessarily the entire interface. For a transform animation of stable content, reuse after initialization is desirable. Continuous highlighting is a reason to inspect update sources, but dynamic content legitimately needs updates. Absence of highlighting alone proves neither caching behavior nor performance. Inspect layer drawing, dimensions, and frame timing together.

Summary

  1. Check content stability and drawing complexity before adding a hardware layer to a property animation.
  2. Do not add layers indiscriminately. Cache creation, memory use, offscreen drawing, and subsequent window drawing all have costs.
  3. Additional offscreen work for alpha depends on overlapping content and rendering paths. Not every setAlpha call or opacity animation creates the same kind of buffer.
  4. Invalidation may require redraw, but not necessarily reallocation of an entire resource. Compare NONE with layer paths when content changes frequently instead of assuming a fixed ranking.
  5. Restore the prior layerType after temporary changes. Use software layers locally where compatibility or measured benefit justifies them.

Statistics Tool: GFXInfo

Alongside Systrace, I used adb shell dumpsys gfxinfo <package> to record HWUI frame statistics. Read the old annotations in this screenshot with the following corrections:

  1. Janky frames follow the system’s frame-interval/deadline rules, not a universal 16 ms threshold. Histograms and percentiles are bucketed; the 99th percentile is not the exact maximum.
  2. High input latency measures neither CPU load nor input-callback execution time. Android 9 JankTracker has a triple-buffering/deferred-deadline branch that can record high input latency without a missed deadline. Reason counters also cannot simply be added to obtain the janky-frame total.
  3. Android 16 JankTracker retains legacy and newer deadline accounting. For current comparisons, record the OS version, refresh rate, measurement interval, and original output. gfxinfo does not cover complete input-to-display latency.
  4. These historical samples contain only 29–31 frames each, with insufficient device, OS, and reset-condition records. Cases 1 and 6 have identical logs, including the histogram; they are not confirmed independent measurements. No device rerun or replacement data was produced for this review.

Summary

The cases preserve a useful observation: caching may help stable content, while changing content needs redraws. They do not establish the original fixed performance rankings. Samples are small, Cases 1 and 6 duplicate data, and growing text changes the workload.

  1. For stable, expensive-to-draw Views, compare temporary hardware layers against NONE using frame timing, memory, and GPU cost.
  2. For dynamic content, inspect invalidation and size changes before assessing extra offscreen work. Do not assume that NONE or any layer type always wins.
  3. Repeated buildDrawingCache/drawLayer slices are investigation leads, not evidence of reallocation every frame or sufficient grounds to blame a system/vendor issue.
  4. Fix the version, refresh rate, initial state, and repetition count for current-device comparisons. On Android 12 (API 31) and later, Perfetto FrameTimeline can add expected/actual-frame evidence when that data is captured; missing data does not mean no jank.

For modern implementation details, compare Android 16 View, RenderNode, SkiaPipeline, and ViewPropertyAnimator. These source tags identify implementation boundaries; they do not imply that the historical experiment was reproduced on an Android 16 device.
