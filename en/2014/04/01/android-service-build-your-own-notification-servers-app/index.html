Updated 2026-10-13: This article records the historical approach of observing notifications through accessibility events before Android 4.3. That approach is outdated for a general notification center. Android 4.3 (API 18) introduced NotificationListenerService; section 4 adds a minimal listener for Android 7.0 (API 24) and later. The legacy examples explain the earlier implementation and do not provide a complete notification list.

1. Accessibility Service in Practice

The previous article introduced accessibility services and their basic configuration. This article follows the original implementation of a simple notification center. Android’s system notification UI displays notifications from apps and system components, such as missed calls, screenshots, weather, and news updates. Before Android 4.3, ordinary third-party apps did not have a public API to query the active notification list. Accessibility events offered a limited way to observe notifications; Android 4.3 added the dedicated NotificationListenerService.getActiveNotifications() API.

The following sections preserve the accessibility-based implementation. Layout resources came from the original project, so these excerpts are not a complete Android project. New notification centers should use the dedicated API in section 4.

2. Building a Third-Party Notification Center

2.1 Extending AccessibilityService

Following the previous article, create a service extending AccessibilityService. Check the event and payload types before forwarding the notification to this application’s interface:

The callbacks have distinct purposes:

  1. onServiceConnected() runs when the system connects the service, not when an Activity binds to it. This implementation handles only notifications, so it subscribes only to TYPE_NOTIFICATION_STATE_CHANGED.
  2. onInterrupt() asks the service to interrupt accessibility feedback; it is not a disconnection callback.
  3. onAccessibilityEvent() receives matching events. Check the type of getParcelableData() before casting it to Notification. See the AccessibilityEvent reference.

Once I had the Notification, I sent it to the Activity through a broadcast. The updated example restricts delivery to the app’s package and uses a signature permission on both sender and receiver. Package targeting limits where the broadcast goes; the receiver’s permission limits who can send data to it.

I also ran into the broadcast payload-size limit with large notifications, including screenshots and missed calls. A full Notification can contain large RemoteViews, images, or extras and trigger TransactionTooLargeException. The original post suggested keeping contentView temporarily in Application, but that doesn’t handle cross-process access, process restarts, or other large fields. For a current implementation, keep the fields you need in the app’s data layer and let the UI read snapshots instead of repeatedly broadcasting whole notification objects.

The receiver is registered in onStart() and unregistered in onStop(), so it stops receiving notifications when the Activity stops. A signature permission protects both ends. Android 13 (API 33) and later also use RECEIVER_NOT_EXPORTED. See the context-registered receiver lifecycle.

The user must enable the service in Settings → Accessibility. The manifest declaration alone does not grant access.

RemoteViews is a description of a remote layout, not a View that can be passed directly to addView(). Call apply() to obtain a View first. Notification.contentView was deprecated in API 24 and may be absent for modern template notifications, so this cannot reproduce every notification. 3. Summary and Limitations

This post took me a while to finish. It also gave me a chance to wrap up the work from that project. These were the problems left in the implementation at the time:

  1. Accessibility events do not supply the complete current notification list or reconstruct notifications that have already been dismissed.
  2. I kept the data only in memory, so it was lost when the service was killed. I tried saving whole notification objects with an object database, db4o, but couldn’t get it working. An app can persist the text, package names, timestamps, and other fields it needs in its own database; whole Notification or RemoteViews objects aren’t a stable persistence format.
  3. Not every system change produces an observable notification event. USB state, for example, should be observed through the relevant system API rather than inferred entirely from notifications.

Call getActiveNotifications() only after connection. It synchronizes notifications that are still active and visible to this listener, not a history of dismissed notifications. After disconnection, an empty local set represents unavailable state, not proof that the device has no notifications. A real UI should observe data-layer snapshots that include connection status and move persistence work out of callbacks.

From Android 15 (API 35), untrusted notification listeners cannot read unredacted content from notifications in which an OTP is detected. Notification access therefore does not guarantee access to every field. See Android 15 notification-content protections.
