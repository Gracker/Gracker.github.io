主线程运行机制的本质

主线程的很多 Java 工作经由 Looper 分发 Handler 消息；MessageQueue 负责排队/取消息，不直接执行业务。nativePollOnce 还会处理文件描述符事件，Vsync 接收就是其中一条路径，因此不能说主线程的一切工作都是一条 Java Message。下图展示该样例的等待和消息分发。

Choreographer 自 API 16 提供。Vsync 节拍和缓冲有助于组织渲染，但不保证帧率稳定；后续 BLAST 改变 buffer/transaction 提交路径，具体见下文。

对于用户来说，稳定的帧率才是好的体验，比如你玩王者荣耀，相比 fps 在 60 和 40 之间频繁变化，用户感觉更好的是稳定在 50 fps 的情况.

这是对体验的直观描述；实际平滑度还取决于呈现间隔。固定 60 Hz 屏幕无法用整数个刷新周期均匀呈现 50 fps，不能据此给所有设备的帧率波动作统一排名。

引入 Choreographer

Choreographer 为动画和遍历等到期回调提供与显示时序相关的执行机会。收到一次软件 Vsync 通知后，还要等待所属 Looper 的调度；它不是显示硬件中断直接执行 Java 绘制。

下图是旧的 60 Hz 简图，16.6 ms 不能作为所有设备的端到端预算。图中 RenderThread 标作 GPU 并不准确：它是 CPU 线程，负责组织并提交绘制工作，GPU 异步执行；UI、RenderThread、GPU 与 SurfaceFlinger 的阶段也可能重叠。

120 Hz 的相邻刷新间隔约 8.33 ms，实际工作期限还受流水线调度影响。刷新率与帧率的区别可结合90 Hz 文章阅读。

Choreographer 简介

Choreographer 协调注册到它的帧回调，不接管所有 Handler 消息。框架按 Input、Animation、Insets Animation、Traversal、Commit 的顺序处理已到期回调；这些是执行阶段，不是 Linux 线程优先级。

它通过 DisplayEventReceiver 请求/接收软件 Vsync 时序。应用、RenderThread、GPU 和 SurfaceFlinger 是否及时完成，仍需分别观测，不能从“使用了 Choreographer + BLAST”推出稳定 60/90/120 fps。APM 接口的观测范围见后文。

流程图有助于解释机制，这篇我主要用 Perfetto 和 MethodTrace 来讲。把 CPU、SurfaceFlinger、SystemServer 和 App 的活动放在同一条时间线上，再对照代码，比较容易看清它们怎样配合。下面会引用少量示意图，其余尽量跟着 Trace 走；具体能看到哪些活动，仍要看采集内容。

Choreographer 的工作流程

  1. getInstance() 在有 Looper 的线程上取得默认线程局部实例，初始化 Handler、DisplayEventReceiver 和回调队列。
  2. 有到期工作时按需请求 Vsync；文件描述符事件到达后，经 JNI 回调 onVsync()，再投递异步 Message。
  3. Message 被 Looper 分发时，run() 调用 doFrame()，处理帧时间、到期回调和诊断标记。
  4. 顺序执行 Input → Animation → Insets Animation → Traversal → Commit。Traversal 可能进行 measure/layout/draw，与 RenderThread 同步；不是每帧都重做所有步骤。
  5. RenderThread/GPU 绘制、BLAST 提交及 SurfaceFlinger 合成可与这些工作交叠。Commit 不是 GPU 完成或上屏回调。
  6. 动画/滚动等仍有工作时重新注册下一次帧回调，才形成连续过程；单次 FrameCallback 不会自动永久循环。

源码小结

  1. getInstance() 是当前 Looper 线程的默认实例入口，不是全进程单例，也不能推广成框架内部永远不允许同线程有其他 Choreographer。
  2. Binder 控制请求、BitTube 事件、native FD 回调和 Java 异步 Message 是不同环节；没有直接把硬件中断当 Java 绘制执行。
  3. 五阶段处理顺序给输入/动画更新先于遍历的机会，但只运行到期工作；COMMIT 不是 GPU fence 或显示完成通知。
  4. ListView/RecyclerView 的布局、绑定、滚动和预取可能出现在不同调用路径。ViewHolder 复用不是 Choreographer 的独立阶段，也不能据此推导 RecyclerView 一定更快；按库版本和实际 trace 定位。
  5. 一次 FrameCallback 运行后被移除，动画靠继续注册维持节奏。框架协调时序，不保证每个回调都按时或每个 buffer 都能呈现。

APM 与 Choreographer

先区分监控对象：帧回调节奏、Window/HWUI 处理、SurfaceFlinger 呈现、一次 Looper 消息，都不是同一个指标。FrameInfo 是隐藏内部结构，应用不应把反射它当稳定接口。

  • API 16 FrameCallback：观察回调节奏，间隔增大可提示延迟，但不是实际显示 fps。
  • API 24 FrameMetrics：按窗口接收帧报告；listener 文档中的 dropCountSinceLastInvocation 是丢失的报告数，不是显示丢帧。回调中的对象会复用，应先复制再异步处理。
  • API 33 postVsyncCallback：提供 FrameData 候选时间线、deadline 和 expected presentation 信息；仍是单次回调及调度预测，不是已呈现证明。见 Choreographer API。
  • gfxinfo/FrameTimeline：前者读对应版本的 HWUI 数据；Android 12 起的 FrameTimeline 用 expected/actual 与呈现关联辅助判断 jank，要求实际采集到该数据源。
  • Looper/IdleHandler：消息分发墙钟和队列空闲可辅助排查，不覆盖 GPU/呈现；IdleHandler 不是每帧结束回调。

利用 Perfetto 进行高级监控

命令形式为 adb shell dumpsys gfxinfo <packagename> framestats，执行前替换包名。下面是原文 StatusBar 历史输出，不是本轮采集结果：

CSV 必须按自身表头解析。时间点与 DequeueBufferDuration/QueueBufferDuration 这类持续时间要分开，单位为 ns；FrameInfo 使用单调时钟，不是日历时间。旧字段 OldestInputEvent=9223372036854775807、NewestInputEvent=0 是未记录输入的哨兵，不能拿来算巨大的输入延迟。

利用 SurfaceFlinger 进行监控

旧版可先用 adb shell dumpsys SurfaceFlinger --list 找 layer，再查询对应的 --latency，例如 adb shell 'dumpsys SurfaceFlinger --latency "实际 layer 名称"'。只给 --latency 不等于已选中某个 App；实现和权限依设备版本而异。

以 Android 10 FrameTracker 为参照，首行为刷新周期，后面三列为 desired present、actual present、frame ready 时间（ns）。该版本 ring 有 128 个槽，dump 遍历 127 个；不是固定拿到 128 个新有效帧。0、未完成 fence 的 INT64_MAX 等记录须识别为无效/未完成。

原来的 ceil((C - A) / refresh_period) 只涉及 ready 与 desired 的差值，没使用 actual present，不能当作通用丢帧公式；高刷新率切换、流水线期限和缺失值也会影响估算。现代分析优先关联 FrameTimeline 的帧与呈现数据。

利用 SurfaceFlinger PageFlip 机制进行监控

此接口已过时，只保留历史说明。 Android 10 的私有事务码 1013 曾返回默认显示的 page-flip 计数，受 system UID/HARDWARE_TEST 等系统权限检查约束，不是某个 App 的 fps。Android 16 对同一码直接返回 NAME_NOT_FOUND。原文直接 transact() 后 readInt() 的做法未处理失败，不再作为可用监控示例。

这是两个版本的独立节选，不是同一个 switch。新实现请按监控对象选择 FrameMetrics 或 FrameTimeline；不支持、权限不足和无数据不能记成 0 fps。Android 16 SurfaceFlinger

Choreographer 自身的掉帧计算逻辑

以下是旧式简化节选。jitterNanos 指实际开始相对该次携带帧时间的延迟；整除 interval 是错过节拍的诊断估算，不是这次 doFrame 的执行时长或最终呈现丢帧数。Android 16 按事件的 frameInterval 计算，并处理 interval=0 等分支。

SKIPPED_FRAME_WARNING_LIMIT 默认 30，属性在类初始化时读取。没有达到输出门槛不表示没有卡顿；改日志门槛也不会修复卡顿。

BlockCanary

BlockCanary 的历史思路是通过 Looper MessageLogging 观察消息分发前后。下方旧 Looper 骨架只说明日志位置，新版可能拆成 loopOnce 等实现；不是当前库的安装建议或维护状态保证。

测得的是 dispatch 墙钟时间，包含同步等待和调度延迟，不是纯 CPU；它不覆盖 nativePollOnce 的全部 FD 工作、GPU 或显示。连续短消息也可能使后续帧迟到。日志回调有开销，并应与其他使用同一 Looper logger 的工具协调。

MessageQueue 与 Choreographer

同步屏障是队列机制，不是 CPU 优先级提升。以 Android 10 MessageQueue.next() 为例，队首为屏障（target 为 null）时会寻找后续异步消息，再检查它是否已到执行时间；它不会抢占当前正在运行的回调，也不是另开线程。

框架内部用 postSyncBarrier()/removeSyncBarrier() 管理屏障，这些不是应用稳定公开 API。Message.setAsynchronous(boolean) 自 API 22 已公开，Handler.createAsync() 自 API 28 公开；旧文把 setAsynchronous 标成隐藏方法是错误的。没有阻挡它的屏障时，异步标记不会自动把消息移到队首，跨 Handler 的顺序依赖也不能被忽略。

厂商优化

系统厂商由于可以直接修改源码，也利用这方面的便利，做一些功能和优化，不过由于保密的问题，代码就不直接放上来了，我可以大概说一下思路，感兴趣的可以私下讨论

下面是我当时的一些工程思路，不是 AOSP 默认行为或所有固件已验证的收益。实际修改需要维持输入/生命周期顺序、动画时间基准和 buffer/fence 合同，并比较延迟、呈现、功耗与兼容性。

移动事件优化

Choreographer 已有 CALLBACK_INPUT，ViewRootImpl 可在这里消费批量输入；不能说它完全没有 input。厂商可以把更多输入状态用于更早调度，但需要区分接收、批量消费和应用回调，验证事件顺序、重采样及输入到呈现延迟。

后台动画优化

不可见且没有业务必要的动画，可以结合生命周期/可见性停止更新。厂商也可研究受控限制，但“后台”不自动等于所有回调无意义，需考虑多窗口、画中画和状态推进等情形。下面旧图可见密集 doFrame，我当时标注的是后台场景；图本身没有独立的可见性、功耗或固件配置证据，不能据此评判现在同一应用的行为。

帧绘制优化

厂商可研究在特定场景提前调度合成，而不机械等待原计划的软件时序；这不表示显示面板可以任意时刻呈现。SurfaceFlinger/HWC 仍需满足 buffer、fence、显示 deadline 和功耗约束，不能仅凭“提前做合成”推断少掉帧。

应用启动优化

启动关键消息被排队工作延迟时，可以先定位无关耗时和等待，再考虑受控调度。直接把任意启动 Message 移到队首可能破坏生命周期、输入顺序或让其他任务饥饿；收益应以首帧/可交互时间和回归场景验证，不能只看某条消息更早运行。

animation callback 前置

上一帧主线程工作结束到下个 Vsync 之间可能有余量，但不保证 CPU 空闲；其他消息、线程和 GPU 仍可工作。提前计算动画需要保持 frameTime、属性更新及输入采样的一致性。它属于特定框架策略，不能默认提前执行就减少 jank。

插帧

这里更接近厂商预渲染/预测后续动画状态的构想，不能把“一个 Vsync 调两次 doFrame”定义为通用插帧。doFrame 有已调度状态、单调帧时间和回调队列约束；多执行一次不等于生成、提交或呈现第二帧，也不等于图像运动补偿。

OverScroller 可根据当前速度/边界预测滚动，但新输入、碰边、布局与内容变化会使预测失效。若尝试提前准备，必须处理取消、时间基准、额外 buffer/功耗和真实呈现节奏；不能声称 touch up 时已确定之后每帧的全部内容。

高帧率优化

当显示模式实际工作在 120 Hz 时，刷新间隔约 8.33 ms，而不是 60 Hz 的 16.67 ms；应用出帧率仍可能不同。优化应同时观察工作期限、帧呈现节奏和能耗，而不是把整个流水线都塞进固定的单线程预算。厂商需要评估的方向包括：

  1. 超级 App 的性能表现以及优化
  2. 游戏高帧率合作
  3. 120 fps、90 fps 和 60 fps 相互切换的逻辑
